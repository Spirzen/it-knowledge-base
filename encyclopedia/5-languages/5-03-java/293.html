Hibernate и JPA — практический старт​

JPA (Jakarta Persistence API) — стандарт ORM: работа с БД через объекты. Hibernate — основная реализация JPA в Java.

В Spring Boot обычно используют Spring Data JPA, а не EntityManager вручную.

База Spring: Первая программа на Spring · обзор ORM: 110.md · Spring Framework.

Зависимости (Maven)​

В start.spring.io выберите: Spring Web, Spring Data JPA, H2 Database.

Или в pom.xml:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>runtime</scope>
</dependency>

Разбор:

  • этот XML-блок описывает конфигурацию сборки, которую инструмент считывает до выполнения прикладного Java-кода.
  • элементы с артефактами spring-boot-starter-data-jpa, h2 включают нужные библиотеки и определяют доступные API в кодовой базе.
  • секция <scope>test</scope> ограничивает зависимость тестовым контуром и не тащит ее в production-артефакт.
  • любое изменение здесь влияет на classpath и поведение сборки, поэтому такие правки проверяют полным прогоном тестов.
  • после редактирования этого фрагмента проверяют, что проект собирается и тестовый раннер видит нужные классы без конфликтов версий.

application.properties:

spring.datasource.url=jdbc:h2:mem:notes
spring.h2.console.enabled=true
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true

Разбор:

  • блок задает runtime-конфигурацию приложения, и эти параметры читаются фреймворком при старте контекста.
  • ключи spring.datasource.url, spring.h2.console.enabled, spring.jpa.hibernate.ddl-auto, spring.jpa.show-sql управляют подключением к БД, режимом генерации схемы и диагностическим выводом SQL.
  • изменение значений здесь мгновенно меняет поведение приложения без правок Java-классов.
  • такие параметры важно разделять по окружениям (dev/test/prod), чтобы безопасные настройки разработки не ушли в production.
  • корректность проверяется запуском приложения и фактическим поведением: подключение к БД, миграции и ожидаемые логи.

Сущность​

package com.example.notes;

import jakarta.persistence.*;

@Entity
@Table(name = "notes")
public class Note {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 500)
    private String text;

    protected Note() {}

    public Note(String text) {
        this.text = text;
    }

    public Long getId() { return id; }
    public String getText() { return text; }
    public void setText(String text) { this.text = text; }
}

Разбор:

  • фрагмент показывает прикладной сценарий по теме раздела: здесь есть входные данные, операции над ними и проверяемый итог.
  • аннотации Entity, Table, Id, GeneratedValue, Column включают поведение фреймворка (тестовый раннер, web-маршрутизация, ORM или транзакционные правила).
  • ключевые вызовы Table, GeneratedValue, Column, Note, getId, getText, setText задают основную механику этого примера: обработку, проверку и формирование результата.
  • чтение этого блока по шагам дает предсказуемую картину: сначала подготовка данных, затем действие API, затем получение конечного значения.
  • после запуска стоит проверить именно эффект этого примера: вывод, значение переменной, статус ответа, состояние БД или результат теста.
  • при переносе в production обычно добавляют валидацию входа, явную обработку ошибок и тест на граничные случаи вокруг этого сценария.

REST-контроллер​

package com.example.notes;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.server.ResponseStatusException;

import java.util.List;

@RestController
@RequestMapping("/api/notes")
public class NoteController {

    private final NoteRepository repo;

    public NoteController(NoteRepository repo) {
        this.repo = repo;
    }

    @GetMapping
    public List<Note> list() {
        return repo.findAll();
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public Note create(@RequestBody NoteCreate body) {
        return repo.save(new Note(body.text()));
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void delete(@PathVariable Long id) {
        if (!repo.existsById(id)) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND);
        }
        repo.deleteById(id);
    }

    public record NoteCreate(String text) {}
}

Разбор:

  • фрагмент показывает прикладной сценарий по теме раздела: здесь есть входные данные, операции над ними и проверяемый итог.

  • ключевые вызовы RequestMapping, NoteController, list, findAll, ResponseStatus, create, save задают основную механику этого примера: обработку, проверку и формирование результата.

Ключевые понятия​

ТерминСмысл
Entityтаблица в виде класса
PersistenceContextкэш сессии Hibernate
ddl-auto=updateсхема подстраивается (только dev!)
Lazy loadingсвязи грузятся по требованию

Production: миграции через Flyway или Liquibase, не ddl-auto=update.

Жизненный цикл сущности простыми словами​

Чтобы перестать "магически" воспринимать JPA, полезно держать в голове четыре состояния объекта:

СостояниеЧто это значит
New (transient)объект создан через new, в БД еще нет
Managedобъект прикреплен к persistence context, Hibernate отслеживает изменения
Detachedобъект был managed, но контекст закрыт
Removedобъект помечен на удаление и будет удален при flush/commit

Практическая выгода: вы понимаете, почему save() иногда делает INSERT, а иногда UPDATE.

Сервисный слой и транзакции​

В учебном примере контроллер работает напрямую с репозиторием, это нормально для старта. В боевом сервисе обычно добавляют слой сервиса и явную транзакцию:

@Service
public class NoteService {
    private final NoteRepository repo;

    public NoteService(NoteRepository repo) {
        this.repo = repo;
    }

    @Transactional
    public Note rename(Long id, String text) {
        Note note = repo.findById(id)
            .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
        note.setText(text);
        return note;
    }
}

Разбор:

  • фрагмент показывает прикладной сценарий по теме раздела: здесь есть входные данные, операции над ними и проверяемый итог.
  • аннотации Service, Transactional включают поведение фреймворка (тестовый раннер, web-маршрутизация, ORM или транзакционные правила).
  • ключевые вызовы NoteService, rename, findById, orElseThrow, ResponseStatusException, setText задают основную механику этого примера: обработку, проверку и формирование результата.
  • чтение этого блока по шагам дает предсказуемую картину: сначала подготовка данных, затем действие API, затем получение конечного значения.
  • после запуска стоит проверить именно эффект этого примера: вывод, значение переменной, статус ответа, состояние БД или результат теста.
  • при переносе в production обычно добавляют валидацию входа, явную обработку ошибок и тест на граничные случаи вокруг этого сценария.

Почему так удобнее:

  • бизнес-логика не размазывается по контроллерам;
  • правила транзакций концентрируются в одном месте;
  • код проще покрывать тестами.

Связи сущностей на минимальном примере​

Частый шаг после первой таблицы — добавить автора заметки:

@Entity
public class Author {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
}

@Entity
public class Note {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "author_id", nullable = false)
    private Author author;
}

Разбор:

  • фрагмент показывает прикладной сценарий по теме раздела: здесь есть входные данные, операции над ними и проверяемый итог.
  • аннотации Entity, Id, GeneratedValue, ManyToOne, JoinColumn включают поведение фреймворка (тестовый раннер, web-маршрутизация, ORM или транзакционные правила).
  • ключевые вызовы GeneratedValue, ManyToOne, JoinColumn задают основную механику этого примера: обработку, проверку и формирование результата.
  • чтение этого блока по шагам дает предсказуемую картину: сначала подготовка данных, затем действие API, затем получение конечного значения.
  • после запуска стоит проверить именно эффект этого примера: вывод, значение переменной, статус ответа, состояние БД или результат теста.
  • при переносе в production обычно добавляют валидацию входа, явную обработку ошибок и тест на граничные случаи вокруг этого сценария.

На этом этапе важно понимать разницу EAGER и LAZY, иначе появляются лишние SQL-запросы и просадки производительности. Полезное продолжение: ввод-вывод и файлы и асинхронность, если API работает под нагрузкой.

Частые ошибки на старте JPA​

  1. @Entity без пустого конструктора — Hibernate не сможет создать объект.
  2. Использование ddl-auto=update в production — миграции становятся непредсказуемыми.
  3. Возврат сущностей напрямую во внешний API без DTO — утечки полей и проблемы с lazy loading.
  4. Отсутствие индексов в БД на часто фильтруемые поля.

Дальше​

  • связи @OneToMany, @ManyToOne;
  • @Transactional на сервисном слое;
  • JUnit 5 с @DataJpaTest.
