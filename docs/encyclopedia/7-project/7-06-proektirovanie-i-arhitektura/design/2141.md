# Оценка архитектурных альтернатив

<span class="complexity-badge">Аналитику</span>

Спор «монолит vs микросервисы» требует **явной оценки альтернатив** в контексте проекта: какие NFR важны, какие риски приемлемы, сколько стоит владение. Эта статья — практичный шаблон для архитектора и техлида, без тяжёлого ATAM «на полгода».

Связь: [NFR](1116.md), [ADR в основах](../1.md), [техническое письмо — архитектурное решение](/encyclopedia/7-project/7-08-tehnicheskoe-pismo/1002), [роль архитектора](../117.md).

---

## Когда нужна формальная оценка

- Выбор стиля развёртывания или способа интеграции.
- Смена брокера, БД, облака, модели согласованности.
- Спор между командами, который повторяется каждый квартал.
- Требование аудита или регулятора «обосновать решение».

Не нужна для: переименования пакета, выбора между двумя равными библиотеками с одинаковым риском (достаточно spike на два дня).

---

## Шаг 1. Зафиксировать контекст и драйверы

**Контекст** — одна фраза проблемы:

> «Нужно обрабатывать до 3 000 заказов/мин с p95 ≤ 400 мс и выдерживать падение одной AZ без потери заказов».

**Архитектурно значимые требования** (quality attributes) — обычно 3–6 штук, не двадцать:

| Атрибут | Вопрос | Пример формулировки |
|---------|--------|---------------------|
| Производительность | Какая нагрузка и latency? | p95 ≤ 400 мс при 3k RPM |
| Доступность | Допустимый простой? | 99.9%, RTO 15 мин |
| Масштабируемость | Как растём? | Горизонтально без простоя |
| Безопасность | Где границы доверия? | PCI: карты только в Payment context |
| Сопровождаемость | Сколько команд? | 4 команды, независимый релиз раз в 2 недели |
| Стоимость | Бюджет инфры/людей? | OpEx облака ≤ X / месяц |

Полный каталог атрибутов качества (ISO/IEC 25010) в жизни сводят к такому короткому списку — иначе таблица не заполняется. Развёрнутый разбор всех характеристик — [модель ISO/IEC 25010](/encyclopedia/7-project/7-13-ekonomika-proizvodstva-po/2).

---

## Шаг 2. Набросать 2–4 варианта (не больше)

Пример для заказов:

- **A.** Модульный монолит + read replicas.
- **B.** Микросервисы Order / Payment / Inventory, синхронный REST.
- **C.** То же, но Order → события → Payment и Inventory (async).
- **D.** Оставить легаси, Strangler только для витрины.

Вариант «как сейчас, но на Kubernetes» — не вариант, если не меняется граница ответственности.

---

## Шаг 3. Матрица trade-off

Оценки: **++** / **+** / **0** / **−** / **−−** или баллы 1–5 — главное, **одна шкала для всех**.

| Критерий (вес) | A Модульный монолит | B MS sync | C MS events |
|----------------|---------------------|-----------|-------------|
| Time-to-market (×3) | ++ | − | − |
| p95 latency (×3) | + | 0 | + |
| Независимый релиз (×2) | − | ++ | ++ |
| Сложность эксплуатации (×2) | ++ | −− | − |
| Согласованность заказа (×3) | ++ | + | 0 |
| Стоимость (×1) | ++ | − | − |

**Веса** ставятся с бизнесом: для стартапа часто ×3 на time-to-market, для банка — на согласованность и аудит.

<div class="callout callout--info">
  <div class="callout-title">Разбор</div>
  <p>Вариант C выигрывает по релизам, но проигрывает по <strong>объяснимости для пользователя</strong> (eventual consistency). Если продукт обещает «мгновенную оплату», на витрине нужен UX под задержку — иначе матрица «красивая», продукт — нет.</p>
</div>

## Шаг 4. Риски и «что убьёт вариант»

Для каждого варианта — **deal-breaker**:

- B: нет зрелого tracing → при инциденте MTTR &gt; 4 ч → отклонить до внедрения observability.
- C: нет идемпотентных consumer’ов → дубли заказов → блокер.

Spike на 3–5 дней дешевле, чем полгода «распределённого монолита».

---

## Шаг 5. Решение и ADR

Краткий ADR (можно в `docs/adr/001-order-architecture.md`):

```markdown
## Контекст
3k RPM, 4 команды, легаси-Billing менять нельзя 12 месяцев.

## Решение
Модульный монолит Order+Fulfillment; Payment — Strangler через ACL;
события только на границе с Billing.

## Последствия
+ быстрый релиз, одна транзакция для заказа
− Payment остаётся узким местом до миграции
```

## Architecture review (лёгкий формат)

**30–45 минут**, участники: автор решения, техлиды затронутых команд, по желанию ops/security.

Повестка:

1. Контекст и NFR (5 мин).
2. Варианты и матрица (10 мин).
3. Риски и spike’и (10 мин).
4. Решение и действия (10 мин).

Не голосование «большинством» — ответственность за решение остаётся у архитектора/техлида с фиксацией в ADR.

**Fitness functions** (по желанию): автопроверки в CI — запрет циклических зависимостей между модулями (ArchUnit, Deptrac), линтер на запрещённые импорты между контекстами.

## Мини-кейс: синхронный REST и очередь

**Сценарий:** после `OrderCreated` нужно списать остаток и отправить чек.

| | Sync REST | Async event |
|--|-----------|-------------|
| Плюс | Проще отладка, сразу ошибка в UI | Слабая связность, пики сглаживаются |
| Минус | Цепочка отказов, latency суммируется | Задержка, дубли, сложнее тесты |
| Когда | Мало вызовов, жёсткая согласованность | Высокий throughput, допустима задержка |

Частый компромисс: **sync до оплаты** (пользователь ждёт), **async после** (email, аналитика, склад).
