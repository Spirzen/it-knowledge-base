## С чего начинается выбор

До сравнения вендоров в компании уже есть **мотив** (стратегия, боль финдиректора, регулятор, рост холдинга). Дальше нужно перевести мотив в **проверяемые требования**.

**Ключевой сотрудник** — тот, от чьей работы зависит результат подразделения и кто знает процесс "как на самом деле" (руководитель или ведущий исполнитель). Они формируют списки; проектная команда сводит их в **единый перечень функциональных требований**.

Типичные **нефункциональные** требования к КИС:

- производительность и отказоустойчивость;
- масштабирование и мониторинг;
- доработки и совместимость при обновлениях;
- разграничение прав (в т.ч. RLS на уровне записей);
- интеграция с текущим **ИТ-ландшафтом**;
- обучение, UX, стоимость **владения**;
- наличие отработанной **методики внедрения** у исполнителя.

**Функциональные** отвечают на вопрос "что должна делать система" (модули продаж, закупок, производства, казначейства, учёта и т.д.).

### Критерии хорошей формулировки

| Критерий | Смысл |
|----------|--------|
| Полнота | Описан сценарий целиком |
| Точность | Без "прозрачной" и "гибкой" без метрик |
| Осуществимость | Технически возможно |
| Необходимость | Не "хотелки" без владельца |
| Приоритет | Что в первую очередь |
| Проверяемость | Как примем на приёмке |

На раннем сборе допустимы черновые фразы; перед тендером их уточняют. Пример проверяемой формулировки — "Отчёт по всем организациям за месяц строится **не дольше 3 минут** с разрезами X, Y, Z".

## Тендер и запрос предложений

На рынке ERP выбор часто идёт через **тендер**. Цепочка документов может включать:

| Документ | Назначение |
|----------|------------|
| **RFI** | Запрос информации — знакомство с рынком |
| **RFP** | Запрос предложения — требования и условия участия |
| **RFQ** | Уточнение цены по выбранному варианту |

В **RFP** передают спецификацию требований (часто по модулям ERP). Исполнители отвечают коммерческим предложением и заполненным **fit-gap**.

<div class="callout callout--caution">
  <div class="callout-title">Нет требований — нет проекта</div>

  <div class="callout-body">
  Если у заказчика нет детализированных требований, готовности к полномасштабному внедрению тоже нет. Нужен **предпроект** (обследование) с отдельным договором и "вилками" бюджета основного этапа. Оценка "на глаз" по всем фазам сразу — явный **риск** для сроков и сметы.
  </div>
</div>

Дополнительно на этапе выбора проверяют **нагрузочные тесты** (типовой сценарий под число пользователей и объём данных), **перспективный ИТ-ландшафт** и **обоснование окупаемости** (ROI) автоматизации.

## Fit-gap анализ

**Fit-gap** — сопоставление требований заказчика с возможностями конкретной ERP: где **подходит (fit)**, где **разрыв (gap)**.

Исполнитель (внешний или внутренняя команда) берёт таблицу требований из RFP и для каждой строки ставит оценку. Расширенный шаблон может включать столбцы:

| Столбец | Значение |
|---------|----------|
| Требование | Краткое описание |
| Приоритет | 1 (высший) … 10 |
| Обязательность | Must have на первом этапе |
| Из коробки | Штатная функция |
| Настройка | Без программирования |
| Модификация | Нужна разработка |
| Стороннее решение | Интеграция + лицензия |
| В roadmap вендора | Появится в версии |
| Не поддерживается | Ограничение платформы |
| Комментарий | Пояснение оценки |

Упрощённый вариант — два столбца **fit / gap** или шкала 0–10, но тогда нюансы ("поддерживается, но только после доработки") уходят в комментарии.

**Как заполняют:** рассылка экспертам по блокам, совместный разбор в переговорной, уточнения у заказчика при двусмысленности. Заказчик потом сравнивает несколько систем по **одной** структуре таблицы.

Разница **настройка** и **модификация** критична для TCO: модификации проверяют при каждом обновлении платформы. **Сторонние** решения добавляют интеграцию и лицензии.

### Пример фрагмента таблицы

Упрощённый фрагмент для модуля "Продажи" (одна ERP в тендере; для сравнения вендоров — те же строки, разные столбцы оценки):

| ID | Требование | Must | Оценка | Комментарий |
|----|------------|------|--------|-------------|
| S-01 | Резервирование товара под заказ клиента | да | Настройка | Типовой механизм резервов |
| S-02 | Скидка от объёма по 5 уровням прайса | да | Из коробки | |
| S-03 | Автоотправка КП на email из карточки заказа | нет | Модификация | Нужна интеграция с почтовым шлюзом |
| S-04 | Учёт серийных номеров при отгрузке | да | Настройка + обучение | Редкая операция — проверить на ОЭ |

По итогам таблицы считают долю **must have**, закрытых "из коробки" и настройкой, и отдельно — **трудоёмкость** всех модификаций и интеграций для сметы.
