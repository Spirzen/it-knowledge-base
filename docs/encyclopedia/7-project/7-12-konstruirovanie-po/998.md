## FAQ — Часто задаваемые вопросы

Вопросы студентов и джунов на стыке "учебник SDLC" и реальной команды: где конструирование в спринте, зачем PERT, когда Waterfall. Здесь — **практика и путаницы**; формулировки для зачёта — в [чек-листе](./999).

<div class="faq-list">

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Мы "просто пишем код" в Jira — зачем отдельно говорить про конструирование?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Конструирование — это не только набор текста, а <strong>артефакты</strong>: код, unit-тесты, сборки, интеграция модулей. Без явной стадии легко забыть DoD, ревью и локальную верификацию. Подробнее здесь — [глава 1](/encyclopedia/7-project/7-12-konstruirovanie-po/1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Архитектор нарисовал диаграмму — это уже конструирование?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Нет, это <strong>проектирование</strong> (вход). Конструирование начинается, когда решения воплощаются в исходниках, тестах и скриптах сборки. Подробнее здесь — [глава 1](/encyclopedia/7-project/7-12-konstruirovanie-po/1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> В Scrum "нет фазы кодирования" — где тогда конструирование?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Оно <strong>каждый спринт</strong>: инкремент = working software + тесты по DoD. Фаза не исчезает, она внутри итерации. Подробнее здесь — [глава 1](/encyclopedia/7-project/7-12-konstruirovanie-po/1), [Scrum](/encyclopedia/7-project/7-14-scrum/4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Много файлов в репозитории — значит, модульность хорошая?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Не обязательно: важны <strong>границы ответственности</strong>, связность внутри и слабое сцепление между модулями. "God package" из сотни файлов — не модульность. Подробнее здесь — [глава 2](/encyclopedia/7-project/7-12-konstruirovanie-po/2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Поменял одно поле DTO — упало пять сервисов. Что пошло не так?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Высокое <strong>сцепление</strong> и connascence: изменение в одном месте тянет цепочку. Сигнал пересмотреть границы и контракты (OpenAPI, версии API). Подробнее здесь — [глава 2](/encyclopedia/7-project/7-12-konstruirovanie-po/2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Преподаватель требует Waterfall, в стажировке — Agile. Кто прав?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Оба контекста: регуляторика и фиксированный scope → длинная фаза кодирования после проекта; продукт с обратной связью → инкременты. Универсального процесса нет. Подробнее здесь — [глава 3](/encyclopedia/7-project/7-12-konstruirovanie-po/3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> V-модель — это то же, что unit-тесты в CI?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> V-модель — <strong>идея парности</strong>: уровень кода ↔ unit-тесты, интеграция ↔ integration tests. CI автоматизирует правую "ногу" V на практике. Подробнее здесь — [глава 3](/encyclopedia/7-project/7-12-konstruirovanie-po/3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> RAD дали на хакатоне — можно так же в банке?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> RAD ускоряет прототип UI/CRUD, но без плана <strong>"закалки"</strong> прототип станет продом с дырами. В банке нужны NFR, аудит, тесты — иначе антипаттерн. Подробнее здесь — [глава 3](/encyclopedia/7-project/7-12-konstruirovanie-po/3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Критический путь в Gantt "красный" — что делать команде разработки?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Задачи на критическом пути <strong>без резерва (float = 0)</strong> — любая задержка бьёт по сроку релиза. Приоритет ресурсов, снятие блокеров, не распылять людей с CP. Подробнее здесь — [глава 4](/encyclopedia/7-project/7-12-konstruirovanie-po/4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> PERT дал 6 месяцев, менеджер обещал 3 — кому верить?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> PERT с O/M/P — <strong>диапазон</strong>, не wishful thinking. Если P (пессимист) игнорируют, риск срыва на интеграции. Обсудите допущения и резерв. Подробнее здесь — [глава 4](/encyclopedia/7-project/7-12-konstruirovanie-po/4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Planning Poker: все сказали "8", один "1" — давить на единицу?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Нет — <strong>обсудите расхождение</strong>: разное понимание scope или рисков. Poker для выявления неопределённости, не голосования большинством. Подробнее здесь — [глава 4](/encyclopedia/7-project/7-12-konstruirovanie-po/4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> OpenAPI "потом допишем" — можно начать код?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Можно параллельно, но без контракта растёт <strong>рассинхрон</strong> frontend/backend. Минимум — стабильные пути, схемы ошибок, версионирование. Подробнее здесь — [глава 5](/encyclopedia/7-project/7-12-konstruirovanie-po/5).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Зачем DSL, если есть Python?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> DSL сжимает <strong>доменный язык</strong> (правила, конфиги, пайплайны). Избыточен для разовой задачи; полезен, когда правила пишут не только программисты. Подробнее здесь — [глава 5](/encyclopedia/7-project/7-12-konstruirovanie-po/5).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> TDD "не успеваем" — отменить на проекте?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> TDD — один из способов локальной верификации на конструировании. Без тестов скорость кажется выше, но <strong>стоимость дефектов</strong> растёт на интеграции. Компромисс — критичные модули с TDD, остальное — тесты после. Подробнее здесь — [глава 5](/encyclopedia/7-project/7-12-konstruirovanie-po/5).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Цикломатическая сложность — это только для линтера?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Конструктору она показывает, где <strong>много веток</strong> и нужны unit-тесты по путям. Связь с white-box тестированием и рефакторингом. Подробнее здесь — [глава 2](/encyclopedia/7-project/7-12-konstruirovanie-po/2), [культура кода](/encyclopedia/7-project/7-10-kultura-koda/2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> CBSE — купили готовый компонент, интеграция "на вечер"?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Нужны <strong>адаптеры, контрактные тесты</strong>, учёт лицензий и версий. COTS экономит время только при явных границах интеграции. Подробнее здесь — [глава 3](/encyclopedia/7-project/7-12-konstruirovanie-po/3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Спираль Боэма — это Agile?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Спираль — про <strong>управление рисками</strong> прототипами и витками; Agile — про частую поставку ценности. Пересекаются, но не синонимы. Подробнее здесь — [глава 3](/encyclopedia/7-project/7-12-konstruirovanie-po/3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> WBS построили, но сроки всё равно плывут — почему?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> WBS без <strong>зависимостей, ресурсов и CP</strong> — только список работ. Добавьте Gantt/CPM, резервы, учёт параллелизма команды. Подробнее здесь — [глава 4](/encyclopedia/7-project/7-12-konstruirovanie-po/4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> "20–30 строк на unit-тест" — жёсткое правило?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Ориентир на <strong>локальную проверку</strong> одного поведения; длинный тест часто проверяет слишком много и ломается непонятно почему. Подробнее здесь — [глава 6](/encyclopedia/7-project/7-12-konstruirovanie-po/6).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Связность "случайная" — как распознать в своём пакете?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Файлы в папке <strong>не связаны одной задачей</strong> ("utils", "helpers" на всё). Признак — изменения в одном файле не требуют правок соседей по смыслу. Подробнее здесь — [глава 2](/encyclopedia/7-project/7-12-konstruirovanie-po/2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> ISO 12207 — только для госконтракта?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Это <strong>справочник процессов</strong> ЖЦ; в Agile берут идеи прослеживаемости и интеграции, не обязательно всю бюрократию. Подробнее здесь — [глава 1](/encyclopedia/7-project/7-12-konstruirovanie-po/1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Инкремент сдали, но регресс на старом функционале — кто виноват?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Часто слабая <strong>интеграция и регресс</strong> на стадии конструирования: нужны CI, контрактные и integration-тесты между инкрементами. Подробнее здесь — [глава 6](/encyclopedia/7-project/7-12-konstruirovanie-po/6), [тестирование](/encyclopedia/7-project/7-05-testirovanie/111).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> RUP — "устаревший Waterfall"?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> RUP — итеративный фреймворк с фазами; массовое конструирование — на стадии Construction. Не линейный каскад одним блоком. Подробнее здесь — [глава 3](/encyclopedia/7-project/7-12-konstruirovanie-po/3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Оценка в человеко-часах vs story points — что ставить в план конструирования?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Points — для <strong>скорости команды</strong> внутри спринта; часы/CPM — для календарного плана релиза. Смешивайте осознанно, не переводите points в рубли линейно. Подробнее здесь — [глава 4](/encyclopedia/7-project/7-12-konstruirovanie-po/4), [команда](/encyclopedia/7-project/7-02-komanda-i-upravlenie/112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Конфиг в YAML разросся — это уже конструирование или инфраструктура?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Конфигурационные языки — часть <strong>артефактов конструирования</strong> (вместе с кодом и сборкой). Граница с DevOps — там, где начинается эксплуатация сред. Подробнее здесь — [глава 5](/encyclopedia/7-project/7-12-konstruirovanie-po/5).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Myers: "цель теста — найти дефекты" — значит, QA виноваты, если баг в проде?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Нет — качество <strong>строится на конструировании</strong> (unit, ревью), системное тестирование дополняет. Баг в проде — сигнал улучшить процесс на всех уровнях V. Подробнее здесь — [глава 6](/encyclopedia/7-project/7-12-konstruirovanie-po/6).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> ТКПО в учебнике — где это в GitHub-проекте?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Аналог — <strong>repo + CI + issues + releases + документация</strong>: всё, что нужно воспроизвести сборку и понять состав поставки. Подробнее здесь — [глава 6](/encyclopedia/7-project/7-12-konstruirovanie-po/6), [SCM](/encyclopedia/7-project/7-13-ekonomika-proizvodstva-po/3).</p>
</div>

## FAQ — Поисковые запросы

Краткие ответы на формулировки, которые часто вводят в Google и Yandex.

<div class="faq-list">

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое конструирование ПО в жизненном цикле?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Стадия SDLC, где проект становится <strong>кодом, модулями, тестами и сборками</strong>; в Agile — каждый спринт. Подробнее здесь — [глава 1](/encyclopedia/7-project/7-12-konstruirovanie-po/1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> SDLC жизненный цикл разработки ПО — этапы.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Требования → проектирование → <strong>конструирование</strong> → тестирование → внедрение → сопровождение; в Agile этапы перекрываются. Подробнее здесь — [глава 1](/encyclopedia/7-project/7-12-konstruirovanie-po/1), [методология](/encyclopedia/7-project/7-03-metodologiya-i-zhiznennyy-tsikl-po/1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Waterfall модель — что это и когда применяют?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Каскад: фазы <strong>последовательно</strong>, изменения формальны. Уместна при регуляторике и фиксированном scope. Подробнее здесь — [модели ЖЦ](/encyclopedia/7-project/7-12-konstruirovanie-po/3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> V-модель тестирования — суть.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Каждому уровню разработки соответствует уровень тестов: код ↔ unit, интеграция ↔ integration. Подробнее здесь — [глава 3](/encyclopedia/7-project/7-12-konstruirovanie-po/3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Связность и сцепление модулей (cohesion coupling) — простыми словами.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>Связность</strong> — насколько элементы модуля про одну задачу; <strong>сцепление</strong> — насколько модули зависят друг от друга. Цель: высокая связность, низкое сцепление. Подробнее здесь — [глава 2](/encyclopedia/7-project/7-12-konstruirovanie-po/2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Критический путь CPM — как рассчитать?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Цепочка задач с <strong>нулевым резервом (float)</strong>; задержка любой из них сдвигает срок проекта. Подробнее здесь — [планирование](/encyclopedia/7-project/7-12-konstruirovanie-po/4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> PERT формула расчёта времени TE = (O+4M+P)/6.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Оптимист O, наиболее вероят M, пессимист P — <strong>ожидаемое время</strong> и разброс для рискованных задач. Подробнее здесь — [глава 4](/encyclopedia/7-project/7-12-konstruirovanie-po/4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Planning Poker — что это в Agile?</p>

## Что запомнить

Краткое резюме. Подробности, примеры и диаграммы — в статьях **[Конструирование ПО — понятие, жизненный цикл, стандарты](./1)**–**[Тестирование на стадии конструирования](./6)**; самопроверка — в **[чек-листе](./999)**.

**Конструирование** — стадия SDLC, на которой проект превращается в **исходный код, модули, тесты и сборки**. Она связана с проектированием (вход) и тестированием/внедрением (выход), но в Agile выполняется **итеративно**, а не одним блоком.

| Тема | Главная мысль |
|------|----------------|
| **Место в ЖЦ** | Реализация + локальная верификация; артефакты: код, unit-тесты, скрипты сборки |
| **SWEBOK / 12207** | Прослеживаемость, процессы реализации и интеграции |
| **Модульность** | Высокая **связность** внутри, низкое **сцепление** между модулями |
| **Connascence** | Что ещё придётся менять вместе — сигнал для границ |
| **Модели ЖЦ** | Waterfall — линейно; инкремент — порциями; RAD — прототипы; спираль — риски; CBSE — компоненты |
| **V-модель** | Уровень кода ↔ unit-тесты; интеграция ↔ integration tests |
| **Планирование** | WBS → Gantt; **CPM** — критический путь; **PERT** — TE = (O+4M+P)/6; Poker — points + декомпозиция |
| **Языки** | Программирование + проектирование + контракты + конфиг + DSL + конфигурационный/toolkit |
| **Тестирование на коде** | Myers: цель — найти дефекты; unit/integration; 20–30 строк — локальная проверка |
| **Шкалы СС / СЦ** | Связность 0–10, сцепление 1–9 |

---

### Формулы для запоминания

| Метод | Формула |
|-------|---------|
| PERT (ожидание) | **TE = (O + 4M + P) / 6** |
| PERT (разброс) | **σ = (P − O) / 6** |
| Float (упрощённо) | **LS − ES** (у критической задачи = 0) |

### Модели и конструирование — одной строкой

- **Waterfall / V** — длинная фаза кодирования после проекта; тесты "парные" по уровням.
- **Инкремент / Scrum** — код порциями; нужны CI, DoD и рефакторинг между инкрементами.
- **RAD** — быстрый UI и CRUD; обязателен план "закалки" прототипа.
- **Spiral** — прототипы на рисках, затем production code.
- **CBSE** — интеграция COTS + адаптеры + контрактные тесты.

На качество конструирования влияют **[культура кода](/encyclopedia/7-project/7-10-kultura-koda/intro)**, **[тестирование](/encyclopedia/7-project/7-05-testirovanie/intro)** и **[методология](/encyclopedia/7-project/7-03-metodologiya-i-zhiznennyy-tsikl-po/intro)** — они не заменяют друг друга.

Универсального процесса нет: выбор модели и глубины планирования опирается на **контекст** (регуляторика, неопределённость, размер команды) — см. Stacey и Cynefin в [SDLC](/encyclopedia/7-project/7-03-metodologiya-i-zhiznennyy-tsikl-po/1).
