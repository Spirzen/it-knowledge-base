## Black-box уже знаете — когда нужен white-box

[Black-box](/encyclopedia/7-project/7-05-testirovanie/111) проверяет **поведение снаружи**. Этого хватает для API и UI. Но внутри модуля может быть **12 веток `if`**, и один сценарий **не покрывает** опасную комбинацию.

**White-box** (тестирование «белого ящика», **структурное**) использует **знание кода**: граф потока управления, присвоения переменных, пути выполнения. Глава **2.3** учебника «экономика производства ПО» посвящена именно этому — на уровне **модулей и компонентов**.

## Граф потока управления (CFG)

**Control Flow Graph** — узлы = **базовые блоки** (последовательность без ветвлений), рёбра = **переходы**.

Пример:

```python
def discount(total, is_vip):       # блок 1
    if total > 1000:               # решение
        rate = 0.1 if is_vip else 0.05   # блок 2 / 3
    else:
        rate = 0                     # блок 4
    return total * rate              # блок 5
```

Три независимых пути через `if/else` → нужны **минимум три** теста для ветвевого покрытия (с разными `total`, `is_vip`).

Подробнее о метрике — [цикломатическая сложность](/encyclopedia/7-project/7-10-kultura-koda/2).

## Стратегии тестирования потока управления

| Стратегия | Идея | Покрытие |
|-----------|------|----------|
| **Statement** | Каждая строка выполнена хотя бы раз | Слабое |
| **Branch / decision** | Каждая ветка true/false | Базовое для модулей |
| **Condition** | Все комбинации в сложном `if a && b` | Сильнее branch |
| **Basis path** | Число путей ≈ цикломатическая сложность M | Классика McCabe |
| **Path (полное)** | Все пути | Часто нереально (экспонента) |

**Basis path testing:** выберите **M линейно независимых** путей — минимальный набор, чтобы «пройти» все ветвления разумно.

:::info Сложность тестирования
Чем выше **M**, тем **больше** обязательных сценариев. Функция с M > 15 — сигнал **упростить** код, а не «добить coverage любой ценой» ([культура кода](/encyclopedia/7-project/7-10-kultura-koda/2)).
:::

## Корректность white-box тестов

Тест **корректен**, если:

1. **Достижимость** — путь реально выполняется (нет «мертвого кода» в тесте).
2. **Оракул** — известен **ожидаемый результат** для входа ([127](/encyclopedia/7-project/7-05-testirovanie/127)).
3. **Независимость** — тесты не зависят от порядка (FIRST в [120](/encyclopedia/7-project/7-05-testirovanie/120)).
4. **Учёт данных** — ветка пройдена с **конкретными** значениями, активирующими условие.

**Ложное покрытие:** тест «прошёл» по строке, но **не проверил** результат — coverage зелёный, качество нет.

## Тестирование с учётом переменных и констант

Условия зависят от **границ**:

| Конструкция | Что проверять |
|-------------|---------------|
| `x > 1000` | 999, 1000, 1001 |
| `a && b` | все 4 комбинации true/false |
| `switch (code)` | каждый `case` + `default` |
| Константы `#define TIMEOUT 50` | граница timeout−1, timeout, timeout+1 |

Это пересекается с [эквивалентными классами и границами](/encyclopedia/7-project/7-05-testirovanie/127) — white-box говорит **где** в коде эти границы **реально** ветвят выполнение.

## Потоки данных (data flow testing)

**Поток данных** — от **определения** (definition) переменной до **использования** (use).

| Аббревиатура | Смысл |
|-------------|--------|
| **DEF** | Присвоение значения |
| **USE** | Чтение в выражении / условии |
| **DU-chain** | Цепочка def → use |

**Классы покрытия** (упрощённо для экзамена):

| Критерий | Требование |
|----------|------------|
| **All-defs** | Каждое определение имеет хотя бы один тест, доходящий до use |
| **All-uses** | Каждое use покрыто тестом от **какого-то** def |
| **All-du-paths** | Все пути def→use (дорого) |

### Мини-разбор

```csharp
int x = ReadInput();    // DEF x
if (x < 0) x = 0;       // DEF x (повторное)
return x * 2;           // USE x
```

Тесты:

1. `x = -5` → после clamp `0` → return `0`.
2. `x = 3` → return `6`.

Без теста с **отрицательным** x ветка clamp **не проверена** — branch coverage может быть неполным.

## Связь control-flow и data-flow

| Только control-flow | + data-flow |
|-------------------|-------------|
| «Зашли в `if`» | «Зашли с x=-1 и получили 0» |
| Может пропустить **неинициализированную** переменную | Ловит USE без DEF |

Статический анализ (Sonar, PVS-Studio) частично автоматизирует data-flow **до** запуска.

## White-box на уровне комплекса

На **интеграции** white-box смотрит на **взаимодействие модулей**: все ли **интерфейсы** вызваны, все ли **коды ошибки** обработаны. Это ближе к **gray-box** ([111](/encyclopedia/7-project/7-05-testirovanie/111)).

Для **систем реального времени** white-box дополняется **измерением времени** пути — см. [заказные РВ-системы](/encyclopedia/7-project/7-13-ekonomika-proizvodstva-po/5).

## Типичные ошибки

1. **Гонка за 100% coverage** — тесты без assert.
2. **Игнор `else` и `catch`** — «так не бывает».
3. **Не тестировать boolean short-circuit** — `a || expensive()`.
4. **Путать branch с path** — комбinatorный взрыв.
