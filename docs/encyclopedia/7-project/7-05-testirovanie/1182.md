## Что такое E2E-автоматизация

**E2E (end-to-end)** — тест проходит **весь путь пользователя** в реальном браузере: открыть сайт → войти → оформить заказ → увидеть подтверждение.

Единый формат практики в статье:
- когда выбирать Playwright для команды;
- минимальный рабочий сценарий и CI-профиль;
- антифлейк-чеклист для стабильного регресса.

Практический ориентир: E2E-тесты закрывают критичные сквозные риски, а основную массу логики выгоднее закрывать на [unit](./120.md) и [integration/API](./121.md). Тогда регресс остаётся быстрым и стабильным.

Мини-маршрут внедрения в команде:
1. Выбрать 3-10 P0-сценариев.
2. Зафиксировать данные и критерии в [документации](./119.md).
3. Автоматизировать сценарии в Playwright и включить их в CI.
4. Еженедельно анализировать flaky-падения и чистить технический долг.

| Уровень | Что проверяет | Инструмент (примеры) |
|---------|---------------|----------------------|
| Unit | Одна функция/класс | pytest, JUnit |
| API | HTTP без UI | Postman, REST-клиент в коде |
| E2E | UI + браузер + сеть | **Playwright**, Selenium |

E2E **медленнее** и **хрупче** (ломается при смене вёрстки), зато ловит ошибки интеграции, которые unit не видит. Обычно их меньше, чем unit, но на **критичных сценариях** (оплата, регистрация) они обязательны.

Ручная проверка того же сценария — [Ручное тестирование веба](./128.md). Общая теория автоматизации — [Автоматизация тестирования](./115.md).

## Selenium или Playwright?

<div class="callout callout--info">
  <div class="callout-title">Сравнение</div>

  <div class="callout-body">
  | | Selenium | Playwright |
  |---|----------|------------|
  | Возраст экосистемы | Очень зрелая, много legacy | Моложе, активно растёт |
  | Ожидания элементов | Часто пишут вручную | Auto-wait по умолчанию |
  | Браузеры | Через отдельные драйверы | Chromium, Firefox, WebKit из коробки |
  | Отладка | Логи + скрины сами | Trace Viewer, video, screenshot on fail |
  | Когда брать | Enterprise, старый стек, Appium-опыт | Новый фронт, React/Vue, CI на GitHub Actions |
  
  Обе технологии валидны. Для обучения начните с Playwright на зелёном проекте; Selenium — если команда уже на нём сидит.
</div>

### Миграция с Selenium на Playwright

Если команда уже сидит на Selenium, переход обычно делают поэтапно:
1. Оставляют стабильный legacy-регресс на Selenium.
2. Новые E2E-сценарии пишут сразу на Playwright.
3. Постепенно переносят самые flaky и дорогие в поддержке сценарии.
4. После стабилизации CI сокращают Selenium-набор до необходимого минимума.

Такой путь снижает риск "сломать всё сразу" и позволяет измерить выгоду на практике — время прогона, стабильность, скорость разбора падений.

## Установка

Нужны **Node.js 18+** (или Python/Java — Playwright мультиязычен; ниже — **TypeScript** как самый частый выбор в E2E).

```bash
npm init playwright@latest
```

Мастер спросит — папку тестов (`tests`), базовый URL, установку браузеров. После установки:

```bash
npx playwright test
npx playwright test --ui
```

`--ui` — **UI Mode**: пошаговый прогон, удобно QA без глубокого опыта в коде.

Структура проекта (типично):

```text
project/
  playwright.config.ts   # настройки
  tests/
    example.spec.ts      # тесты
  package.json
```

## Первый тест — построчно

```typescript

import { test, expect } from '@playwright/test';

test('главная страница открывается', async ({ page }) => {
  await page.goto('https://example.com');
  await expect(page).toHaveTitle(/Example Domain/);
});
```

| Строка | Что происходит |
|--------|----------------|
| `test(...)` | Один сценарий с именем для отчёта |
| `async ({ page })` | Playwright даёт вкладку браузера `page` |
| `goto` | Переход по URL, ожидание загрузки |
| `expect(...).toHaveTitle` | Проверка заголовка; **ретраи** до таймаута — без `sleep` |

Структура E2E как в [автоматизации](./115.md): **подготовка → действие → проверка (assert)**.

---

### Несколько тестов в файле

```typescript
test.describe('Каталог', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/catalog');
  });

  test('список товаров виден', async ({ page }) => {
    await expect(page.getByRole('heading', { name: 'Каталог' })).toBeVisible();
  });
});
```

`beforeEach` — общая подготовка перед каждым тестом в группе.

## Локаторы — как не ловить flaky-тесты

**Flaky** — тест упал на CI, локально прошёл. Частая причина — элемент ещё не появился или изменился селектор.

Приоритет локаторов (от устойчивых к хрупким):

| Приоритет | Локатор | Пример |
|-----------|---------|--------|
| 1 | `getByRole` | `page.getByRole('button', { name: 'Войти' })` |
| 2 | `getByLabel` | `page.getByLabel('Email')` |
| 3 | `getByTestId` | `page.getByTestId('checkout-submit')` |
| 4 | `getByText` | осторожно при смене языка |
| 5 | CSS/XPath | только если иначе никак |

Попросите разработчиков добавить `data-testid` на критичные элементы — договорённость команды.

```typescript
await page.getByTestId('login-email').fill('qa@test.local');
await page.getByTestId('login-password').fill('Secret123!');
await page.getByRole('button', { name: 'Войти' }).click();
await expect(page.getByText('Личный кабинет')).toBeVisible();
```

---

### Продвинутые локаторы — CSS и XPath

Когда `getByRole` / `getByTestId` недоступны, Playwright поддерживает **CSS** и **XPath** через `page.locator(...)`. Используйте их осознанно: они чаще ломаются при рефакторинге вёрстки.

| Подход | Пример | Когда уместен |
|--------|--------|---------------|
| CSS по атрибуту | `page.locator('[data-testid="cart-badge"]')` | Стабильный `data-testid` от команды фронта |
| CSS по структуре | `page.locator('form.checkout >> button[type=submit]')` | Вложенные блоки без роли ARIA |
| XPath по тексту | `page.locator('xpath=//button[contains(., "Оплатить")]')` | Legacy-страницы без testid |
| Фильтр Playwright | `page.locator('.row').filter({ hasText: 'Итого' })` | Уточнение среди похожих элементов |
| Цепочка | `page.locator('#sidebar').getByRole('link', { name: 'Заказы' })` | Сначала контейнер, потом устойчивый локатор |

```typescript
const row = page.locator('tr.order-row').filter({ hasText: 'Оплачен' });
await expect(row.getByRole('cell', { name: 'Статус' })).toHaveText('Оплачен');
```

<div class="callout callout--warning">
  <div class="callout-title">Антипаттерн</div>

  <div class="callout-body">
  XPath вида `/html/body/div[3]/div[1]/button` привязан к дереву DOM и почти гарантированно даст flaky-тесты. Лучше договориться с разработчиками о `data-testid` на P0-элементах.
</div>
  </div>

## Auto-wait и assertions

Playwright перед кликом ждёт, пока элемент **visible, stable, enabled**. Ошибка Selenium "element not interactable" встречается реже.

```typescript
await expect(page.locator('.toast-success')).toHaveText('Заказ оформлен');
await expect(page).toHaveURL(/\/orders\/\d+/);
```

---

### Проверка API в том же тесте

```typescript
const responsePromise = page.waitForResponse('**/api/orders');
await page.getByRole('button', { name: 'Оформить' }).click();
const response = await responsePromise;
expect(response.status()).toBe(201);
```

Так вы связываете UI и [проверку API](./2.md) в одном сценарии.

## SPA и React — что учитывать в E2E

**SPA (Single Page Application)** — маршрут меняется без полной перезагрузки страницы. React, Vue и Angular рендерят UI через виртуальный DOM; элементы появляются асинхронно после запросов к API.

| Особенность SPA | Риск для теста | Приём в Playwright |
|-----------------|----------------|-------------------|
| Клиентский роутинг | `goto` прошёл, контент ещё пустой | `await expect(locator).toBeVisible()` вместо фиксированной паузы |
| Скелетоны и спиннеры | Клик по "невидимой" кнопке | Ждать исчезновения loader или появления целевого блока |
| Модальные окна и порталы | Элемент вне основного DOM | Локатор внутри `page.getByRole('dialog')` |
| Состояние в памяти | Тесты зависят от порядка | Изолировать данные, уникальные email, API seed |
| Hydration (SSR) | Расхождение серверного и клиентского HTML | Первое действие — дождаться стабильного UI |

```typescript
await page.goto('/orders');
await expect(page.getByRole('heading', { name: 'Мои заказы' })).toBeVisible();
await page.getByRole('button', { name: 'Создать' }).click();
await expect(page.getByTestId('order-form')).toBeVisible();
```

Для React-команд договоритесь о **`data-testid`** на формах оплаты, корзине и авторизации. Сетевые заглушки (`page.route`) помогают стабилизировать сценарии без реального платёжного шлюза — тот же приём описан в [кейсе автоматизации](./115.md#этап-4-реализация-ключевого-сценария-оплата).

Подробнее про уровень E2E и паттерны UI — [End-to-End и системное тестирование](./114.md).

## Авторизация без повторного логина

Долгий логин в каждом тесте замедляет прогон. Паттерн **storageState**:

```typescript
// tests/auth.setup.ts

import { test as setup } from '@playwright/test';

setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByTestId('login-email').fill('qa@test.local');
  await page.getByTestId('login-password').fill('Secret123!');
  await page.getByRole('button', { name: 'Войти' }).click();
  await page.context().storageState({ path: 'playwright/.auth/user.json' });
});
```

В `playwright.config.ts` укажите `storageState: 'playwright/.auth/user.json'` для проектов, которым нужна сессия. Один раз залогинились — остальные тесты стартуют уже авторизованными.

## Архитектура UI-автотестов и паттерны проектирования

Когда сценариев больше пяти, плоские spec-файлы превращаются в "спагетти" из селекторов. Три рабочих уровня абстракции — **Page Object**, **Page Component** и **фабрика страниц** (Page Factory). Общая теория POM и Screenplay — в [End-to-End и системное тестирование](./114.md#архитектурные-паттерны), структура репозитория в кейсе — [Автоматизация тестирования](./115.md#этап-3-архитектура-тестовой-базы).

### Page Object Model

Класс страницы инкапсулирует локаторы и действия. Тест описывает **бизнес-шаги**, страница — **как кликнуть**.

### Page Component

Повторяющиеся блоки UI (шапка, сайдбар, модалка, таблица) выносят в **компонент**, который принимают несколько страниц.

### Page Factory — фабрика страниц

**Page Factory** — слой, который **создаёт** готовые Page Object’ы с уже переданным `page` (или `browser context`). Тесты остаются короткими, зависимости собираются в одном месте.

### Масштабируемая структура проекта

Типовая раскладка для команды SDET (TypeScript или Python):

```text
ui-automation/
├── config/                 # окружения, таймауты (Pydantic / .env)
├── pages/                  # Page Object по экранам
├── components/             # переиспользуемые блоки UI
├── tests/                  # spec — только сценарии
├── fixtures/               # данные, auth state, API helpers
├── reports/                # allure-results (в .gitignore)
├── playwright.config.ts    # или conftest.py для Python
├── .github/workflows/      # CI
└── README.md               # как запустить, ссылка на отчёт
```

| Слой | Ответственность |
|------|----------------|
| `tests/` | Сценарий "логин → заказ → проверка" |
| `pages/`, `components/` | Локаторы и действия |
| `fixtures/` | Пользователи, тестовые заказы, моки API |
| `config/` | URL стенда, секреты из переменных окружения |

### Минимальный CI-профиль команды

Для большинства проектов удобно разделить прогоны на три слоя:
- PR: только smoke-набор (быстрый фидбек до merge);
- nightly: полный регресс во всех целевых браузерах;
- pre-release: smoke + критичный регресс + обязательная публикация артефактов.

Пример практичного профиля:
- `trace: "on-first-retry"` для экономии места;
- `video: "retain-on-failure"` для разборов падений;
- `retries: 1` в CI как временная страховка, но с обязательным разбором причин флейков.

## Видео, скриншоты и Trace Viewer

В `playwright.config.ts` артефакты настраиваются в блоке `use`:

| Опция | Значения | Зачем |
|-------|----------|-------|
| `screenshot` | `only-on-failure`, `on`, `off` | Снимок экрана в момент падения |
| `video` | `retain-on-failure`, `on`, `off` | Видео прогона для разбора таймингов |
| `trace` | `on-first-retry`, `on`, `retain-on-failure` | Пошаговая запись для Trace Viewer |

```typescript
use: {
  screenshot: 'only-on-failure',
  video: 'retain-on-failure',
  trace: 'on-first-retry',
},
```

После падения в CI скачайте артефакты workflow и откройте trace:

```bash
npx playwright show-trace test-results/.../trace.zip
```

**Trace Viewer** показывает timeline действий, DOM на каждом шаге, сетевые запросы и консоль браузера. Это основной инструмент разбора "упало только на CI".

Дополнительно:

```bash
npx playwright test --debug
npx playwright codegen https://test.shop.example
```

`codegen` записывает действия в код — стартовая заготовка, затем рефакторинг на устойчивые локаторы.

## Pytest и экосистема (Python + Playwright)

Многие команды QA пишут E2E на **Python**: тот же Playwright, но раннер **pytest**. Базовый unit-практикум — [Подготовка среды и создание первого теста](./1011.md); каталог плагинов — [Инструменты для ручного и автоматизированного тестирования](./118.md).

### Установка

```bash
pip install pytest pytest-playwright allure-pytest pytest-xdist
playwright install
```

### Фикстуры и "фабрика" страниц

`conftest.py` — центр pytest — браузер, контекст, авторизация, Page Object’ы.

```python

import pytest

from playwright.sync_api import Page
from pages.login_page import LoginPage

@pytest.fixture
def login_page(page: Page) -> LoginPage:
    return LoginPage(page)

@pytest.fixture(scope="session")
def base_url() -> str:
    return "https://test.shop.example"
```

В тесте: `def test_login(login_page): login_page.login(...)`.

### Параметризация и маркеры

```python

import pytest

@pytest.mark.smoke
@pytest.mark.parametrize("browser_name", ["chromium", "firefox"])
def test_home_title(page, browser_name):
    ...
```

| Маркер / механизм | Назначение |
|-------------------|------------|
| `@pytest.mark.smoke` | Быстрый набор на PR |
| `@pytest.mark.regression` | Полный регресс nightly |
| `@pytest.mark.parametrize` | Один тест — несколько входных данных |
| `pytest -m smoke` | Запуск только помеченных тестов |

Зарегистрируйте маркеры в `pyproject.toml` или `pytest.ini`, чтобы CI и IDE не ругались на неизвестные имена.

### Плагины и параллельный запуск

| Пакет | Задача |
|-------|--------|
| `pytest-playwright` | Фикстуры `page`, `browser`, конфиг из CLI |
| `pytest-xdist` | Параллель на нескольких ядрах: `pytest -n auto` |
| `allure-pytest` | Шаги и вложения в Allure |
| `pytest-rerunfailures` | Временный ретрай flaky (с обязательным разбором) |

Параллель ускоряет регресс, но требует **изолированных** тестовых данных — два воркера не должны бронировать один и тот же email.

### Моки и оптимизация

- **Сеть**: `page.route("**/api/orders", lambda route: route.fulfill(...))` — стабильный ответ без реального бэкенда.
- **API setup**: создать пользователя через REST до UI, затем только проверить экран — меньше шагов в браузере.
- **storageState**: один раз залогиниться в setup-фикстуре, переиспользовать cookie в тестах.
- **Моки Python**: `unittest.mock` / `pytest-mock` для unit-слоя; в E2E чаще мокируют HTTP, а не DOM.

Подробнее про моки в unit — [Подготовка среды и создание первого теста](./1011.md#работа-с-моками-и-внешними-зависимостями), про дублёры — [Объекты и уровни тестирования](./117.md).

## Отчётность и инфраструктура

### Allure Report и Allure TestOps

**Allure Report** собирает HTML-отчёт из результатов прогона — шаги, вложения (скрин, trace), история падений.

```bash
pytest --alluredir=allure-results
allure serve allure-results
```

В Playwright (TypeScript) подключают репортер `@playwright/test` + `allure-playwright` или выгружают артефакты pytest в CI.

**Allure TestOps** — корпоративная платформа поверх тех же результатов — дашборды, связь с Jira, анализ стабильности, ручные + автотесты в одном месте. Для учебного проекта достаточно локального `allure serve`; в компании TestOps подключают через upload API после CI.

Слой отчётности в архитектуре автоматизации — [Автоматизация тестирования](./115.md).

### CI/CD и публикация отчётов

Типовый pipeline (GitHub Actions, GitLab CI, Jenkins):

1. Установка зависимостей и браузеров (`playwright install --with-deps`).
2. Прогон smoke на PR, полный регресс на `main` / nightly.
3. Загрузка `playwright-report/`, `allure-results/`, trace и video при падении.
4. Публикация Allure на GitHub Pages или внутренний nginx.

Общий вводный материал — [DevOps и CI/CD](/encyclopedia/8-infra-security/8-04-devops-ci-cd/intro). Пример workflow с Playwright — в разделе ниже.

### Конфигурация через Pydantic и переменные окружения

Секреты и URL стендов **не хранят** в репозитории. Модуль настроек читает `.env` и переменные CI:

```python
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    base_url: str = "http://localhost:3000"
    qa_user_email: str
    qa_user_password: str
    headless: bool = True

settings = Settings()
```

В `conftest.py`: `page.goto(settings.base_url)`. В GitHub Actions — secrets `QA_USER_PASSWORD`, в локальной разработке — `.env` в `.gitignore`. Подробнее про Pydantic — [Pydantic — валидация входящих данных](/encyclopedia/5-languages/5-02-python/41).

```yaml
- uses: actions/checkout@v4
- uses: actions/setup-node@v4
  with:
    node-version: 20
- run: npm ci
- run: npx playwright install --with-deps
- run: npx playwright test

  if: failure()
  with:
    name: playwright-report
    path: playwright-report/
```

Отчёт HTML — артефакт для команды QA. При падении скачайте trace и report из CI.

## Типичные ошибки новичка

| Ошибка | Решение |
|--------|---------|
| `sleep(5000)` везде | `expect` с auto-wait |
| XPath на полный DOM | `getByRole` / `getByTestId` |
| Один огромный тест на 200 строк | `test.describe` + Page Object |
| Тесты зависят от порядка | Изолировать данные, уникальный email |
| Гоняют только локально headless=false | Периодически прогон как в CI |

---

### Антифлейк-чеклист для команды

- используйте только устойчивые локаторы: role/label/testid;
- не храните хрупкое состояние между тестами, данные должны быть изолированы;
- избегайте `sleep`, опирайтесь на `expect` и события;
- фиксируйте окружение — версия браузера, node, зависимости;
- любое нестабильное падение разбирайте через trace в тот же спринт;
- держите короткий "карантинный список" flaky-тестов и срок их исправления.

## Практика и карьера

Автотесты на Playwright — сильный аргумент в резюме junior/middle QA (автоматизатор, SDET). Ниже — что оформить в портфолио и как готовиться к собеседованию.

### Git и GitHub для тестового репозитория

| Шаг | Действие |
|-----|----------|
| Репозиторий | Публичный `qa-playwright-demo` с README на русском или английском |
| Ветки | `feature/QA-1-login-e2e` → Pull Request, как в продуктовой команде |
| CI | Badge в README: статус workflow GitHub Actions |
| Секреты | Пароли только в Secrets, пример — `.env.example` без значений |

Минимум команд и review-процесс — [Дополнительные модули для тестировщика](./1274.md#git--минимум-для-тестировщика) и [раздел Git](/encyclopedia/4-code-dev/4-13-osnovy-raboty-s-git/intro).

### Оформление проекта в портфолио

В README укажите:

- **Стек** — Playwright, pytest или TypeScript, Allure, GitHub Actions.
- **Что проверяете** — 3–5 P0-сценариев (логин, корзина, оплата с моком API).
- **Как запустить**: `git clone`, `pip install -r requirements.txt`, `playwright install`, `pytest`.
- **Отчёт**: скрин Allure или ссылка на опубликованный Pages.
- **Архитектура** — схема папок `pages/`, `tests/`, `conftest.py`.

Ревьюер на собеседовании смотрит на **читаемость тестов** и **устойчивые локаторы**, а не на количество файлов.

### Резюме и собеседование

| Тема на интервью | Что подготовить |
|------------------|-----------------|
| Пирамида тестирования | Где у вас unit, API, E2E; почему E2E мало |
| Локаторы | Почему `getByRole` / `data-testid` лучше XPath |
| Flaky | Пример, как нашли через trace и исправили |
| CI | Как падение блокирует merge, куда смотрят артефакты |
| Page Object | Зачем выносили страницу в класс, пример рефакторинга |
| Pytest | Фикстуры, маркеры smoke/regression, параллель `-n` |

Рассказ о проекте на 2–3 минуты: продукт → ваша роль → стек → один конкретный баг, пойманный автотестом. Карьера и soft skills — [Карьера в IT](/encyclopedia/1-basics/1-26-karera-v-it-i-mify/1), бонус-модули — [Дополнительные модули для тестировщика](./1274.md). Вопросы для самопроверки — [Тестирование программного обеспечения — чек-лист](./999.md).
