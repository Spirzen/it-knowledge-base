## Обзор PostgreSQL

PostgreSQL ведёт происхождение от академического проекта **POSTGRES** (Беркли, 1980‑е), затем Postgres95 и с 1996 года — имя **PostgreSQL** (связь с POSTGRES и переход на SQL). Произносят «постгрес-ку-эль» или просто «постгрес».

Развитием руководит **PostgreSQL Global Development Group**; релиз major-версии выходит примерно раз в год (сейчас актуальна **16**). Среди ключевых механизмов ядра — **MVCC**, **WAL** и **vacuum**; к экосистеме относятся полнотекстовый поиск, типы **JSON/JSONB** и семейства индексов **GiST/GIN**. Подробнее про MVCC, VACUUM и эксплуатацию — [практикум 8.11](/encyclopedia/8-infra-security/8-11-praktikum-postgresql/1).

## Как работает PostgreSQL

Кластер PostgreSQL — это **процессы ОС**, **разделяемая память** и **файлы на диске**. Ниже — краткая напоминалка по слоям; подробнее про путь SQL-запроса и компоненты — в [Принципах работы SQL-движка](./2.md#архитектура-postgresql-компоненты-субд), про WAL при сбое — в [Восстановлении после сбоя](/encyclopedia/3-data-markup/3-05-osnovy-baz-dannyh/8.md).

### Подключения и процессы

- Главный процесс **`postmaster`** слушает порт (обычно **5432**), принимает подключения и **порождает дочерний backend-процесс** на каждую сессию клиента (модель **«одно подключение — один процесс»**).
- **Backend-процесс** разбирает SQL, строит план, читает и пишет страницы через общие буферы, возвращает результат приложению (`psql`, JDBC, драйвер в коде).
- Тяжёлые запросы могут задействовать **parallel workers** — отдельные фоновые процессы, которые помогают одному backend'у (сортировка, сканирование, агрегация).

### Разделяемая память

Все backend'ы и служебные процессы работают с одним блоком **shared memory**:

| Область | Назначение |
| :--- | :--- |
| **Shared buffers** | Кэш страниц таблиц и индексов в ОЗУ |
| **WAL buffers** | Буфер записей журнала до сброса на диск |
| **CLOG buffers** | Статусы транзакций (committed / aborted / in progress) |
| **Temp buffers** | Временные таблицы сессии |
| Прочие буферы | Служебные структуры ядра |

Параметр `shared_buffers` задаёт размер кэша данных; `work_mem` — память **на операцию** внутри одного запроса (сортировка, хеш), а не на всё подключение.

### Фоновые (auxiliary) процессы

Они обслуживают кластер, пока приложения шлют SQL:

| Процесс | Роль |
| :--- | :--- |
| **WAL Writer** | Сбрасывает WAL buffers в файлы `pg_wal/` |
| **Background Writer (BG Writer)** | Дозаписывает «грязные» страницы из shared buffers в файлы данных |
| **Checkpointer** | Периодические **checkpoint** — сокращают объём WAL при recovery |
| **Autovacuum** | Убирает «мёртвые» строки (MVCC), обновляет статистику |
| **Stats Collector** | Собирает метрики для планировщика (`pg_stat_*`) |
| **Sys Logger** | Пишет текстовые логи сервера |
| **Archiver** | Копирует сегменты WAL в архив (бэкап, PITR) |
| **Replication Launcher** | Запускает процессы потоковой репликации |

### Физическое хранение и WAL

- **Data files** — таблицы и индексы в каталоге кластера (`base/`, tablespace).
- **WAL files** — журнал опережающей записи: **любое изменение, которое должно пережить сбой, сначала попадает в WAL**, затем (с задержкой) отражается в файлах данных через буферы и BG Writer / checkpoint.
- **Archive files** — архивированные сегменты WAL для восстановления на момент времени ([Резервное копирование и восстановление PostgreSQL](./106.md)).
- **Log files** — текстовые логи PostgreSQL (отдельно от WAL).

Транзакции и **MVCC** дают параллельное чтение и запись без блокировки каждой строки на чтение; согласованность при падении питания обеспечивает цепочка **WAL → checkpoint → crash recovery** ([глава 8](/encyclopedia/3-data-markup/3-05-osnovy-baz-dannyh/8.md)).

```sql
SHOW server_version;
SHOW data_directory;
SHOW wal_level;
SHOW shared_buffers;

SELECT pid, usename, state, query
FROM pg_stat_activity
WHERE backend_type = 'client backend';
```

## Подключение и запуск

### psql

```bash
psql -h localhost -p 5432 -U app_user -d app_db
```

В интерактивном режиме **приглашение** подсказывает контекст:

| Приглашение | Значение |
| :--- | :--- |
| `postgres=#` | БД `postgres`, роль с правами **суперпользователя** (`#`) |
| `appdb=>` | БД `appdb`, обычная роль (`>`) |

Команды, начинающиеся с `\`, понимает только **psql** (не SQL). Шпаргалка мета-команд — в [Первые шаги с SQL](./101.md#psql-meta-komandy).

### Перечитать конфигурацию без перезапуска

После правок `postgresql.conf` или `pg_hba.conf` (для параметров с `sighup`):

```sql
SELECT pg_reload_conf();
```

Проверка значения — `SHOW parameter_name;`. Параметры уровня `postmaster` (например, `shared_buffers`) требуют **restart** службы.

Альтернатива правке файла вручную — `ALTER SYSTEM SET work_mem = '128MB';` (значения попадают в `postgresql.auto.conf`).

### Строка подключения (URI)

```text
postgresql://app_user:secret@localhost:5432/app_db
postgresql://app_user@localhost/app_db?sslmode=require
```

### Базовая настройка

```sql
CREATE ROLE app_user LOGIN PASSWORD 'secret';
CREATE DATABASE app_db OWNER app_user;
GRANT CONNECT ON DATABASE app_db TO app_user;
```

## Типы данных и синтаксис

Ключевые типы PostgreSQL:
- Числовые: `smallint`, `integer`, `bigint`, `numeric`, `real`, `double precision`
- Строки: `text`, `varchar`, `char`
- Дата/время: `date`, `timestamp`, `timestamptz`, `interval`
- Булев: `boolean`
- Бинарные: `bytea`
- Расширенные: `json`, `jsonb`, `uuid`, `array`, `hstore`, `tsvector`, `tsquery`

Теория типа `json` / `jsonb` и сравнение с текстовым [JSON](/encyclopedia/3-data-markup/3-04-konfiguratsii-i-dannye/3) — [JSONB](/encyclopedia/3-data-markup/3-04-konfiguratsii-i-dannye/217). Пошаговая практика (операторы, функции, индексы, `EXPLAIN`) — [Практикум PostgreSQL по JSONB](./66.md).

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    email TEXT NOT NULL UNIQUE,
    profile JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## Доступные и недоступные команды

| Категория | Команда / конструкция | Статус в PostgreSQL | Комментарий |
|---|---|---|---|
| DML | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | Доступно | Полноценная поддержка |
| DDL | `CREATE/ALTER/DROP` | Доступно | Широкий набор возможностей |
| Транзакции | `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT` | Доступно | Полная поддержка ACID |
| Права | `CREATE ROLE`, `GRANT`, `REVOKE` | Доступно | Ролевая модель доступа |
| Серверные объекты | `FUNCTION`, `PROCEDURE`, `TRIGGER` | Доступно | PL/pgSQL и расширения |
| Репликация/WAL | streaming replication, logical replication | Доступно | Продакшен-масштабирование |
| Материализованные view | `CREATE MATERIALIZED VIEW` | Доступно | Поддерживается |
| Подсказки оптимизатору как `/*+ hint */` | Частично/ограничено | Нет стандартных Oracle-style hints |
| `MERGE` | Доступно (современные версии) | Проверять версию кластера |
| Горизонтальный шардинг "из коробки" | Частично | Реализуется через архитектуру/расширения |

## Практика SQL в PostgreSQL

На учебной схеме интернет-магазина (JOIN, `GROUP BY`, выручка, склад, DML) с построчным разбором — [SQL — реальные кейсы](/lab/Примеры/1152). Тот же смысл в PostgreSQL с префиксом `shop_data.` — [практикум shop_data](./111.md).

### CRUD

```sql
CREATE TABLE tasks (
  id BIGSERIAL PRIMARY KEY,
  title TEXT NOT NULL,
  done BOOLEAN NOT NULL DEFAULT FALSE
);

INSERT INTO tasks(title) VALUES ('Пройти PostgreSQL');
SELECT id, title, done FROM tasks ORDER BY id;
UPDATE tasks SET done = TRUE WHERE id = 1;
DELETE FROM tasks WHERE id = 1;
```

### UPSERT

```sql
INSERT INTO tasks(id, title, done)
VALUES (1, 'Обновлённая задача', FALSE)
ON CONFLICT(id) DO UPDATE SET
  title = EXCLUDED.title,
  done = EXCLUDED.done;
```

### Транзакция

```sql
BEGIN;
INSERT INTO tasks(title) VALUES ('A');
INSERT INTO tasks(title) VALUES ('B');
COMMIT;
```

### Возврат данных сразу после изменения

```sql
INSERT INTO tasks(title) VALUES ('C') RETURNING id, title;
UPDATE tasks SET done = TRUE WHERE id = 2 RETURNING id, done;
DELETE FROM tasks WHERE id = 3 RETURNING id;
```

```php

}
```

## Минимальный шаблон безопасной работы

- Используйте параметризованные запросы (`$1`, `$2`, именованные параметры в ORM).
- Включайте TLS для внешних соединений.
- Ограничивайте права ролей по принципу minimum privilege.
- Используйте миграции с откатом.
- Мониторьте медленные запросы и планы выполнения.

```sql
SET statement_timeout = '5s';
SET lock_timeout = '3s';
SHOW transaction_isolation;
```

## Когда PostgreSQL подходит и когда выбрать другой путь

PostgreSQL подходит:
- многопользовательские серверные системы;
- аналитические и транзакционные сценарии в одном кластере;
- сложные типы данных и поиск;
- строгие требования к целостности и правам доступа.

Другой путь выбирают:
- для сверхпростого локального файла в приложении удобнее SQLite;
- для экстремального горизонтального масштаба нужен отдельный архитектурный слой с шардингом;
- для узкоспециализированного OLAP-хранилища используют колоночные СУБД.
