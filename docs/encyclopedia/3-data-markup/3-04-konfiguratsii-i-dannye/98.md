## FAQ — Часто задаваемые вопросы

Типичные ошибки при работе с конфигами и форматами данных. Здесь — **что делать и где копать в главах**; определения для зачёта — в [чек-листе](./99).

<div class="faq-list">

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `kubectl apply` падает с "yaml: line 12: did not find expected key".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Почти всегда <strong>сломан отступ</strong> или смешаны пробелы с табами. YAML чувствителен к иерархии; выровняйте блоки пробелами (2 или 4), проверьте через `yamllint`. Подробнее здесь — [YAML](./4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> В JSON после последнего поля стоит запятая — парсер в браузере OK, на сервере 500.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Стандарт JSON <strong>запрещает trailing comma</strong>; часть парсеров терпимее. Уберите лишнюю запятую; в IDE включите JSON Schema. Подробнее здесь — [JSON](./3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Пароль от БД лежит в `appsettings.json` в Git — что делать срочно?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Считайте секрет <strong>скомпрометированным</strong>: смените пароль, уберите из истории Git (BFG/filter-repo), храните в vault / env / secrets manager. Подробнее здесь — [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `enabled: on` в YAML включило флаг, хотя хотел строку "on".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> YAML 1.1 трактует `on`/`off`/`yes`/`no` как <strong>булевы значения</strong>. Заключите в кавычки: `enabled: "on"`. Подробнее здесь — [YAML](./4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> XML "валидный", но парсер ругается на `<` внутри текста.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Символы `<`, `>`, `&` в тексте нужно <strong>экранировать</strong> (`&lt;` и т.д.) или обернуть в CDATA. Подробнее здесь — [XML](./2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Два тега `<Order>` и `<order>` — "дубликат" или разные элементы?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> В XML имена <strong>чувствительны к регистру</strong> — это разные элементы. Договоритесь о стиле (PascalCase/camelCase) в схеме. Подробнее здесь — [XML](./2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> XPath не находит элемент, хотя он виден в Notepad++.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Проверьте <strong>namespace</strong> — без префикса и `xmlns` выборка пустая. Используйте `local-name()` или зарегистрируйте префикс в XPath 2.0. Подробнее здесь — [XPath](./213).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Конфиг в репозитории для dev, на prod другие значения — как не путать?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Разделите <strong>шаблон и секреты</strong>: `appsettings.json` + `appsettings.Production.json` + переменные окружения; секреты — вне Git. Подробнее здесь — [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> JSON с комментариями `//` — VS Code подсвечивает, CI падает.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> JSON <strong>не поддерживает комментарии</strong>; VS Code иногда терпит JSONC. Для человекочитаемых конфигов — YAML; комментарии в JSON — через поле `"_comment"`. Подробнее здесь — [JSON](./3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Скопировал YAML из Word — "невидимые" ошибки.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Word подставляет <strong>"умные" кавычки и неразрывные пробелы</strong>. Редактируйте конфиги в plain-text редакторе, включите отображение whitespace. Подробнее здесь — [YAML](./4), [Текстовые форматы](./111).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> README.md вместо `config.yaml` — "удобнее править".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Markdown — для <strong>людей и документации</strong>, не для машинного парсинга настроек. Программа ожидает строгую структуру JSON/YAML. Подробнее здесь — [Markdown](./5), [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> XSLT "ничего не вывел" — шаблон match есть.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Проверьте <strong>namespace в match</strong>, default template (копирует детей), порядок шаблонов и `<xsl:output`. Тестируйте на одном узле через XPath. Подробнее здесь — [XSLT](./214).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `.env` файл попал в Docker-образ на Docker Hub.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Добавьте `.env` в <strong>.dockerignore</strong>, передавайте секреты через runtime env или orchestrator secrets. Образ считайте публичным. Подробнее здесь — [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Ansible playbook на Windows с `\` в путях ломает YAML.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Обратный слэш — escape в YAML; пути Windows лучше в <strong>кавычках</strong> или с прямыми `/`. Подробнее здесь — [YAML](./4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> XML огромный — DOM съел всю память.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> DOM загружает <strong>всё дерево</strong>. Для больших файлов — SAX/StAX потоковый парсинг или XPath на streaming API. Подробнее здесь — [XML DOM](./215).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> JSON `{"id": 001}` — id стал 1.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> В JSON числа без ведущих нулей; `001` — <strong>невалидно</strong> как число. ID с ведущими нулями храните строкой `"001"`. Подробнее здесь — [JSON](./3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Два разработчика мержат один YAML — silent merge conflict.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Git может оставить оба блока без маркеров конфликта в <strong>соседних ключах</strong>. Ревью diff внимательно; для k8s — `kubectl diff`. Подробнее здесь — [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> XSD валидация OK, но интеграция с партнёром падает.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Партнёр может использовать <strong>другую версию схемы</strong> или optional поля по-другому. Сверьте sample messages, namespace, кодировку пролога UTF-8. Подробнее здесь — [XML](./2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Protobuf "сломался" после добавления поля — старые клиенты падают.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Менять <strong>номер или тип</strong> существующего поля нельзя. Новые поля — новые tag; reserved для удалённых. Подробнее здесь — [MessagePack, BSON, Protobuf](./216).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Эмодзи в логе YAML превратились в "квадратики" или знаки вопроса.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Кодировка файла или терминала <strong>не UTF-8</strong>. Сохраните конфиг в UTF-8 без BOM, проверьте locale контейнера. Подробнее здесь — [Текстовые форматы](./111), [Эмодзи в тексте](./112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `docker-compose.yml` version: '3' — предупреждение "obsolete".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Новые Compose V2 <strong>игнорируют поле version</strong> — это не ошибка данных, а смена спецификации. Обновите документацию под актуальный compose spec. Подробнее здесь — [YAML](./4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Конфиг разросся до 2000 строк — никто не знает, что можно удалить.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Разбейте на модули, включите <strong>defaults в коде</strong>, документируйте обязательные ключи, grep по репозиторию на использование. Подробнее здесь — [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> JSON из JavaScript `undefined` сериализовался странно.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> `JSON.stringify` <strong>пропускает ключи со значением undefined</strong>; массивы с `undefined` → `null`. Явно задайте `null` или удалите ключ в контракте API. Подробнее здесь — [JSON](./3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Markdown таблица в GitHub OK, в Docusaurus "плывёт".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> MDX требует <strong>пустую строку</strong> вокруг таблицы и экранирование `{`. Проверьте правила MDX в энциклопедии. Подробнее здесь — [Markdown](./5).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Банк требует XML, команда шлёт JSON — "и так работало".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Контракт интеграции задаёт <strong>формат и XSD</strong> — JSON без согласования отклонят. Для гос. и финтеха XML часто обязателен. Подробнее здесь — [XML](./2), [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> YAML anchor `*defaults` не подставился — ключи пустые.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Alias ссылается на <strong>узел, объявленный выше</strong> через `&`; merge key `<<:` — особый синтаксис. Проверьте отступ alias и поддержку парсера. Подробнее здесь — [YAML](./4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Локально конфиг читается, в Linux-контейнере — FileNotFound.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Windows регистр пути не учитывает; Linux — <strong>case-sensitive</strong>. Путь `./Config/app.json` vs `./config/app.json`. Подробнее здесь — [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Хочу один формат "на всё" — что выбрать?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Универсального нет: <strong>JSON для API</strong>, YAML для IaC и ручных правок, XML для строгих контрактов, Markdown для docs. Выбор — проектное решение под аудиторию и инструменты. Подробнее здесь — [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Валидатор JSON online говорит OK, а Python `json.load` падает.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Проверьте <strong>BOM в начале файла</strong>, одинарные кавычки, NaN/Infinity (не в стандарте JSON). Откройте hex первых байт. Подробнее здесь — [JSON](./3), [Текстовые форматы](./111).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> JSON vs YAML — в чём разница и что выбрать?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>JSON</strong> — строгий, без комментариев, стандарт API. <strong>YAML</strong> — читаем человеком, отступы, комментарии; Kubernetes, Ansible, CI. Подробнее здесь — [JSON](./3), [YAML](./4), [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое JSON и для чего он используется?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Текстовый формат обмена данными: объекты `{}`, массивы `[]`, строки, числа, bool, null. Основа REST API и конфигов сборки. Подробнее здесь — [JSON](./3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как проверить JSON на ошибки онлайн или в терминале?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> `jq . file.json`, `python -m json.tool`, IDE с подсветкой, jsonlint.com. Частые ошибки — trailing comma, одинарные кавычки. Подробнее здесь — [JSON](./3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое YAML файл и как его читать?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Иерархия через <strong>отступы</strong>, списки с `-`, ключ: значение. Без табов — только пробелы. Подробнее здесь — [YAML](./4).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> XML — для чего используется в 2025 году?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Госуслуги, банки, SOAP, конфиги .NET, документооборот со <strong>XSD-валидацией</strong>. Для новых REST чаще JSON. Подробнее здесь — [XML](./2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое XPath и как выбрать элемент в XML?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Язык путей: `/catalog/book/title`, `//item[@id='1']`. Используют в тестах, XSLT, парсерах. Подробнее здесь — [XPath](./213).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> XSLT — что это и зачем преобразовывать XML?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Шаблоны для <strong>XML → HTML, PDF, другой XML</strong>. Legacy интеграции и отчёты. Подробнее здесь — [XSLT](./214).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Markdown vs HTML — когда что использовать?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>Markdown</strong> — README, wiki, статьи (Docusaurus). HTML — точная вёрстка. Markdown не заменяет JSON/YAML для настроек. Подробнее здесь — [Markdown](./5).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Где хранить пароли и API-ключи в проекте?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Не в Git: <strong>переменные окружения</strong>, Vault, Secrets Manager, `.env` локально + `.gitignore`. Подробнее здесь — [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Kubernetes config yaml — с чего начать изучение?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Сначала YAML-синтаксис, затем минимальный Pod/Deployment. Отступы критичны. Подробнее здесь — [YAML](./4), [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое .env файл?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Текстовый список <strong>KEY=VALUE</strong> для локальной разработки; загружается dotenv-библиотеками. Не коммитить секреты. Подробнее здесь — [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Protobuf vs JSON — когда выбрать бинарный формат?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Protobuf компактнее и быстрее при <strong>высоком RPS</strong> и gRPC; JSON проще отлаживать. Подробнее здесь — [MessagePack, BSON, Protobuf](./216).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое JSON Schema?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Описание структуры JSON для <strong>валидации</strong> API-контрактов (типы, required, enum). Аналог XSD для JSON. Подробнее здесь — [JSON](./3), [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> TOML vs YAML vs JSON для конфигурации?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>TOML</strong> — явные секции, популярен в Rust (Cargo.toml). YAML — k8s/Ansible. JSON — API и автогенерация. Подробнее здесь — [Конфигурационные данные](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как конвертировать JSON в YAML и обратно?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> `yq`, онлайн-конвертеры, IDE-плагины. Проверяйте типы (`"on"` в YAML!). Подробнее здесь — [JSON](./3), [YAML](./4).</p>
</div>

<div class="faq-item">

## Что запомнить

Конфигурационные данные — это не просто текстовые файлы, а полноценный интерфейс между программой и её окружением. Они позволяют отделить поведение от реализации, повысить переносимость, упростить тестирование и обеспечить гибкость развёртывания. Для этого используются структурированные машиночитаемые форматы, каждый из которых решает свою задачу в зависимости от контекста.

**XML** — формат с максимальной строгостью и самодокументируемостью. Он поддерживает пространства имён, схемы (XSD/DTD), трансформации (XSLT) и адресацию (XPath). Применяется в государственных системах, корпоративных интеграциях, документообороте и промышленных решениях, где важна верифицируемость и долгосрочная совместимость.

**JSON** — лаконичный, предсказуемый и универсальный. Лишён комментариев и сложных типов, что делает его идеальным для обмена данными между сервисами, конфигурации сборок и API. Его простота обеспечивает надёжность парсинга даже в ресурсоограниченных средах.

**YAML** — ориентирован на человека. Использует отступы вместо скобок, поддерживает комментарии, алиасы и многострочные строки. Широко применяется в описании инфраструктуры как кода (Kubernetes, Ansible, Docker Compose), CI/CD-конфигурациях и проектах, где конфигурацию часто редактируют вручную.

**Markdown** — язык разметки, предназначенный для создания читаемых текстовых документов с минимальным синтаксисом. Не является форматом данных в узком смысле, но служит основой для технической документации, README-файлов, блогов и систем знаний, таких как Docusaurus.

Независимо от выбранного формата, ключевые принципы остаются неизменными:
- **Структурированность** — данные должны иметь однозначную иерархию.
- **Машиночитаемость** — любой валидный документ должен парситься без участия ИИ.
- **Семантическая ясность** — имена ключей, тегов и атрибутов должны отражать назначение.
- **Версионируемость** — конфигурация — часть системы, и её изменения фиксируются в Git.
- **Безопасность** — чувствительные данные (пароли, токены) никогда не хранятся в открытом виде в файлах.

Выбор формата — это проектировочное решение, а не техническая деталь. Он определяет, насколько легко будет поддерживать, расширять и интегрировать систему в будущем.
