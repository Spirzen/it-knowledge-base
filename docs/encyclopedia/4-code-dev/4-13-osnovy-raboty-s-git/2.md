## FAQ — Часто задаваемые вопросы

Типичные сбои и ситуации при работе с Git — от первого коммита до командного merge. Здесь — **что делать и где копать в главах**; определения для самопроверки — в [чек-листе](./3).

<div class="faq-list">

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Сделал `git init`, но `git push` пишет "no upstream branch" — репозиторий "не работает"?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Локальный репозиторий <strong>не связан с сервером</strong>, пока вы не создали remote и не отправили первый коммит (`git remote add`, `git push -u origin main`). `init` только создаёт `.git` в папке. Подробнее здесь — [первый репозиторий](./1), [как работать с Git](./112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Изменил файлы, но `git status` показывает "nothing to commit" — куда делись правки?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Файл может быть <strong>untracked</strong> (ещё не добавляли), в `.gitignore`, или вы редактируете не ту папку/не тот клон. Проверьте путь, `git status -u`, содержимое `.gitignore`. Подробнее здесь — [как работать с Git](./112), [`.gitignore`](./116).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Закоммитил `.env` с паролем и уже сделал `push` — как исправить, не паникуя?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Считайте секрет <strong>скомпрометированным</strong> — смените пароль/ключ, добавьте файл в `.gitignore`, удалите из истории по инструкции (filter-repo / BFG). Один `git revert` не уберёт секрет из старых коммитов на сервере. Подробнее здесь — [типовые ситуации](./1141#секрет-или-конфиденциальный-файл-в-git), [`.gitignore`](./116).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `git push` отклонён — "non-fast-forward". Я "ничего не ломал".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> На сервере уже есть <strong>коммиты, которых нет локально</strong> — сначала `git fetch`, затем `git pull` или rebase вашей ветки поверх актуальной. Force push без согласования команды опасен. Подробнее здесь — [типовые ситуации](./1141#push-отклонён-non-fast-forward), [ветвление](./113).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Начал merge, увидел `<<<<<<< HEAD` в коде — можно просто удалить файл?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Нет — нужно <strong>вручную выбрать итоговый код</strong>, убрать маркеры конфликта, `git add` и завершить merge. Отменить начатый merge — `git merge --abort`. Подробнее здесь — [ветвление и слияние](./113), [типовые ситуации](./1141).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Работал в ветке `feature`, а коммиты оказались в `main` — как перенести без копипасты?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Создайте ветку с текущего состояния, откатите `main` к `origin/main`, перенесите коммиты через <strong>cherry-pick</strong> или перебазируйте feature-ветку. Подробнее здесь — [типовые ситуации](./1141#закоммитил-в-main-нужна-отдельная-ветка), [ветвление](./113).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Коллега просит `git pull`, а у меня незакоммиченные правки — Git отказывается.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Закоммитьте, используйте <strong>`git stash`</strong> с сообщением или временную ветку. Stash — не замена коммиту надолго, но спасает при срочном pull. Подробнее здесь — [типовые ситуации](./1141#временно-спрятать-правки-stash), [как работать с Git](./112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> После `git pull` проект не собирается — "оно работало вчера".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Pull мог принести <strong>новые зависимости, миграции, конфликты</strong>, которые вы уже разрешили с ошибкой. Прочитайте сообщение merge-коммита, changelog коллеги, пересоберите окружение. Подробнее здесь — [рекомендации в команде](./114), [типовые ситуации](./1141#pull-из-неправильной-ветки).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Случайно выполнил `git reset --hard` — коммиты "исчезли".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Смотрите <strong>`git reflog`</strong> — локальная история ссылок хранит старые HEAD. Найдите нужный hash и `git reset --hard` к нему, пока reflog не истёк. На сервере коммиты могут ещё жить, если вы успели push. Подробнее здесь — [типовые ситуации](./1141#после-git-reset---hard), [опасные скрипты](/encyclopedia/8-infra-security/8-03-zabota-o-kode-i-dannyh/101).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Удалил ветку `git branch -D feature` — можно вернуть?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Если коммиты были запушены — <strong>восстановите ветку по hash</strong> с remote или reflog. Если только локально и reflog уже перезаписан — шанс меньше. Не удаляйте ветку, пока PR не merged. Подробнее здесь — [типовые ситуации](./1141#удалена-локальная-ветка), [ветвление](./113).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `git clone` качает гигабайты — репозиторий "сломан"?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> В истории могли оказаться <strong>большие бинарники</strong> до очистки. Используйте shallow clone (`--depth 1`) для CI, проверьте `.gitignore` на будущее, для монорепо — sparse checkout. Подробнее здесь — [`.gitignore`](./116), [углубление — packfile](/encyclopedia/8-infra-security/8-03-zabota-o-kode-i-dannyh/112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> На Windows файл `Config.cs` конфликтует, на macOS коллеги — `config.cs` — "один и тот же" файл?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> На Windows файловая система часто <strong>case-insensitive</strong> — Git на Linux/macOS видит два разных пути. Договоритесь об именовании и включите `core.ignorecase` осознанно. Подробнее здесь — [рекомендации в команде](./114), [типовые ситуации](./1141).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Сделал fork на GitHub — как подтянуть изменения из оригинального репозитория?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Добавьте remote <strong>`upstream`</strong>, `git fetch upstream`, merge или rebase в свою main, затем push в свой fork. PR отправляете из fork в upstream по правилам проекта. Подробнее здесь — [ветвление и слияние](./113#fork-i-upstream), [типовые ситуации](./1141).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Reviewer просит "разбить PR на два коммита" — уже всё в одном коммите.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Локально — <strong>interactive rebase</strong> или `git reset --soft` + несколько `git add -p` / отдельных commit. Не переписывайте историю shared-ветки без согласования. Подробнее здесь — [типовые ситуации](./1141#разделить-изменения-на-несколько-коммитов), [как работать с Git](./112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `git commit --amend` после push — коллеги ругаются. Почему?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Amend <strong>меняет hash</strong> последнего коммита — для уже опубликованной ветки нужен force push, это ломает чужие клоны. После push правьте новым коммитом или revert. Подробнее здесь — [типовые ситуации](./1141#дополнить-или-исправить-последний-коммит), [рекомендации](./114).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Хочу отменить merge, который уже в `main` на сервере.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Безопасный путь — <strong>`git revert -m 1`</strong> merge-коммита (новый коммит отмены). `reset --hard` + force на shared main недопустим без крайней необходимости. Подробнее здесь — [типовые ситуации](./1141#отменить-слияние-merge), [опасные скрипты](/encyclopedia/8-infra-security/8-03-zabota-o-kode-i-dannyh/101).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Rebase feature на main — конфликт на каждом коммите, бросаю на полпути.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Можно <strong>прервать</strong> `git rebase --abort`, squash коммитов перед rebase или merge main один раз вместо длинной цепочки. Для новичка merge часто проще rebase. Подробнее здесь — [типовые ситуации](./1141#конфликт-при-rebase), [ветвление](./113#merge-i-rebase).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> CI падает на `main`, локально тесты зелёные — Git "ни при чём"?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> CI собирает <strong>конкретный commit</strong> — проверьте, что вы на том же hash, те же env-переменные и версии Node/JDK. Часто виноваты незакоммиченные файлы локально или `.env` в `.gitignore`. Подробнее здесь — [рекомендации в команде](./114), [`.gitignore`](./116).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Сообщения коммитов "fix", "fix2", "aaa" — reviewer просит переписать историю.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> До merge в общую ветку — rebase -i и осмысленные сообщения по [рекомендациям](./114). После merge историю не переписывают ради косметики. Подробнее здесь — [рекомендации в команде](./114), [справочник](./115).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `git pull` подтянул чужую ветку — файлы не те, паника.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Проверьте текущую ветку `git branch --show-current`, при необходимости <strong>сбросьте к origin</strong> своей ветки или откатите ошибочный merge. Подробнее здесь — [типовые ситуации](./1141#pull-из-неправильной-ветки), [типовые ситуации](./1141#сбросить-локальную-ветку-к-серверу).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Detached HEAD после checkout старого тега — "You are in detached HEAD state".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Вы смотрите snapshot без имени ветки — коммиты здесь <strong>легко потерять</strong>. Создайте ветку `git switch -c fix-from-tag` или вернитесь на main. Подробнее здесь — [типовые ситуации](./1141#не-понимаю-что-произошло), [ветвление](./113).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Баг появился неделю назад — как найти коммит, который всё сломал?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Запустите <strong>`git bisect`</strong> с хорошим и плохим коммитом, на каждом шаге прогоняйте тест/сборку. Быстрее ручного перебора десятков коммитов. Подробнее здесь — [типовые ситуации](./1141#найти-коммит-который-всё-сломал-bisect).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Нужен один коммит из чужой ветки, merge всей ветки не хочу.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Используйте <strong>`git cherry-pick`</strong> по hash — переносит один commit. При конфликте разрешайте как при merge. Подробнее здесь — [типовые ситуации](./1141#перенести-один-коммит-cherry-pick), [ветвление](./113).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> GUI-клиент (VS Code, GitHub Desktop) показывает одно, в терминале другое.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Проверьте <strong>рабочую директорию и ветку</strong> в обоих местах, обновите статус (`fetch`). GUI и CLI — один Git, расхождение почти всегда из разных папок или stale view. Подробнее здесь — [установка и настройка](./111), [как работать с Git](./112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `git config user.email` не тот — коммиты в PR от "чужого" автора.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Настройте <strong>имя и email</strong> на уровне repo или global, совпадающие с аккаунтом GitHub/GitLab. Старые коммиты в открытом PR — amend/rebase только до merge и с согласованием. Подробнее здесь — [установка и настройка](./111), [рекомендации](./114).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Submodule / LFS — коллега клонировал, у него пустые папки или огромный clone.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> После clone нужен <strong>`git submodule update --init`</strong>; для LFS — `git lfs pull`. Документируйте это в README проекта. Подробнее здесь — [как работать с Git](./112), [углубление — remotes](/encyclopedia/8-infra-security/8-03-zabota-o-kode-i-dannyh/113).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Боюсь `git push --force` — когда `--force-with-lease` реально нужен?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> После rebase своей feature-ветки, которую <strong>никто кроме вас не базировал</strong>, — `--force-with-lease` безопаснее `--force`: откажет, если на remote появились чужие коммиты. На `main` force — табу без процедуры. Подробнее здесь — [типовые ситуации](./1141), [опасные скрипты](/encyclopedia/8-infra-security/8-03-zabota-o-kode-i-dannyh/101).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как установить Git на Windows 10 / 11?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Скачайте установщик с git-scm.com или поставьте через winget/chocolatey, затем проверьте <strong>`git --version`</strong> и настройте имя и email. Подробнее здесь — [установка и настройка Git](./111).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как сделать первый commit в Git — пошагово?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> `git init` → создайте файлы → <strong>`git add .`</strong> → `git commit -m "сообщение"`. Без add файлы останутся untracked. Подробнее здесь — [система контроля версий Git](./1), [как работать с Git](./112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как загрузить проект на GitHub — git push с нуля?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Создайте репозиторий на GitHub, затем <strong>`git remote add origin URL`</strong> и `git push -u origin main`. Первый push привязывает локальную ветку к remote. Подробнее здесь — [как работать с Git](./112), [лабораторный кейс GitHub Pages](/lab/Кейсы/3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Git pull или git fetch — в чём разница простыми словами?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>`fetch`</strong> только скачивает изменения с сервера; <strong>`pull`</strong> = fetch + merge (или rebase) в текущую ветку. Для контроля сначала fetch, потом merge вручную. Подробнее здесь — [как работать с Git](./112), [справочник](./115).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как отменить последний commit, если ещё не делал push?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> С сохранением файлов — <strong>`git reset --soft HEAD~1`</strong>; с откатом изменений — `--mixed` или `--hard` (осторожно). Подробнее здесь — [типовые ситуации](./1141), [справочник](./115).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как решить merge conflict в Git — что делать с <<<<<<< HEAD?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Откройте файл, выберите нужный код между маркерами, удалите <strong>`<<<<<<<`, `=======`, `>>>>>>>`</strong>, сохраните, `git add`, завершите merge. Подробнее здесь — [ветвление и слияние](./113), [типовые ситуации](./1141).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое git branch и зачем создавать ветки?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Ветка — <strong>отдельная линия истории</strong> для фичи или fix без ломания main. `git switch -c feature` создаёт и переключает. Подробнее здесь — [ветвление и слияние](./113).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как клонировать репозиторий с GitHub — git clone команда?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>`git clone https://github.com/user/repo.git`</strong> — HTTPS; для SSH нужен ключ в аккаунте. Clone создаёт папку с полной историей. Подробнее здесь — [как работать с Git](./112), [установка](./111).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Пример .gitignore для Node.js / Python / Visual Studio?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Исключайте <strong>`node_modules/`, `__pycache__/`, `bin/`, `obj/`, `.env`</strong> — шаблоны зависят от стека. Готовые примеры и правила — в полном руководстве. Подробнее здесь — [`.gitignore` — полное руководство](./116).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Git для начинающих — с чего начать изучение?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Маршрут: зачем Git → install → add/commit → branch → push/pull → merge/PR. Практика на pet-проекте лучше зубрёжки команд. Подробнее здесь — [о разделе](./intro), [первый репозиторий](./1).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое pull request (PR) на GitHub?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> PR — запрос <strong>влить вашу ветку в main</strong> с code review и CI. На GitLab аналог — Merge Request. Подробнее здесь — [ветвление и слияние](./113), [рекомендации в команде](./114).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Git merge vs rebase — что лучше для новичка?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>Merge</strong> сохраняет историю слияний; <strong>rebase</strong> выстраивает линейную историю, но переписывает commits. В shared-ветках после push rebase осторожно. Подробнее здесь — [ветвление](./113#merge-i-rebase), [типовые ситуации](./1141).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как настроить git config user.name и user.email?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>`git config --global user.name "Имя"`</strong> и `user.email` — email должен совпадать с GitHub для привязки коммитов. Подробнее здесь — [установка и настройка](./111).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как удалить файл из Git, но оставить на диске?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>`git rm --cached имя_файла`</strong>, добавьте в `.gitignore`, commit. Файл исчезнет из репозитория, локально останется. Подробнее здесь — [`.gitignore`](./116), [типовые ситуации](./1141).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое git stash — как временно спрятать изменения?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>`git stash push -m "описание"`</strong> убирает правки из рабочей копии; `git stash pop` возвращает. Удобно перед срочным switch ветки. Подробнее здесь — [типовые ситуации](./1141#временно-спрятать-правки-stash).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> GitHub Desktop или командная строка — что выбрать?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> GUI проще для обзора diff; CLI нужен в CI и на сервере. Оба работают с одним Git — <strong>полезно знать команды</strong> даже с GUI. Подробнее здесь — [установка](./111), [справочник-шпаргалка](./115).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как откатить файл к версии из последнего commit?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>`git restore имя_файла`</strong> (или `git checkout -- файл` в старых версиях) — отменяет незакоммиченные правки. Из старого commit — `git restore --source=hash`. Подробнее здесь — [типовые ситуации](./1141), [справочник](./115).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое git revert и когда его использовать?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>`git revert`</strong> создаёт новый commit, отменяющий старый — безопасно для уже запушенной истории. В отличие от reset, не переписывает прошлое. Подробнее здесь — [типовые ситуации](./1141), [рекомендации](./114).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> SSH ключ для GitHub — как настроить git push без пароля?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Сгенерируйте ключ <strong>`ssh-keygen`</strong>, добавьте публичную часть в GitHub Settings → SSH keys, используйте remote `git@github.com:user/repo.git`. Подробнее здесь — [установка](./111), [кейс GitHub Pages](/lab/Кейсы/3).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как посмотреть историю коммитов — git log?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>`git log --oneline --graph`</strong> — компактное дерево; `git log -p файл` — история файла. GUI в VS Code и GitHub тоже показывают log. Подробнее здесь — [справочник](./115), [как работать с Git](./112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое GitFlow — нужен ли он маленькой команде?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> GitFlow — модель веток <strong>main / develop / release / hotfix</strong>. Для маленьких команд часто хватает main + feature; GitFlow — для релизных циклов. Подробнее здесь — [GitFlow в разделе 8.03](/encyclopedia/8-infra-security/8-03-zabota-o-kode-i-dannyh/1111), [ветвление](./113).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как работать с Git в команде — базовый workflow?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Ветка от main → commits → push → <strong>PR + review</strong> → merge → удалить ветку. Не коммитьте в main напрямую в shared repo. Подробнее здесь — [рекомендации в команде](./114), [о разделе](./intro).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Git LFS — что это и когда нужен?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Git LFS хранит <strong>большие бинарники</strong> (видео, модели) отдельно от истории commit. Нужен `git lfs install` и track по расширениям. Подробнее здесь — [`.gitignore`](./116), [remotes 8.03](/encyclopedia/8-infra-security/8-03-zabota-o-kode-i-dannyh/113).</p>

## Что запомнить

Система контроля версий Git — это фундаментальный инструмент современной разработки, обеспечивающий надёжное управление изменениями в коде и документации. Git позволяет сохранять полную историю изменений, откатываться к любому предыдущему состоянию проекта, работать над несколькими задачами параллельно с помощью веток и безопасно объединять результаты работы разных участников команды.

Git изначально задуман как распределённая система: каждый разработчик обладает полной копией репозитория со всей историей, что делает работу автономной, устойчивой к сбоям серверов и гибкой в организации процессов. Основные операции — `init`, `add`, `commit`, `push`, `pull`, `branch`, `merge` — формируют базовый рабочий цикл, который необходимо освоить каждому, кто взаимодействует с кодом.

Важнейшим элементом эффективного использования Git является понимание состояний файлов (untracked, modified, staged, committed), а также механизмов ветвления и слияния. Ветки позволяют изолировать эксперименты, новые функции и исправления ошибок, не нарушая стабильность основной версии проекта. Слияние (`merge`) требует внимательного подхода при возникновении конфликтов, поскольку Git не может автоматически решить, какая версия кода корректна — это остаётся за человеком.

Для совместной работы применяются практики, такие как pull request, code review и CI/CD-пайплайны, которые повышают качество кода и снижают риск внедрения ошибок. Даже при серьёзных ошибках — случайном удалении файлов, сбросе коммитов или потере веток — Git предоставляет механизмы восстановления через `reflog`, `restore`, `revert`, `stash` и другие команды. Пошаговые сценарии "случилось X — сделай Y" собраны в главе [Типовые ситуации с Git](./1141.md).

Освоение Git — это принятие культуры ответственного управления изменениями, прозрачности истории и уважения к работе коллег. Навык уверенного владения Git открывает доступ к современным методологиям разработки, облачным платформам и профессиональным сообществам.
