## FAQ — Часто задаваемые вопросы

Типичные сбои при работе с Docker и Kubernetes, ситуации новичков и **ответы на частые запросы в поиске** ("docker daemon not running", "port is already allocated", "ImagePullBackOff"). Краткий ответ здесь; разбор — в главах раздела. Заучивание определений — в [чек-листе](./999).

<div class="faq-list">

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `docker ps` или `docker compose up` пишут "Cannot connect to the Docker daemon" — что проверить?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Демон Docker <strong>не запущен</strong> или клиент смотрит не туда: на Windows/macOS включите Docker Desktop; на Linux — `sudo systemctl start docker` и членство пользователя в группе `docker`. Проверьте переменную `DOCKER_HOST`. Подробнее здесь — [Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/111), [справочник](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> При `docker run -p 8080:80` ошибка "port is already allocated".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Порт <strong>8080 на хосте уже занят</strong> другим процессом или контейнером. Найдите владельца (`ss -tlnp`, `docker ps`), остановите лишний контейнер или смените левую часть маппинга (`-p 8081:80`). Подробнее здесь — [Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/111), [сеть](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/115).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Контейнер стартует и сразу исчезает — статус Exited (0) или Exited (1).</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Процесс внутри <strong>завершился</strong>: одноразовая команда без долгоживущего PID, падение приложения или неверный `CMD`/`ENTRYPOINT`. Смотрите `docker logs <id>` и `docker inspect` — поле `State.ExitCode`. Для отладки запустите с `-it` и shell. Подробнее здесь — [объекты Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/112), [Dockerfile](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/116).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `docker build` падает на шаге `RUN apt-get` или `COPY` — "file not found".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Контекст сборки — <strong>каталог, переданный в build</strong>, а не вся машина. Путь в `COPY` относителен контексту; лишние файлы режет `.dockerignore`. Проверьте синтаксис Dockerfile и базовый образ в `FROM`. Подробнее здесь — [Dockerfile](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/116), [справочник](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Образ получился на 3 ГБ — деплой и pull занимают вечность.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Тяжёлый базовый образ, лишние слои, артефакты сборки внутри слоя. Используйте <strong>slim/alpine</strong>, multi-stage build, `.dockerignore`, объединяйте `RUN`. Подробнее здесь — [Dockerfile](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/116), [работа с Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/114).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Данные в контейнере пропали после `docker rm` — это баг?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Файловая система контейнера <strong>эфемерна</strong>. Постоянные данные храните в named volume или bind mount; без тома удаление контейнера стирает слой записи. Подробнее здесь — [объекты Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/112), [Compose](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1111).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Bind mount на Linux: "Permission denied" при записи в `/app/data`.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> UID/GID процесса в контейнере <strong>не совпадает</strong> с владельцем каталога на хосте. Запускайте от non-root с нужным uid, поправьте `chown` на хосте или используйте named volume. Подробнее здесь — [объекты Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/112), [работа с Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/114).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Два контейнера в Compose не видят друг друга по имени сервиса.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Сервисы должны быть в <strong>одной пользовательской сети</strong> Compose; обращайтесь по имени сервиса из YAML, не по `localhost` внутри контейнера. Проверьте `networks:` и что оба сервиса подключены. Подробнее здесь — [сеть](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/115), [Compose](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1111), примеры — [готовые стеки](/lab/Примеры/11111).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `depends_on` в Compose есть, но приложение падает — "connection refused" к PostgreSQL.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> `depends_on` ждёт <strong>старт контейнера</strong>, а не готовность БД. Добавьте healthcheck у postgres, `condition: service_healthy` или retry/backoff в приложении. Подробнее здесь — [Compose](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1111), [работа с Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/114), готовый пример app+db — [стек №4](/lab/Примеры/11111#4-приложение--postgresql).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Диск забит — Docker пишет "no space left on device".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Старые образы, остановленные контейнеры и build cache копятся в `/var/lib/docker`. `docker system df`, затем `docker system prune` (осторожно с неиспользуемыми volumes). Подробнее здесь — [работа с Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/114), [объекты Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Контейнер убит с кодом 137 — что это значит?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Часто <strong>OOM Kill</strong>: процесс превысил лимит памяти cgroup. Задайте `--memory` / `mem_limit` в Compose, профилируйте утечки, увеличьте лимит на хосте. Подробнее здесь — [работа с Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/114), [Swarm и Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/117).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Запускаю всё от root внутри образа — "на локалке же норм".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Root в контейнере при escape или монтировании docker.sock — <strong>root на хосте</strong>. В Dockerfile — `USER`, минимальные capabilities, read-only root FS где возможно. Подробнее здесь — [работа с Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/114), [оглавление раздела](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/intro).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `kubectl get pods` — статус ImagePullBackOff.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Кластер <strong>не может скачать образ</strong>: неверное имя/тег, приватный registry без `imagePullSecrets`, сеть или rate limit Docker Hub. `kubectl describe pod` — Events внизу. Подробнее здесь — [первые шаги K8s](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1172), [справочник Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/211).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Pod в CrashLoopBackOff — контейнер перезапускается каждые секунды.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Приложение падает при старте или <strong>liveness probe</strong> убивает pod слишком рано. `kubectl logs pod --previous`, events, проверьте env, ConfigMap и образ. Подробнее здесь — [реализация Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1171), [справочник Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/211).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Pod долго в Pending — "0/3 nodes are available: insufficient cpu".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Запрошено <strong>requests</strong> больше, чем свободно на нодах, или taints без tolerations. Уменьшите requests, добавьте ноды или поправьте nodeSelector/affinity. Подробнее здесь — [Swarm и Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/117), [реализация Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1171).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `kubectl apply` прошёл, но в pod старый код — деплой "не сработал".</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Образ с тегом <strong>`latest`</strong> мог не перекачаться (`imagePullPolicy: Always` или смените тег). Проверьте revision deployment и что rollout завершился: `kubectl rollout status`. Подробнее здесь — [реализация Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1171), [Dockerfile](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/116).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Ingress отдаёт 502 Bad Gateway, pod Running.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Service смотрит не на те <strong>labels/ports</strong>, приложение слушает другой порт, или readiness не пройден — трафик идёт на неготовые endpoints. Проверьте `kubectl get endpoints`, Service `targetPort` и логи ingress-controller. Подробнее здесь — [реализация Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1171), [сеть](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/115).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> ConfigMap изменили, приложение в pod всё ещё со старыми значениями.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Смонтированный ConfigMap <strong>не всегда hot-reload</strong> — часто нужен restart pod/deployment. Secrets и envFrom тоже фиксируются на старте контейнера. Подробнее здесь — [справочник Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/211), [реализация Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1171).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> HPA не добавляет реплики при высокой нагрузке.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Нужен рабочий <strong>metrics-server</strong> (или custom metrics), заданы requests у контейнеров, HPA ссылается на правильный Deployment. Проверьте `kubectl describe hpa`. Подробнее здесь — [реализация Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1171), [Swarm и Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/117).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `kubectl` пишет "Forbidden" — права есть у коллеги, у меня нет.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> RBAC: ваш ServiceAccount или user <strong>не входит в RoleBinding</strong> для namespace/ресурса. `kubectl auth can-i create pods -n prod`. Подробнее здесь — [справочник Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/211), [первые шаги K8s](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1172).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Helm install failed — release в статусе failed, ресурсы половиной висят.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Смотрите `helm status`, hooks и pre-install jobs. Откат: `helm rollback` или `helm uninstall` с пониманием, что удалится. Values и chart version должны совпадать со средой. Подробнее здесь — [реализация Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1171), [Swarm и Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/117).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Docker Desktop на Windows — WSL2, контейнеры "тормозят" или не стартуют.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Проверьте интеграцию WSL2, лимиты памяти/CPU в настройках Desktop, что диск не переполнен внутри дистрибутива. Перезапуск Docker Desktop и `wsl --shutdown` — типичный первый шаг. Подробнее здесь — [первые шаги K8s](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1172), [Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/111).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Один сервер — ставить Swarm, Kubernetes или просто Compose?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Локально и на малом стенде достаточно <strong>Compose</strong>; Swarm/K8s нужны для оркестрации множества сервисов, rolling update и self-healing в кластере. Не поднимайте полный K8s "ради одного контейнера". Подробнее здесь — [Swarm и Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/117), [оглавление](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/intro).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Пробросил порт, с хоста сайт открывается, из другого контейнера — нет.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> `-p` публикует порт на <strong>интерфейс хоста</strong>; между контейнерами используйте внутреннюю сеть Docker и порт контейнера без publish. `host.docker.internal` — для доступа контейнера к сервисам на хосте (Desktop). Подробнее здесь — [сеть](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/115), [справочник](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> `docker compose up -d` — сервис unhealthy, healthcheck fail.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Команда healthcheck слишком строгая, короткий `interval`/`start_period` или приложение слушает не тот порт. Временно уберите healthcheck для отладки, поправьте `test:` и таймауты. Подробнее здесь — [Compose](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1111), [работа с Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/114).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Смонтировали docker.sock в контейнер — CI "удобно", безопасно ли?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Это <strong>полный контроль над хостом</strong> для процесса внутри контейнера. В prod и shared CI используйте Kaniko, buildkit в изолированном runner, rootless. Подробнее здесь — [работа с Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/114), [оглавление](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/intro).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Переключил `kubectl config use-context` — команды бьют не в тот кластер.</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Всегда проверяйте <strong>текущий context и namespace</strong>: `kubectl config current-context`, `kubectl config set-context --current --namespace=…`. Для prod — отдельный kubeconfig или prompt в shell. Подробнее здесь — [первые шаги K8s](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1172), [справочник Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/211).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Чем Docker отличается от виртуальной машины?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Контейнер делит <strong>ядро хоста</strong> и изолирует процесс через namespaces и cgroups; VM поднимает отдельную ОС на гипервизоре. Контейнеры стартуют быстрее и легче по ресурсам, но изоляция слабее, чем у полноценной VM. Подробнее здесь — [Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/111), [объекты Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как установить Docker на Windows 10 и 11?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Скачайте <strong>Docker Desktop</strong>, включите WSL2 или Hyper-V по требованиям установщика, перезагрузите ПК и дождитесь запуска демона в трее. Проверка — `docker version` в PowerShell или терминале WSL. Подробнее здесь — [Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/111), [первые шаги K8s](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1172).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое Kubernetes простыми словами?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Kubernetes — <strong>оркестратор контейнеров</strong>: распределяет pod по нодам, перезапускает упавшие, масштабирует реплики и обновляет версии без простоя. Вы описываете желаемое состояние в YAML, control plane приводит кластер к нему. Подробнее здесь — [Swarm и Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/117), [реализация Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1171).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как посмотреть логи Docker-контейнера?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Команда <strong>`docker logs &lt;container&gt;`</strong> показывает stdout/stderr процесса; `-f` — поток в реальном времени, `--tail 100` — последние строки. Для упавшего контейнера укажите id или имя из `docker ps -a`. Подробнее здесь — [работа с Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/114), [справочник](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/2).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что означает инструкция FROM в Dockerfile?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>`FROM`</strong> задаёт базовый образ, на который накладываются следующие слои: ОС, runtime, зависимости. Первая инструкция в Dockerfile (кроме ARG перед FROM); тег или digest фиксируют версию для воспроизводимых сборок. Подробнее здесь — [Dockerfile](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/116), [объекты Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое Helm chart в Kubernetes?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Helm chart — <strong>упакованный набор шаблонов</strong> манифестов K8s плюс values для параметров среды. `helm install` разворачивает release; обновления и откаты версионируются без ручного редактирования десятков YAML. Подробнее здесь — [реализация Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1171), [Swarm и Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/117).</p>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Зачем нужен Ingress в Kubernetes?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Ingress — <strong>HTTP-маршрутизация снаружи кластера</strong> к Service: host, path, TLS, балансировка через ingress-controller (nginx, traefik). Один внешний IP вместо NodePort на каждый сервис. Подробнее здесь — [реализация Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1171), [сеть](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/115).</p>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Что такое Persistent Volume в Kubernetes?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> <strong>PersistentVolume (PV)</strong> — том с данными, переживающий перезапуск pod; PVC запрашивает объём у кластера. Без PV файлы в контейнере исчезают при удалении pod, как в Docker без volume. Подробнее здесь — [справочник Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/211), [объекты Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/112).</p>
</div>

<div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Как установить и запустить minikube на ноутбуке?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Установите minikube и драйвер (Docker, Hyper-V, KVM), выполните <strong>`minikube start`</strong>, затем `kubectl` использует context minikube. Подходит для локальной практики с Deployment, Service и Ingress без облачного кластера. Подробнее здесь — [первые шаги K8s](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1172), [оглавление](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/intro).</p>

Меньший образ быстрее pull и деплой в CI/CD. Подробнее здесь — [Dockerfile](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/116), [работа с Docker](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/114).</p>

Для одноразовой отладки без долгоживущего процесса используйте `docker run -it` с нужным образом. <div class="faq-item">
  <p class="faq-q"><span class="faq-label">Вопрос.</span> Чем Docker Compose отличается от Kubernetes?</p>
  <p class="faq-a"><span class="faq-label">Ответ.</span> Compose описывает <strong>несколько контейнеров на одном хосте</strong> в YAML для dev и малых стендов; Kubernetes управляет кластером, репликами, self-healing и rolling update в prod. Compose проще стартовать, K8s — для масштаба и отказоустойчивости. Подробнее здесь — [Compose](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1111), [готовые стеки](/lab/Примеры/11111), [Swarm и Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/117).</p>

  <p class="faq-a"><span class="faq-label">Ответ.</span> `.dockerignore` исключает каталоги и файлы из <strong>контекста сборки</strong>, который отправляется демону при `docker build`. Меньше данных — быстрее build и нет случайного COPY секретов или `node_modules` в образ. Namespace изолирует объекты и квоты внутри одного кластера для команд и сред. <div class="faq-item">

От readiness отличается тем, что readiness снимает pod с балансировки, liveness — лечит зависшее приложение. Подробнее здесь — [реализация Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/1171), [справочник Kubernetes](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/211).</p>

## Что вынести из раздела

1. **Контейнер** — изолированный процесс с собственной файловой системой; **образ** — неизменяемый шаблон слоёв для его запуска.
2. **Docker Engine** = клиент + демон на хосте (образы, контейнеры) + реестр для обмена образами; `build`/`pull`/`run`/`push` — [схема](/encyclopedia/8-infra-security/8-06-konteynerizatsiya-i-orkestratsiya/111#kak-ustroen-docker); оркестрация (Swarm, Kubernetes) — отдельный уровень для кластеров.
3. Жизненный цикл:
```bash
Dockerfile
docker build
docker push
docker pull
docker run
```

Разбор:
- `Dockerfile` — декларативное описание слоёв образа — базовый образ, зависимости, команда запуска; из него собирают артефакт, а не "живой" контейнер.
- `docker build` — демон читает Dockerfile и контекст каталога, выполняет инструкции (`FROM`, `RUN`, `COPY`…) и складывает слои в локальный образ с тегом.
- `docker push` — загрузка собранного образа в удалённый registry (Docker Hub, ECR, GHCR), чтобы другие хосты и CI могли его скачать.
- `docker pull` — скачивание образа по имени и тегу (или digest) из registry в локальный кэш перед запуском или деплоем.
- `docker run` — создание и старт контейнера из образа — изоляция процесса, сеть, тома, проброс портов, переменные окружения.
- Цепочка отражает типичный путь: описали → собрали → опубликовали → развернули на целевой машине или в оркестраторе.

4. Данные вне контейнера — **тома** и **bind mount**; сеть между сервисами — пользовательские сети и DNS по имени сервиса в Compose.
5. **Compose** описывает несколько контейнеров в YAML; CLI — `docker compose` (V2).

```bash
docker compose
```

Разбор:
- `docker compose` — подкоманда Docker CLI V2 для мультиконтейнерных стеков по файлу `compose.yaml` (раньше отдельный бинарь `docker-compose`).
- Без аргументов часто подразумевают `docker compose up` — поднять все сервисы, сети и тома, описанные в манифесте.
- Compose читает YAML — образы, `ports`, `environment`, `volumes`, `depends_on`, пользовательские сети — и согласует запуск через Engine.
- Один файл заменяет длинную цепочку ручных `docker run` и упрощает локальную разработку и тестовые стенды.
- В продакшене тот же манифест может быть основой, но часто его заменяют или дополняют Kubernetes/Swarm.

6. В продакшене — лимиты ресурсов, `restart`, healthcheck, минимальные образы, non-root, `--security-opt`; при росте нагрузки — Kubernetes или Swarm.
