## Зачем эта статья

Когда хост или сервис **тормозит**, на машине уже есть встроенные средства — без установки агента и без доступа к исходникам приложения. Эта статья — **практический runbook по SSH**: что запустить, на что смотреть в выводе и куда копать дальше.

Постоянный мониторинг, алерты и baseline в Grafana — в [92 — мониторинг](./92.md). Разбор конкретных инцидентов (сервис не отвечает, D-state, OOM) — в [9 — ошибки и логи](./9.md). Справочник FHS, `chmod` и пакетные менеджеры — в [93](./93.md). Базовые `free`, `df`, `top` — в [напоминалке терминала](/encyclopedia/2-system-network/2-05-terminal/101#состояние-системы-и-дисков).

## Модель USE и порядок действий

Удобная схема для узкого места — **USE** (Brendan Gregg):

| Буква | Смысл | Вопрос |
|-------|--------|--------|
| **U** | Utilization | Ресурс занят? (CPU %, `%util` диска) |
| **S** | Saturation | Есть очередь? (load, `await`, swap in/out) |
| **E** | Errors | Ошибки в ядре, SMART, сеть? |

**Типичный порядок** при жалобе «всё медленно» на одном сервере:

1. Общая картина за несколько секунд — `vmstat`, `sar` или `mpstat`.
2. Диск — `iostat` (высокий `iowait` в `vmstat` часто ведёт сюда).
3. Память — `/proc/meminfo`, рост `si`/`so` в `vmstat`.
4. Сеть и порты — `ss`, при конфликте порта — `lsof`.
5. Сообщения ядра — `dmesg` (OOM, I/O error).
6. Подозрительный процесс — `/proc/<pid>/status`, `perf`, `strace`.

```mermaid
flowchart LR
  A[Жалоба на тормоза] --> B[vmstat / sar]
  B --> C{iowait высокий?}
  C -->|да| D[iostat]
  C -->|нет| E[meminfo / swap]
  D --> F[dmesg]
  E --> F
  F --> G[процесс: perf / strace]
```

## Установка утилит

| Пакет | Дистрибутив | Даёт |
|-------|-------------|------|
| `sysstat` | Debian/Ubuntu: `apt install sysstat` | `sar`, `iostat`, `mpstat`, `pidstat` |
| `sysstat` | RHEL/Alma: `dnf install sysstat` | то же |
| `perf` | `linux-tools-common` + метапакет ядра | `perf top`, `perf record` |
| `strace` | обычно уже есть | трассировка syscall |
| `lsof` | `apt install lsof` / в составе системы | открытые файлы и сокеты |

На Debian для `sar` по расписанию иногда нужно включить сбор: `systemctl enable --now sysstat`.

## CPU

### `sar` — срезы загрузки CPU

```bash
sar -u 1 5
```

Пять интервалов по одной секунде: удобно для скриптов и краткого снимка без интерактивного `top`. Смотрите `%user`, `%system`, **`%iowait`** (ожидание диска), `%steal (виртуализация).

История с прошлых дней (если включён `sysstat`):

```bash
sar -u -f /var/log/sysstat/saDD
```

### `mpstat` и `pidstat`

По ядрам:

```bash
mpstat -P ALL 1 3
```

Кто грузит CPU:

```bash
pidstat -u 1 5
```

### `perf top` — горячие функции процесса

```bash
perf top -p <pid>
```

Показывает стеки в реальном времени. Нужны права на трассировку (`perf_event_paranoid`, часто root). Для записи сессии — `perf record -g -p <pid>` и `perf report` (кратко также в [93](./93.md)).

| Симптом в CPU | Куда дальше |
|---------------|-------------|
| Высокий `%iowait` | [Диск](#диск) |
| Один процесс 90 %+ | `perf top -p`, `pidstat` |
| Много потоков, умеренный CPU | `/proc/<pid>/status`, блокировки в приложении |

## Память

### `/proc/meminfo` — детали от ядра

```bash
grep -E 'MemTotal|MemFree|MemAvailable|Cached|Dirty|Swap' /proc/meminfo
```

**`MemAvailable`** — ориентир «сколько можно выделить без агрессивного свопа»; для быстрой оценки информативнее, чем только `MemFree`. **`Dirty`** — страницы, ещё не сброшенные на диск; рост при тяжёлой записи. Полный справочник полей — [51 — `/proc`](/encyclopedia/2-system-network/2-01-operatsionnaya-sistema/51).

### `vmstat` — своп, контекстные переключения, очередь

```bash
vmstat 1 5 -S M
```

Ключевые колонки (зависит от версии, смотрите заголовок):

- **`si` / `so`** — swap in/out; устойчивый поток при наличии RAM — признак давления на память.
- **`wa`** — ожидание I/O (аналог iowait).
- **`cs`** — context switches; резкий всплеск вместе с ростом latency — перегруз или борьба за CPU.

### Память одного процесса

```bash
grep -E 'VmRSS|VmSwap|Threads' /proc/<pid>/status
```

- **`VmRSS`** — резидентная память в RAM.
- **`VmSwap`** — сколько процесса ушло в swap.
- **`Threads`** — число потоков (утечки потоков иногда маскируются под «утечку памяти»).

Утечки и OOM в сценариях — [9 — память и OOM](./9.md).

## Диск

### `iostat` — I/O и загрузка устройств

```bash
iostat -xz 1
```

Флаги:

- **`-x`** — расширенные поля (`await`, `r/s`, `w/s`).
- **`-z`** — скрыть idle-устройства.
- **`1`** — интервал в секундах.

На что смотреть:

| Поле | Интерпретация |
|------|----------------|
| **`%util`** | Близко к 100 % — устройство насыщено |
| **`await`** | Среднее время операции (мс); рост при нормальной нагрузке — bottleneck |
| **`avgqu-sz`** | Длина очереди к диску |

Высокий `%util` при малом throughput иногда указывает на мелкий random I/O или проблемный диск — сверка с `dmesg` и SMART (см. [9 — аппаратная диагностика](./9.md)).

Дополнительно по процессам — `iotop` (пакет `iotop`).

## Сеть и порты

### `ss` — listening-порты и процессы

```bash
ss -tulpn | grep LISTEN
```

Аудит «что слушает хост», поиск лишних сервисов. Таблица сетевых команд — [6 — справочник при сбоях](./6.md#setevye-komandy-diagnostika).

### `lsof` — кто занял порт

```bash
lsof -i :8080
```

Классический ответ на `address already in use`. По PID — `lsof -p <pid>`.

Пропускная способность и задержки канала — `iftop`, `nethogs`, `iperf3` (в [6](./6.md) и [9 — сценарий медленного сервиса](./9.md)).

## Ядро — `dmesg`

```bash
dmesg -T | grep -E 'OOM|kill|error|I/O' | tail -20
```

Флаг **`-T`** — человекочитаемое время. Здесь же — OOM killer, ошибки диска, сбои драйверов. Для служб с journal — `journalctl -k --since "1 hour ago"`.

<div class="callout callout--info">
  <div class="callout-title">Сообщения ядра и логи приложения</div>

  `dmesg` фиксирует то, что сообщило **ядро**. Ошибки уровня HTTP, SQL или бизнес-логики ищите в `journalctl -u …` и файлах в `/var/log/` — см. [9](./9.md).
</div>

## Отладка процесса без исходников

### `strace` — системные вызовы

```bash
strace -p <pid> -e trace=network -T
```

- **`-p`** — подключиться к работающему процессу.
- **`-e trace=network`** — только сетевые syscall (сокеты, connect, send).
- **`-T`** — время на каждый вызов.

Другие полезные фильтры: `openat`, `read`, `write`, `futex`. Вывод в файл: `strace -o trace.log -f ./app`.

<div class="callout callout--warning">
  <div class="callout-title">Нагрузка на проде</div>

  `strace` и `perf` замедляют процесс. На боевом трафике сначала снимите метрики (`pidstat`, `vmstat`), затем краткую трассировку с ограничением по времени или на копии нагрузки в staging.
</div>

### `perf top` — CPU hotspots

См. раздел [CPU](#cpu). Для Java/.NET есть свои инструменты (`jstat`, `dotnet-counters`) — в [9 — диагностика по приложению](./9.md).

## Сводная таблица команд

| Ресурс | Команда | Зачем |
|--------|---------|--------|
| CPU | `sar -u 1 5`, `mpstat -P ALL 1` | Загрузка, iowait |
| CPU (процесс) | `perf top -p <pid>` | Горячие функции |
| Память | `grep … /proc/meminfo` | Available, dirty, swap |
| Память (динамика) | `vmstat 1 5 -S M` | Swap, wait, cs |
| Память (процесс) | `grep … /proc/<pid>/status` | RSS, swap, threads |
| Диск | `iostat -xz 1` | util, await, очередь |
| Сеть | `ss -tulpn` | Listening-порты |
| Порт | `lsof -i :<port>` | Конфликт порта |
| Ядро | `dmesg -T` + grep | OOM, I/O errors |
| Процесс | `strace -p <pid> …` | Зависания, сеть, файлы |
