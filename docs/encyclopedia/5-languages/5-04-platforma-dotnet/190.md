## Чем F#-проект отличается от C#

В C# порядок файлов в `.csproj` почти не важен: типы из любого файла видны везде. В F# **компилятор читает файлы строго по порядку**, указанному в `.fsproj`. Файл может использовать только то, что объявлено **выше** — в предыдущих файлах или в начале того же файла.

Ошибка «The value or namespace 'X' is not defined» часто означает не опечатку, а **неправильный порядок** `<Compile Include="..."/>`.

---

## Минимальный консольный проект

```bash
dotnet new console -lang F# -n DemoApp
```

Структура:

```text
DemoApp/
  DemoApp.fsproj
  Program.fs
```

`Program.fs` — точка входа. В SDK-шаблоне порядок файлов подставляется автоматически; при добавлении своих `.fs` порядок нужно задавать явно.

---

## Явный порядок в `.fsproj`

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>
  </PropertyGroup>
  <ItemGroup>
    <Compile Include="Domain.fs" />
    <Compile Include="Services.fs" />
    <Compile Include="Program.fs" />
  </ItemGroup>
</Project>
```

| Файл | Содержимое |
|------|------------|
| `Domain.fs` | типы, DU, записи, чистые функции без I/O |
| `Services.fs` | оркестрация, доступ к БД, HTTP |
| `Program.fs` | `[<EntryPoint>]`, композиция, запуск |

Правило: **от данных к эффектам**, от общего к частному.

## Библиотека и ссылка из приложения

```bash
dotnet new classlib -lang F# -n DemoLib
dotnet new console -lang F# -n DemoApp
dotnet add DemoApp/DemoApp.fsproj reference DemoLib/DemoLib.fsproj
```

В `DemoLib.fsproj`:

```xml
<ItemGroup>
  <Compile Include="Types.fs" />
  <Compile Include="Api.fs" />
</ItemGroup>
```

В `DemoApp` достаточно `open DemoLib` (или полного имени модуля), если namespace совпадает с именем сборки и модуля.

Публичный API библиотеки для C#: записи с `[<CLIMutable>]`, осмысленные имена модулей, `[<RequireQualifiedAccess>]` при риске конфликтов имён.

## Модули, namespace и один файл

В одном `.fs` допустимы:

```fsharp
namespace MyCompany.Demo

module Domain =
    type Id = Id of int

module Services =
    open Domain
    let load (Id n) = string n
```

Файл с `namespace` не может содержать «голый» код вне `module` или `type` — всё верхнего уровня внутри модуля или типа.

Несколько `module` в одном файле компилируются в порядке появления; разнести тяжёлые зависимости по файлам проще для сопровождения.

## Файлы подписей (`.fsi`)

Файл интерфейса скрывает реализацию:

```text
Domain.fsi   — публичные сигнатуры
Domain.fs    — реализация
```

В `.fsproj` **`.fsi` идёт сразу перед соответствующим `.fs`**:

```xml
<Compile Include="Domain.fsi" />
<Compile Include="Domain.fs" />
```

Полезно для библиотек: клиент видит контракт, детали остаются в `.fs`.

## Solution из нескольких проектов

Типичная схема:

```text
src/
  App.Core/       # F# library — домен
  App.Infrastructure/  # F# или C# — БД, файлы
  App.Web/        # ASP.NET Core, может быть C#
tests/
  App.Core.Tests/
```

F#-тесты ссылаются на библиотеку так же, как приложение. Порядок файлов настраивается **в каждом** `.fsproj` отдельно.

Смешанный solution (C# UI + F# core) распространён: F# собирается в DLL, C# подключает ссылку на проект — без особых настроек, кроме публичного API.

## Частые проблемы

| Симптом | Решение |
|---------|---------|
| Тип не найден | Поднять файл с определением типа выше в `.fsproj` |
| Циклическая зависимость между файлами | Вынести общие типы в третий файл или объединить модули |
| Дублирование `module` имён | `RequireQualifiedAccess` или разные namespace |
| IntelliSense «отстаёт» | Собрать проект; Ionide опирается на успешную компиляцию |
| Скрипт `#load` падает | Загружать файлы в том же порядке, что в `.fsproj` |

```bash
dotnet build
dotnet test
dotnet run --project src/App/App.fsproj
```
