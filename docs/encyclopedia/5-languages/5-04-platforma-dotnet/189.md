# Асинхронность в F#: async, task и агенты

## Две модели ожидания

F# исторически использует вычислительное выражение **`async`** — своя очередь продолжений, не привязанная напрямую к `System.Threading.Tasks.Task`. С F# 6 добавлено **`task`** — обёртка над `Task`/`Task<T>`, удобная в проектах ASP.NET Core и при вызове C# API.

| | `async` | `task` |
|---|---------|--------|
| Тип результата | `Async<'T>` | `Task<'T>` |
| Типичный запуск | `Async.RunSynchronously`, `Async.Start` | `task.GetAwaiter().GetResult()` (осторожно), `await` из C# |
| Interop с C# `Task` | `Async.AwaitTask` | нативно |
| Новые веб-сервисы на .NET | допустимо | **предпочтительно** |

В [обзоре F#](./18.md) показан классический `async`; здесь — как выбрать и связать с агентами.

---

## Блок `async`

```fsharp
open System.Net.Http

let fetchLength (url: string) =
    async {
        use client = new HttpClient()
        let! text = client.GetStringAsync(url) |> Async.AwaitTask
        return text.Length
    }

let len = fetchLength "https://example.com" |> Async.RunSynchronously
```

- `let!` — ожидание асинхронной операции внутри блока;
- `use` / `use!` — освобождение `IDisposable` при выходе;
- `return` — результат блока.

Параллельный запуск нескольких операций:

```fsharp
let urls = [ "https://a.example"; "https://b.example" ]
let lengths =
    urls
    |> List.map fetchLength
    |> Async.Parallel
    |> Async.RunSynchronously
```

`Async.Parallel` ограничивает степень параллелизма на уровне F# async; для тяжёлого CPU лучше явные пулы или `Task`.

## Блок `task`

```fsharp
let fetchLengthTask (url: string) =
    task {
        use client = new HttpClient()
        let! text = client.GetStringAsync url
        return text.Length
    }
```

Возвращаемый тип — `Task<int>`. Такой код естественно вызывать из C# `await` и из middleware ASP.NET Core.

Правило для новых библиотек на .NET 6+: **внешний контракт** — `Task` / `ValueTask`; внутри F#-модуля можно комбинировать `task` и чистые функции.

---

## Переход между async и Task

```fsharp
// Task -> Async
let taskToAsync (t: System.Threading.Tasks.Task<'T>) = Async.AwaitTask t

// Async -> Task (запуск)
let asyncToTask a = Async.StartAsTask a
```

Избегайте `Async.RunSynchronously` в UI-потоке и в ASP.NET request thread — блокирует поток пула. В библиотеках для C# экспортируйте `Task`, а не `Async`.

## Управление ресурсами

```fsharp
let readFile path =
    async {
        use stream = new System.IO.FileStream(path, System.IO.FileMode.Open)
        use reader = new System.IO.StreamReader(stream)
        return reader.ReadToEnd()
    }
```

Аналог `try/finally` для `IDisposable`. Для синхронного кода — ключевое слово `use` в обычном `let`. Исключения в async/task обрабатываются `try/with` внутри блока; для ожидаемых сбоев по-прежнему предпочтителен `Result` (см. [Сопоставление с образцом](./186.md)).

## MailboxProcessor (агент)

**Агент** — легковесный процесс с очередью сообщений и одним потоком обработки. Состояние меняется только внутри цикла агента — проще рассуждать, чем о `lock` на `mutable`.

```fsharp
type CounterMsg =
    | Add of int
    | Get of AsyncReplyChannel<int>

let createCounter () =
    MailboxProcessor.Start(fun inbox ->
        let rec loop total =
            async {
                let! msg = inbox.Receive()
                match msg with
                | Add n -> return! loop (total + n)
                | Get reply ->
                    reply.Reply total
                    return! loop total
            }
        loop 0)

let agent = createCounter ()
agent.Post (Add 10)
let current = agent.PostAndReply (fun reply -> Get reply)
```

| Подходит | Не подходит |
|----------|-------------|
| Очередь команд к одному ресурсу | Массовый параллельный CPU на всех ядрах |
| Троттлинг, батчинг событий | Простой разовый `async` без состояния |
| Модель «актора» в одном процессе | Распределённый кластер без доп. библиотек |

Для высокой нагрузки смотрят также на `System.Threading.Channels` и `Task`, но агент остаётся идиоматичным инструментом F#.

---

## Типичные ошибки

1. **Блокировать** поток через `RunSynchronously` в серверном коде.
2. **Смешивать** свободный `mutable` и несколько потоков без агента или lock.
3. **Игнорировать** отмену: `CancellationToken` передавать в `GetStringAsync` и проверять в длинных циклах.
4. **Захватывать** `HttpClient` неправильно: один экземпляр на приложение или `IHttpClientFactory`, не новый клиент на каждый запрос в production.
