## Первая программа на Gin

### Где применяют Gin

**HTTP** — протокол, по которому браузер и мобильное приложение обращаются к серверу: метод (`GET`, `POST`, `DELETE`), URL (`/api/notes`), заголовки и тело (часто JSON).

**REST API** — набор URL + методов для работы с ресурсами (заметки, пользователи) без HTML-страниц. Клиент шлёт JSON, сервер отвечает JSON и кодом статуса (`200`, `201`, `404`).

**Gin** — популярный фреймворк поверх стандартного пакета Go **`net/http`**. Он упрощает маршруты, разбор JSON, группы URL и **middleware** (цепочка функций "до и после" handler).

Обзор Gin, Echo, Fiber: [Фреймворки и библиотеки Go](./19.md). Соседние туториалы: [Echo](./2413.md) · [Fiber](./2414.md). Тесты handlers: [Тестирование в Go](./192.md). Чистый `net/http`: [Пример микросервиса](./241.md).

---

### Что получится

Мини-сервис "Заметки" на порту **8080**: health-check, список заметок, создание и удаление. Данные в памяти (слайс), защита от гонок через **`sync.Mutex`**.

---

## Термины

| Термин | Простыми словами |
|--------|------------------|
| **Маршрут (route)** | Связка "метод + путь" → функция-обработчик |
| **Handler** | Функция, которая читает запрос и пишет ответ |
| **`gin.Context`** | Всё про текущий запрос: параметры URL, тело, ответ |
| **Middleware** | Прослойка: лог, recovery от паники, авторизация |
| **JSON-тег** | `json:"text"` — имя поля в JSON |
| **`binding`** | Правила проверки тела запроса (обязательное поле, длина) |
| **`:id` в пути** | Параметр, например `/notes/5` → `id = "5"` |

## REST API "Заметки"

Полный `main.go`:

```go
package main

import (

    "net/http"
    "strconv"
    "sync"

    "github.com/gin-gonic/gin"
)

type Note struct {
    ID   int    `json:"id"`
    Text string `json:"text" binding:"required,min=1,max=500"`
}

var (
    notes  []Note
    nextID = 1
    mu     sync.Mutex
)

func main() {
    r := gin.Default()

    r.GET("/health", func(c *gin.Context) {
        c.JSON(http.StatusOK, gin.H{"status": "ok"})
    })

    api := r.Group("/api")
    {
        api.GET("/notes", listNotes)
        api.POST("/notes", createNote)
        api.DELETE("/notes/:id", deleteNote)
    }

    r.Run(":8080")
}
```

Разбор:
- `package main` и функция `main()` определяют точку входа исполняемого приложения.
- Блок `import` подтягивает стандартные пакеты (`net/http`, `strconv`, `sync`) и внешний фреймворк `gin`.
- Структура `Note` описывает форму данных и контракт JSON-ответов через теги `json:"..."`.
- Глобальные `notes`, `nextID`, `mu` формируют учебное in-memory хранилище и защиту от гонок между конкурентными запросами.
- `gin.Default()` поднимает роутер с полезными middleware по умолчанию, затем регистрируются маршруты `GET/POST/DELETE`.
- `r.Run(":8080")` запускает HTTP-сервер и блокирует текущую горутину до остановки процесса.

---

### Структура `Note` и теги

```go
type Note struct {
    ID   int    `json:"id"`
    Text string `json:"text" binding:"required,min=1,max=500"`
}
```

Разбор:
- `type Note struct` объявляет пользовательский составной тип для хранения заметки.
- Поле `ID int` хранит числовой идентификатор и сериализуется как `id` в JSON.
- Поле `Text string` хранит содержимое заметки и сериализуется как `text`.
- Тег `binding:"required,min=1,max=500"` активирует валидацию при разборе тела запроса: поле обязательно и ограничено по длине.
- Такая структура одновременно используется и для входных данных, и для ответа API, что упрощает учебный пример.

- **`json:"id"`** — при `c.JSON` поле уйдёт в JSON как `"id"`, не `ID`.
- **`binding:"required,min=1,max=500"`** — при `ShouldBindJSON` Gin проверит: поле есть, длина текста от 1 до 500 символов.

---

### Память и mutex

```go
var (
    notes  []Note
    nextID = 1
    mu     sync.Mutex
)
```

Разбор:
- `var (...)` группирует связанные глобальные переменные в одном блоке.
- `notes []Note` — слайс, в котором хранятся все заметки в памяти процесса.
- `nextID = 1` — простой счётчик для выдачи нового идентификатора при создании заметки.
- `mu sync.Mutex` — мьютекс, который сериализует доступ к общим данным между горутинами.
- Такой подход подходит для демо и локального запуска; в боевом сервисе данные обычно выносят в БД.

Несколько HTTP-запросов обрабатываются **параллельно**. Без блокировки два `POST` могут одновременно менять `notes` и `nextID` — **гонка данных**. `mu.Lock()` / `defer mu.Unlock()` в handler гарантируют, что в один момент времени список меняет только одна горутина.

### `main` — маршруты и группа

| Строка | Смысл |
|--------|--------|
| `gin.Default()` | Роутер + встроенные middleware Logger и Recovery |
| `r.GET("/health", ...)` | GET → JSON `{"status":"ok"}` |
| `r.Group("/api")` | Префикс: реальные пути `/api/notes`, не `/notes` |
| `api.DELETE("/notes/:id", ...)` | `:id` — сегмент URL, читается через `c.Param("id")` |
| `r.Run(":8080")` | Слушает `http://127.0.0.1:8080` |

`gin.H{"status": "ok"}` — сокращение для `map[string]interface{}`.

### Handlers — разбор

**Список:**

```go
func listNotes(c *gin.Context) {
    mu.Lock()
    defer mu.Unlock()
    c.JSON(http.StatusOK, notes)
}
```

Разбор:
- Handler принимает `*gin.Context`, через который читает запрос и формирует ответ.
- `mu.Lock()` захватывает блокировку перед чтением общего слайса, чтобы избежать гонок.
- `defer mu.Unlock()` гарантирует освобождение блокировки при любом выходе из функции.
- `c.JSON(http.StatusOK, notes)` отправляет клиенту код `200` и массив заметок в формате JSON.
- Функция короткая и предсказуемая: только чтение данных без изменения состояния.

`defer mu.Unlock()` — разблокировка при выходе из функции, даже если позже добавите `return` с ошибкой.

**Создание:**

```go
func createNote(c *gin.Context) {
    var body Note
    if err := c.ShouldBindJSON(&body); err != nil {
        c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()})
        return
    }
    mu.Lock()
    body.ID = nextID
    nextID++
    notes = append(notes, body)
    mu.Unlock()
    c.JSON(http.StatusCreated, body)
}
```

Разбор:
- `var body Note` создаёт переменную для данных из JSON-тела запроса.
- `c.ShouldBindJSON(&body)` десериализует входной JSON и одновременно запускает проверку `binding`-тегов.
- Ветка `if err != nil` возвращает клиенту `400` и текст ошибки в JSON, после чего выполнение останавливается через `return`.
- После успешного bind код захватывает `mu`, присваивает `ID`, увеличивает `nextID` и добавляет объект в `notes`.
- `c.JSON(http.StatusCreated, body)` возвращает `201 Created` и созданную сущность как подтверждение результата операции.

- `ShouldBindJSON(&body)` — читает тело запроса в struct и применяет `binding`-теги.
- При ошибке — `400 Bad Request` и **обязательный `return`**, иначе код пойдёт дальше с пустым телом.
- `201 Created` — стандартный код "ресурс создан".

**Удаление:**

```go
func deleteNote(c *gin.Context) {
    id, err := strconv.Atoi(c.Param("id"))
    // ...
    notes = append(notes[:i], notes[i+1:]...)
    c.Status(http.StatusNoContent)
}
```

Разбор:
- `c.Param("id")` получает параметр пути `:id` как строку из URL.
- `strconv.Atoi(...)` конвертирует строку в число; при ошибке обычно возвращают `400`.
- Внутри цикла ищется индекс заметки с нужным `ID`.
- `append(notes[:i], notes[i+1:]...)` собирает новый слайс без удаляемого элемента.
- `c.Status(http.StatusNoContent)` возвращает `204` без тела, что удобно для успешного удаления.

`strconv.Atoi` — строка `"5"` → число `5`. Удаление из слайса: два `append` "вырезают" элемент по индексу. `204 No Content` — успех без тела ответа.

Запуск:

```bash
go run .
```

Разбор:
- `go run .` компилирует текущий модуль и сразу запускает получившийся бинарник без явного `go build`.
- Точка `.` означает "собирать пакет из текущей директории".
- Команда удобна для локальной разработки, когда важна скорость цикла "изменил код -> проверил".
- Если порт уже занят, запуск завершится ошибкой bind и это сигнал проверить фоновые процессы.

## Проверка через curl

```bash
curl http://127.0.0.1:8080/health
curl http://127.0.0.1:8080/api/notes
curl -X POST http://127.0.0.1:8080/api/notes \
  -H "Content-Type: application/json" \
  -d '{"text":"Изучить Gin"}'
curl -X DELETE http://127.0.0.1:8080/api/notes/1
```

Разбор:
- Первый запрос проверяет liveness endpoint и быстрый отклик сервера.
- Второй запрос читает текущую коллекцию заметок и помогает проверить сериализацию массива.
- `POST` передаёт JSON-тело и заголовок `Content-Type`, чтобы сервер корректно распарсил payload.
- Последний `DELETE` проверяет работу маршрута с параметром пути и логику удаления по `id`.
- Последовательный запуск этих команд покрывает базовый жизненный цикл ресурса: create/read/delete.

| Команда | Что проверяет |
|---------|----------------|
| Первая | Сервер жив (`200`, JSON status) |
| Вторая | Пустой или текущий список заметок |
| POST | Создание; заголовок `Content-Type` нужен для JSON |
| DELETE | Удаление заметки с `id=1` |

В PowerShell кавычки в `-d` иногда экранируют иначе — удобно использовать одинарные снаружи для JSON.

## Свой middleware

**Middleware** в Gin — функция, возвращающая `gin.HandlerFunc`. Обычно вызывают `c.Next()` — передать управление следующему звену цепочки.

```go
func requestLogger() gin.HandlerFunc {
    return func(c *gin.Context) {
        c.Next()
        // после всех handler — статус уже известен:
        // c.Writer.Status(), c.Request.Method, c.Request.URL.Path
    }
}

// r.Use(requestLogger())
```

Разбор:
- Функция возвращает `gin.HandlerFunc`, то есть совместимый middleware-обработчик для Gin.
- Внутренняя функция получает `*gin.Context` и может выполнять логику до и после `c.Next()`.
- `c.Next()` передаёт управление следующему middleware или конечному handler в цепочке.
- После возврата из `c.Next()` доступны итоговый статус и детали запроса, что удобно для логирования метрик.
- Строка `r.Use(requestLogger())` показывает подключение middleware глобально ко всем маршрутам.

`gin.Default()` уже подключает лог запросов и **Recovery** (перехват паники, чтобы сервер не падал целиком).

## Graceful shutdown

При остановке процесса (Ctrl+C, деплой) обрывать активные запросы резко плохо. **Graceful shutdown** — дать handler’ам до N секунд завершиться.

```go

import (

    "context"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"
)

srv := &http.Server{Addr: ":8080", Handler: r}
go func() { _ = srv.ListenAndServe() }()

quit := make(chan os.Signal, 1)
signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
<-quit

ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
_ = srv.Shutdown(ctx)
```

Разбор:
- Дополнительные импорты (`context`, `os/signal`, `syscall`, `time`) нужны для контролируемого завершения процесса.
- `http.Server{Handler: r}` оборачивает Gin-роутер в стандартный сервер и даёт больше контроля над жизненным циклом.
- `signal.Notify(...)` подписывает канал `quit` на системные сигналы завершения (`SIGINT`, `SIGTERM`).
- `context.WithTimeout(..., 5*time.Second)` задаёт верхнюю границу ожидания активных запросов.
- `srv.Shutdown(ctx)` прекращает приём новых соединений и мягко завершает текущие до истечения таймаута.

| Часть | Смысл |
|-------|--------|
| `http.Server{Handler: r}` | Gin-роутер совместим с `http.Handler` |
| `signal.Notify` | Ожидание SIGINT/SIGTERM |
| `Shutdown(ctx)` | Прекращает приём новых соединений, ждёт текущие |

### Частые ошибки

| Симптом | Причина |
|---------|---------|
| `404` на POST | Неверный метод или путь без префикса `/api` |
| `bind` не заполняет struct | Нет `json:"..."` или неверный `Content-Type` |
| Паника в handler | Ошибка после `ShouldBindJSON` без `return` |

## Что часто упускают в первом API на Gin

### Единый формат ошибок

Когда ошибок становится больше, клиенту удобнее получать предсказуемый JSON:

```json
{
  "error": {
    "code": "validation_error",
    "message": "text is required"
  }
}
```

Разбор:
- Формат с вложенным объектом `error` делает структуру ответа расширяемой без ломающих изменений.
- Поле `code` предназначено для машинной обработки на клиенте и маршрутизации сценариев в UI.
- Поле `message` даёт человекочитаемое описание, полезное для логов и интерфейса.
- Единый шаблон стоит применять во всех ошибках (`400`, `404`, `409`, `500`), чтобы фронтенд не писал ветвления под каждый endpoint.
- Такая стандартизация упрощает observability и поддержку API на длинной дистанции.

Даже в учебном проекте полезно ввести один формат ответа для `400`, `404` и `500`. Это упрощает фронтенд и ускоряет отладку.

---

### Пагинация списка

Endpoint `GET /api/notes` быстро становится тяжёлым. Базовая версия с `limit` и `offset`:

```go
limit, _ := strconv.Atoi(c.DefaultQuery("limit", "20"))
offset, _ := strconv.Atoi(c.DefaultQuery("offset", "0"))
```

Разбор:
- `c.DefaultQuery("limit", "20")` читает query-параметр `limit`, а при отсутствии подставляет значение по умолчанию.
- `c.DefaultQuery("offset", "0")` аналогично задаёт сдвиг для выборки.
- `strconv.Atoi` преобразует строковые значения query в числа для дальнейшей работы с пагинацией.
- Игнорирование ошибки через `_` допустимо в учебной версии, но в проде лучше валидировать и возвращать `400` при нечисловом вводе.
- Пара `limit/offset` помогает контролировать размер ответа и предсказуемо нагружать сервер.

Пагинация сразу закладывает масштабирование API и снижает риск "случайно отдали 100000 записей одним ответом".

---

### Логика идемпотентности

`POST` обычно не идемпотентен, а `DELETE /notes/:id` должен быть идемпотентным: повторный запрос на уже удалённый объект возвращает либо `204`, либо `404` по политике команды. Главное — закрепить правило и применять его одинаково.

---

### Контекст и таймауты

Если handler вызывает базу данных или внешний API, передавайте `c.Request.Context()` дальше в сервисы. Тогда отмена запроса клиентом завершает и внутренние операции.

## Мини-чеклист качества для Gin-сервиса

- Есть `gin.Recovery()` и request logging.
- Все ветки ошибок завершаются `return`.
- Данные защищены от гонок (`mutex`) или вынесены в потокобезопасный слой.
- Валидация входных данных отделена от бизнес-логики.
- Есть хотя бы 3 теста: happy path, validation error, not found.

## Дополнительные сниппеты с разбором

### Пример — middleware для API key

```go
func apiKeyGuard(expected string) gin.HandlerFunc {
    return func(c *gin.Context) {
        key := c.GetHeader("X-API-Key")
        if key == "" {
            c.JSON(http.StatusUnauthorized, gin.H{"error": "missing api key"})
            c.Abort()
            return
        }
        if key != expected {
            c.JSON(http.StatusForbidden, gin.H{"error": "invalid api key"})
            c.Abort()
            return
        }
        c.Next()
    }
}

// api := r.Group("/api")
// api.Use(apiKeyGuard("dev-secret"))
```

Разбор:
- `apiKeyGuard(expected string)` создаёт middleware-фабрику, чтобы ключ можно было передать параметром при регистрации.
- `c.GetHeader("X-API-Key")` читает значение конкретного HTTP-заголовка из входящего запроса.
- Ветка с `StatusUnauthorized` (`401`) обрабатывает отсутствие ключа как неаутентифицированный запрос.
- Ветка с `StatusForbidden` (`403`) отделяет ситуацию "ключ есть, но неверный".
- `c.Abort()` останавливает цепочку middleware и не даёт запросу дойти до handler.
- `c.Next()` вызывается только для валидных запросов и передаёт управление маршруту.

### Пример — валидация query-параметров пагинации

```go
func parsePagination(c *gin.Context) (limit, offset int, err error) {
    limit, err = strconv.Atoi(c.DefaultQuery("limit", "20"))
    if err != nil || limit <= 0 || limit > 100 {
        return 0, 0, fmt.Errorf("limit must be in range 1..100")
    }

    offset, err = strconv.Atoi(c.DefaultQuery("offset", "0"))
    if err != nil || offset < 0 {
        return 0, 0, fmt.Errorf("offset must be >= 0")
    }
    return limit, offset, nil
}
```

Разбор:
- Функция инкапсулирует разбор параметров и убирает дублирование кода по handlers.
- `DefaultQuery` задаёт безопасные значения по умолчанию, если клиент не передал параметры.
- Проверка диапазона `limit` защищает сервис от слишком тяжёлых ответов.
- Проверка `offset < 0` предотвращает некорректные смещения и ошибки логики выборки.
- Возврат `error` позволяет handler явно решить, какой HTTP-код отправить клиенту.
- Такой helper удобно покрыть unit-тестами отдельно от HTTP-слоя.

## Версии REST API

Несколько версий контракта в одном сервисе:

| Подход | Пример | Плюсы |
|--------|--------|-------|
| Prefix в URL | `/v1/notes`, `/v2/notes` | Явно, просто в Gin |
| Header | `Accept: application/vnd.app.v2+json` | Чистый URL |
| Subrouter | `v1 := r.Group("/v1")` | Изоляция middleware |

```go
v1 := r.Group("/v1")
{
    v1.GET("/contacts", listContactsV1)
}
v2 := r.Group("/v2")
{
    v2.GET("/contacts", listContactsV2)
}
```

Разбор:
- Группы Gin задают общий prefix и middleware только для версии.
- Старый клиент продолжает ходить на `/v1`, новый — на `/v2`.
- Breaking changes не ломают существующие интеграции.

## Загрузка и скачивание файлов

Бинарные тела в REST:

```go
func upload(c *gin.Context) {
    file, err := c.FormFile("document")
    if err != nil {
        c.JSON(http.StatusBadRequest, gin.H{"error": "file required"})
        return
    }
    dst := filepath.Join(os.TempDir(), filepath.Base(file.Filename))
    if err := c.SaveUploadedFile(file, dst); err != nil {
        c.JSON(http.StatusInternalServerError, gin.H{"error": "save failed"})
        return
    }
    c.JSON(http.StatusCreated, gin.H{"path": dst})
}

func download(c *gin.Context) {
    c.FileAttachment("/data/report.pdf", "report.pdf")
}
```

Разбор:
- `FormFile` читает `multipart/form-data`; лимит размера задают `MaxMultipartMemory` у Engine.
- `filepath.Base` отсекает `../` в имени файла — базовая защита от path traversal.
- `FileAttachment` выставляет `Content-Disposition: attachment` для скачивания.
