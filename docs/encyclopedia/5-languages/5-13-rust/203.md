## Потоки и синхронные каналы в Rust

**Потоки ОС** (`std::thread`) — отдельные цепочки выполнения с собственным стеком. **Асинхронность** ([отдельная глава](./17.md)) кооперативно мультиплексирует много задач на небольшом пуле потоков. Оба подхода легальны в Rust; компилятор через `Send` и `Sync` не даёт передавать между потоками данные, для которых это небезопасно.

База: [владение и типы](./13.md) · [async](./17.md) · [справочник](./3.md).

---

## Когда потоки, когда async

| Сценарий | Подход |
|----------|--------|
| Много ожидания сети/диска на одном сервисе | `async` + Tokio |
| CPU-bound расчёты на всех ядрах | `std::thread` или **rayon** |
| Фоновая работа из sync-кода (CLI, GUI) | `thread::spawn` |
| Блокирующая библиотека внутри async-сервера | `tokio::task::spawn_blocking` |

Правило: **async не ускоряет CPU** — он снижает стоимость ожидания I/O. Тяжёлую математику выносите в потоки или `rayon`.

## Запуск потока

```rust
use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        thread::sleep(Duration::from_millis(100));
        42
    });

    let answer = handle.join().expect("поток завершился с паникой");
    println!("{answer}");
}
```

`join()` возвращает `Result<T, Box<dyn Any + Send>>` — паника в дочернем потоке превращается в ошибку `join`.

Передача данных в поток — через **move-замыкание**: владение переходит в новый поток.

```rust
let data = vec![1, 2, 3];
thread::spawn(move || {
    println!("{:?}", data);
});
// data здесь уже недоступен
```

## Канал mpsc

`std::sync::mpsc` — очередь «много отправителей — один получатель». Сообщения передают **владение** (`String`, `Vec`, структуры), а не сырые указатели.

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        tx.send("готово".to_string()).unwrap();
    });

    match rx.recv() {
        Ok(msg) => println!("{msg}"),
        Err(_) => println!("отправитель отключился"),
    }
}
```

- `Sender::clone()` — несколько производителей.
- `recv_timeout` — ожидание с таймаутом.
- Итератор `rx.iter()` — блокирующее чтение до закрытия всех `tx`.

Для **неблокирующего** приёма в цикле событий смотрите `try_recv`.

## Разделяемое изменяемое состояние

Каналы хороши, когда владение передаётся целиком. Если нужен общий счётчик или кэш:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..4 {
        let c = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            let mut n = c.lock().unwrap();
            *n += 1;
        }));
    }

    for h in handles {
        h.join().unwrap();
    }
    println!("{}", *counter.lock().unwrap());
}
```

- `Arc` — разделяемое владение между потоками (`Send` + `Sync` для счётчика ссылок).
- `Mutex` — эксклюзивный доступ; `lock()` может вернуть `PoisonError`, если другой поток запаниковал с захваченным мьютексом.

Для **много читателей / один писатель** — `RwLock`. Для атомарных счётчиков без блокировки — `AtomicUsize` и др.

## Send и Sync

| Трейт | Смысл |
|-------|--------|
| `Send` | тип можно **переместить** в другой поток |
| `Sync` | на тип можно брать **ссылки** из нескольких потоков (`&T` — `Send`) |

`Rc<T>` — не `Send` (нет атомарного счётчика). `Arc<Mutex<T>>` — `Send`, если `T: Send`.

Компилятор отклонит код вроде передачи `Rc` в `thread::spawn` — это защита от data races в safe-коде.

## Потоки внутри async (Tokio)

В `async fn` нельзя долго блокировать executor:

```rust
// плохо в async-обработчике
std::thread::sleep(std::time::Duration::from_secs(1));

// лучше
tokio::time::sleep(std::time::Duration::from_secs(1)).await;
```

Блокирующий API (сжатие, синхронный SQLite, старый HTTP-клиент):

```rust
let result = tokio::task::spawn_blocking(|| heavy_sync_work())
    .await
    .expect("join spawn_blocking")?;
```

`spawn_blocking` берёт поток из отдельного пула — основной runtime продолжает обслуживать I/O.

## Типичные ошибки

1. **Дедлок** — два `Mutex` в разном порядке в разных потоках. Решение: единый порядок захвата или каналы вместо взаимных lock.
2. **Удержание lock во время I/O** — другие потоки простаивают. Сужайте критическую секцию: скопируйте данные и отпустите `Mutex` до сетевого вызова.
3. **`std::thread::sleep` в async** — «замораживает» воркер Tokio.
4. **Паника в потоке** — теряется стек, если не обработать `join`; в серверах часто логируют и перезапускают задачу.
