## GUI на Windows — выбор стека

На Windows можно строить интерфейс по-разному: **нативные API** (Win32, WinUI, WinRT), **кроссплатформенные UI на Rust** (Iced, Slint, egui) или **гибрид** (Tauri — WebView + Rust). Учебные циклы сообщений Win32 полезны для понимания ОС, но для новых продуктов чаще выбирают фреймворк с готовой абстракцией.

Обзор экосистемы: [приложения на Rust](./110.md) · [фреймворки](./15.md) · FFI: [практика](./205.md).

---

## Варианты

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| **Win32 / windows-rs** | максимальная интеграция с ОС, нет лишних слоёв | много boilerplate, ручная обработка сообщений |
| **WinUI 3 / WinRT** | современный Fluent, Store | в основном Windows, сложная модель COM |
| **Tauri** | знакомый HTML/CSS, малый размер установки | зависимость от WebView2, политика IPC |
| **Slint / Iced / egui** | UI на Rust, кроссплатформа | свой рендер, меньше «родных» контролов |
| **Dioxus + WebView** | React-подобная модель | молодая экосистема |

## Когда нативный API

Имеет смысл, если нужно:

- встроиться в существующее Win32-приложение или драйвер оболочки;
- вызвать редкий системный API без обёртки;
- минимальный размер и нулевые зависимости от WebView.

Типичная схема: crate **windows** или **windows-sys** для объявлений, тонкий слой `unsafe`, поверх — модули с логикой на safe Rust. Цикл `GetMessage` / `DispatchMessage` остаётся в одном месте; бизнес-логика не смешивается с обработчиками `WM_*`.

Для новичка **не** стоит начинать с ручного Win32 — лучше [первая программа](./20.md) и кроссплатформенный UI, затем при необходимости углубиться в нативный слой.

## Когда Tauri или WebView

- команда уже пишет фронт на React/Vue/Svelte;
- нужен установщик для Windows/macOS/Linux из одной кодовой базы;
- важны автообновления, системные диалоги, ограничение прав (capabilities).

Rust отвечает за файлы, сеть, криптографию; UI в изолированном WebView. Безопасность строится на явном списке разрешённых команд — не давать JS прямой доступ к диску.

---

## Когда Slint, Iced, egui

- интерфейс должен выглядеть одинаково на Linux/macOS/Windows;
- нельзя тянуть Chromium/WebView2;
- встраиваемые панели, HMI, инструменты.

**Slint** — декларативные `.slint`-файлы, компиляция в Rust. **Iced** — Elm-архитектура, OpenGL/WGPU. **egui** — immediate mode, удобен для внутренних утилит и редакторов.

---

## WebView2 на Windows

Tauri и часть обёрток используют **WebView2** (Edge Chromium). На свежих Windows 10/11 runtime часто уже есть; иначе нужен bootstrap установщика. Это компромисс: нативный «хром» без упаковки полного Electron, но зависимость от компонента Microsoft.

---

## Практическая рекомендация

1. **Утилита / прототип** — egui или Iced.
2. **Продукт с веб-командой** — Tauri.
3. **Промышленный HMI** — Slint.
4. **Интеграция в Win32/COM legacy** — windows-rs + FFI из [практики](./205.md).
5. **Магазин Microsoft, Fluent** — WinUI 3 (отдельная траектория, C#/C++ опыт помогает).
