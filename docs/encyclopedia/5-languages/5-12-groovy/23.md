## Gradle Groovy DSL — первая сборка

**Gradle** — система сборки для JVM (и не только): компиляция, тесты, упаковка JAR, запуск приложения. Сценарий описывают в **`build.gradle`** (язык **Groovy**) или **`build.gradle.kts`** (Kotlin).

Android и многие enterprise-репозитории до сих пор используют **Groovy DSL**. Строка `implementation 'group:artifact:version'` внутри `dependencies { }` — это вызов метода, который Gradle добавляет через [делегирование замыканий](./11.md), а не "магический" синтаксис.

Java-аналог на Kotlin DSL: [Gradle — практический старт](/encyclopedia/5-languages/5-03-java/292). Maven: [структура и сборки Java](/encyclopedia/5-languages/5-03-java/12). Тесты Spock: [21.md](./21.md). CI: [Jenkinsfile](./22.md).

### Что получится

Проект `hello-groovy-gradle`: `./gradlew build`, JAR, unit-тест. Понимание блоков `plugins`, `repositories`, `dependencies`, `tasks`.

```bash
./gradlew build
```

Разбор:
- Фрагмент на `bash` показывает рабочий пример: начинается с `./gradlew build` и задает контекст выполнения.
- Ключевые операторы и выражения (`def`, литералы, вызовы) формируют данные, с которыми работает остальная часть примера.
- Основная логика выражена последовательностью инструкций, которые рантайм выполняет сверху вниз.
- Поток выполнения линейный: шаги идут последовательно, поэтому итог зависит от порядка операций в блоке.
- Итог фрагмента — воспроизводимый результат: вывод в консоль, изменение данных или артефакт, который можно сразу проверить.

## Термины

| Термин | Простыми словами |
|--------|------------------|
| **Проект** | Корень с `build.gradle` или подпапка в multi-module |
| **Плагин (`plugin`)** | Набор готовых задач (java, application) |
| **Задача (`task`)** | Единица работы: `compileJava`, `test`, `build` |
| **Конфигурация** | `implementation`, `testImplementation` — "роль" зависимости |
| **Wrapper (`gradlew`)** | Скрипт, который скачивает фиксированную версию Gradle |
| **Maven Central** | Публичный репозиторий JAR-файлов |
| **Toolchain** | Gradle сам подберёт JDK нужной версии |

## Groovy DSL и Kotlin DSL

| Groovy `build.gradle` | Kotlin `build.gradle.kts` |
|-----------------------|---------------------------|
| Исторически в Android | Новые модули часто на KTS |
| Больше примеров в сети | Строже подсказки IDE |
| Один и тот же Gradle "под капотом" | Один и тот же Gradle |

Логика одинакова; меняется только синтаксис файла.

## Создание проекта

```bash
mkdir hello-groovy-gradle && cd hello-groovy-gradle
gradle init
```

Разбор:
- `mkdir ... && cd ...` — создаёт каталог проекта и переходит в него (одна строка в shell).
- `gradle init` — мастер Gradle: предложит тип проекта (application), язык (Java), DSL скрипта (Groovy).
- После мастера появятся `build.gradle`, `settings.gradle`, wrapper — их коммитят в Git.
- Глобальный `gradle` нужен только для `init`; дальше команда — `./gradlew`.
- Без wrapper коллеги и CI получат другую версию Gradle и «плавающие» сборки.

### Таблица блоков

| Блок | Назначение |
|------|------------|
| `plugins { id 'java' }` | Задачи компиляции, тестов, JAR |
| `plugins { id 'application' }` | Задача `run` с точкой входа |
| `group` / `version` | Координаты артефакта (Maven-style) |
| `repositories { mavenCentral() }` | Откуда скачивать зависимости |
| `dependencies { ... }` | Список библиотек по конфигурациям |
| `application { mainClass = ... }` | Класс с `public static void main` |
| `java { toolchain { ... } }` | Сборка под JDK 17 без ручного JAVA_HOME |
| `tasks.named('test') { useJUnitPlatform() }` | JUnit 5 вместо устаревшего JUnit 4 |

---

### Конфигурации зависимостей

| Конфигурация | Куда попадает JAR |
|--------------|-------------------|
| `implementation` | Только ваш модуль при компиляции и runtime |
| `testImplementation` | Только тесты (`src/test`) |
| `api` (в библиотеках) | Пробрасывается потребителям модуля |

**Правило для новичка:** production-код → `implementation`, тестовые библиотеки (JUnit, Spock) → `testImplementation`.

Строка `'org.apache.groovy:groovy:4.0.21'` — **координата Maven**: `group:artifact:version`.

Почему `implementation '...'` работает внутри `{ }` — см. [делегирование DSL](./11.md).

## Реальный workflow команды с Gradle

Типичный ежедневный цикл:

1. Локально запускаем `./gradlew test`.
2. Перед пушем делаем `./gradlew build`.
3. В CI повторяем тот же wrapper-командой.
4. Для релиза добавляем версионирование и публикацию.

```bash
./gradlew clean test build
```

Разбор:
- Фрагмент на `bash` показывает рабочий пример: начинается с `./gradlew clean test build` и задает контекст выполнения.
- Ключевые операторы и выражения (`def`, литералы, вызовы) формируют данные, с которыми работает остальная часть примера.
- Основная логика выражена последовательностью инструкций, которые рантайм выполняет сверху вниз.

## Производительность сборки

Для ускорения больших проектов применяют:

- `org.gradle.caching=true` в `gradle.properties`;
- `org.gradle.parallel=true` для независимых модулей;
- remote build cache в CI;
- разделение модулей, чтобы изменения в одном модуле не пересобирали все дерево.

```properties
org.gradle.caching=true
org.gradle.parallel=true
```

Разбор:
- Фрагмент на `properties` показывает рабочий пример: начинается с `org.gradle.caching=true` и задает контекст выполнения.
- Ключевые операторы и выражения (`def`, литералы, вызовы) формируют данные, с которыми работает остальная часть примера.
- Основная логика выражена последовательностью инструкций, которые рантайм выполняет сверху вниз.
- Поток выполнения линейный: шаги идут последовательно, поэтому итог зависит от порядка операций в блоке.
- Итог фрагмента — воспроизводимый результат: вывод в консоль, изменение данных или артефакт, который можно сразу проверить.


Оптимизацию проверяют через build scan и время критичных задач (`compileJava`, `test`).

## Мини-памятка по качеству build.gradle

- Плагины и версии вынесены в единый каталог версий или convention plugins.
- Зависимости группируются по назначению.
- Кастомные задачи имеют `group` и `description`.
- Wrapper хранится в репозитории и обновляется осознанно.
