## Groovy и Java — совместимость и отличия

Groovy компилируется в байт-код JVM и использует те же классы из JDK и Maven-зависимостей. На практике его часто описывают как "Java с синтаксическим сахаром", но это упрощение: есть отличия, которые ломают ожидания при переносе кода и при вызове из Java.

---

## Что обычно работает без изменений

Большая часть **валидного Java 8+** кода компилируется `groovyc` как Groovy:

- объявления классов, интерфейсов, enum (с оговорками по новым фичам Java);
- поля, методы, наследование, generics в исходниках;
- вызовы JDK (`java.util`, `java.time`, NIO, JDBC и т.д.);
- аннотации Java и многие библиотеки Spring, Hibernate, JUnit.

```groovy
// Фрагмент "чистой" Java внутри .groovy-файла

import java.util.stream.Collectors

List<String> names = List.of("a", "b", "c")
List<String> upper = names.stream()
    .map(String::toUpperCase)
    .collect(Collectors.toList())
```

Разбор:
- Фрагмент на `groovy` показывает рабочий пример: начинается с `// Фрагмент "чистой" Java внутри .groovy-файла` и задает контекст выполнения.
- Строки `import` подключают нужные классы и модули, чтобы дальше вызывать API без полного имени пакета.
- Вызовы функций или команд выполняют полезное действие: чтение данных, вычисление результата или запуск задачи сборки.
- Поток выполнения строится на итерации: код последовательно применяет одну и ту же операцию к набору значений.
- Итог фрагмента — воспроизводимый результат — вывод в консоль, изменение данных или артефакт, который можно сразу проверить.


Обратное направление: **Java-класс вызывается из Groovy** напрямую, без обёрток.

## Главные отличия (ловушки при переходе)

| Тема | Java | Groovy |
|------|------|--------|
| `==` | Сравнение ссылок (для объектов) | Вызов `equals()` |
| Идентичность | `==` для примитивов | `is()` или `===` (версия Groovy) |
| Деление int | `5 / 2` → `2` | `5 / 2` → `2.5` |
| Строки | Только `String` | `String` и **GString** (`"Hi $name"`) |
| Тип переменной | Обязателен (кроме `var` с Java 10+) | `def` — вывод типа |
| Итерация | `for`, Stream | `for (x in list)`, `each`, `collect` |
| Проверка "пусто" | Явные сравнения | Truthiness: `if (list)` |
| Исключения | Проверяемые `throws` | Не проверяются компилятором Groovy |
| Скрипт | Нужен `class` + `main` | Топ-уровневые выражения в `.groovy` |

### GString и сравнение

```groovy
def plain = 'Hello'
def gstr = "Hello"
assert plain == gstr    // true — equals по содержимому
assert !plain.is(gstr)  // false — разные классы
```

Разбор:
- `plain` — обычный `java.lang.String` из одинарных кавычек.
- `gstr` — объект **GString** из двойных кавычек без подстановки (содержимое то же, класс другой).
- `plain == gstr` в Groovy вызывает `equals()` по содержимому → `true` (в Java `==` сравнил бы ссылки).
- `plain.is(gstr)` — проверка **идентичности** объектов (тот же класс и ссылка) → `false`.
- В `HashMap`/`HashSet` ключи-GString и ключи-String ведут себя по-разному — в API лучше нормализовать к `String`.

В Java `==` для двух `new String("Hello")` дало бы `false` (ссылки).

Сравнение деления — ещё одна ловушка при переносе с Java:

```groovy
println 5 / 2      // 2.5 в Groovy
println (int)(5/2) // 2 — явное приведение, если нужен int
```

Разбор:
- В Groovy оператор `/` для целых даёт `BigDecimal` или `double` (здесь `2.5`), а не целочисленное деление Java.
- В Java `5 / 2` при `int` операндах даёт `2`.
- `(int)(5/2)` принудительно отбрасывает дробную часть после деления в Groovy.
- В финансовых расчётах часто используют `5.intdiv(2)` или `BigDecimal` для явной семантики.

### Операторы, которых нет в Java

- `?.` — безопасная навигация;
- `?:` — Elvis (значение по умолчанию для "ложного" операнда);
- `*.method()` — spread по коллекции;
- `in` / `!in` — принадлежность;
- `=~` / `==~` — регулярные выражения;
- `..` / `..<` — диапазоны.

```groovy
def user = [profile: [city: 'Berlin']]
println user?.profile?.city          // Berlin
println user?.profile?.country ?: 'N/A'  // N/A

assert 3 in [1, 2, 3]
assert (1..3) == [1, 2, 3]
assert (1..<3) == [1, 2]             // верхняя граница не включена
```

Разбор:
- `?.` — если слева `null`, цепочка обрывается и выражение даёт `null`, без `NullPointerException`.
- `?:` после `country` подставляет `'N/A'`, потому что `country` отсутствует (доступ к полю даёт `null`).
- `in` проверяет вхождение элемента в коллекцию или диапазон.
- `1..3` — диапазон включительно; `1..<3` — до 3, не включая 3 (аналог `range(1, 3)` в Python).
- В Java для тех же задач писали бы явные `if (x != null)` и циклы.

## Вызов Groovy из Java

**Работает предсказуемо**, если Groovy-класс ведёт себя как обычный JavaBeans-класс:

- явные типы в публичных методах;
- без опоры на `methodMissing` / динамические свойства в API, видимом Java;
- рантайм Groovy (`groovy-*.jar`) в classpath при необходимости.

```java
// Java
Person person = new Person("Alice", 30);
System.out.println(person.getName());
```

Разбор:
- Фрагмент на `java` показывает рабочий пример: начинается с `// Java` и задает контекст выполнения.
- Ключевые операторы и выражения (`def`, литералы, вызовы) формируют данные, с которыми работает остальная часть примера.
- Вызовы функций или команд выполняют полезное действие: чтение данных, вычисление результата или запуск задачи сборки.
- Поток выполнения линейный: шаги идут последовательно, поэтому итог зависит от порядка операций в блоке.
- Итог фрагмента — воспроизводимый результат — вывод в консоль, изменение данных или артефакт, который можно сразу проверить.


```groovy
// Groovy — компилируется в .class с getName()/setName()
class Person {
    String name
    int age
    Person(String name, int age) {
        this.name = name
        this.age = age
    }
}
```

Разбор:
- Фрагмент на `groovy` показывает рабочий пример: начинается с `// Groovy — компилируется в .class с getName()/setName()` и задает контекст выполнения.
- Конструкция `class` описывает структуру объекта: поля хранят состояние, а методы инкапсулируют поведение.
- Вызовы функций или команд выполняют полезное действие: чтение данных, вычисление результата или запуск задачи сборки.
- Поток выполнения линейный: шаги идут последовательно, поэтому итог зависит от порядка операций в блоке.
- Итог фрагмента — воспроизводимый результат — вывод в консоль, изменение данных или артефакт, который можно сразу проверить.


**Сложнее из Java:**

- скрипты без класса (нужен `GroovyShell` / `GroovyClassLoader`);
- DSL с `methodMissing`, категории, глобальный `metaClass`;
- методы только с `def` в сигнатуре на границе API.

Для публичного API библиотек предпочтительны **явные типы** и **`@CompileStatic`** на границе модулей.

## Динамика и статика в одном проекте

| Режим | Когда | Поведение |
|-------|--------|-----------|
| По умолчанию | Скрипты, Gradle, Spock | MetaClass, позднее связывание |
| `@TypeChecked` | Поиск ошибок типов | Проверка при компиляции, вызовы могут оставаться динамическими |
| `@CompileStatic` | Ядро, hot path | Вызовы как в Java, меньше рантайма Groovy |

Типичная схема в enterprise — **Java или `@CompileStatic` Groovy** для домена, **динамический Groovy** для сборки, пайплайнов и тестовых спецификаций.

## Что не стоит утверждать в документации и на собеседованиях

- "Любой Java-код — валидный Groovy" — неверно для edge cases и новых конструкций только в Java.
- "100% бинарная совместимость" — на практике совместимость высокая, но динамические фичи и различия операторов требуют внимания.
- "Groovy заменил Java в вебе" — Grails уступил долю Spring Boot; Groovy остался в инфраструктуре.

## Стратегия миграции Java-проекта к Groovy

Безопасный маршрут обычно выглядит так:

1. Оставить production-код на Java.
2. Добавить Spock-тесты на Groovy в `src/test/groovy`.
3. Вынести инфраструктурные скрипты в Groovy (Gradle tasks, CI, миграции).
4. Переводить отдельные модули на Groovy с `@CompileStatic` и явными сигнатурами.

Такой порядок снижает риск изменений на критичном пути и дает команде время освоить язык.

## Чек-лист совместимости для API

Перед публикацией Groovy-модуля для Java-потребителей проверьте:

- сигнатуры публичных методов с явными типами;
- отсутствие зависимости публичного API от `methodMissing` и `metaClass`;
- корректный `equals`/`hashCode` у объектов, которые участвуют в коллекциях;
- единые версии `groovy-*` артефактов во всем проекте.

```groovy

import groovy.transform.CompileStatic

@CompileStatic
class UserApi {
    String formatName(String name) {
        name?.trim()?.toUpperCase()
    }
}
```

Разбор:
- Фрагмент на `groovy` показывает рабочий пример: начинается с `import groovy.transform.CompileStatic` и задает контекст выполнения.
- Строки `import` подключают нужные классы и модули, чтобы дальше вызывать API без полного имени пакета.
- Вызовы функций или команд выполняют полезное действие: чтение данных, вычисление результата или запуск задачи сборки.
- Поток выполнения линейный: шаги идут последовательно, поэтому итог зависит от порядка операций в блоке.
- Итог фрагмента — воспроизводимый результат — вывод в консоль, изменение данных или артефакт, который можно сразу проверить.


С таким контрактом Java-клиент работает с классом предсказуемо, как с обычным JVM-классом.
