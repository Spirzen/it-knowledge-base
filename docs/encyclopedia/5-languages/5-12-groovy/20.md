**Java** и **Groovy** — два языка для одной платформы [JVM](/encyclopedia/4-code-dev/4-03-vypolnenie-koda/314) (Java Virtual Machine, виртуальная машина Java). Исходник компилируется в [байт-код](/encyclopedia/4-code-dev/4-02-chto-takoe-kod-i-kak-on-rabotaet/1) (промежуточные инструкции для JVM), после чего программа запускается в одном процессе с общим **classpath** (список подключённых библиотек и `.class`-файлов).

- **Java** — основной язык крупных серверных систем. [Статическая типизация](/encyclopedia/1-basics/1-09-dannye-i-informatsiya/4) фиксирует тип переменной при написании кода; компилятор и IDE подсвечивают многие ошибки до запуска. Подробнее — [Java — о разделе](/encyclopedia/5-languages/5-03-java/intro).
- **Groovy** — язык на той же JVM с коротким синтаксисом и [динамической типизацией](/encyclopedia/1-basics/1-09-dannye-i-informatsiya/4) по умолчанию (тип может уточняться во время выполнения). На нём пишут [скрипты Gradle](./23.md), [пайплайны Jenkins](./22.md) и [тесты Spock](./21.md).

Большая часть корректного Java-кода компилируется компилятором `groovyc` без правок. При этом операторы (`==`, деление целых), строки (**GString**) и выбор перегруженного метода работают иначе, чем в Java. Обзор отличий — ниже; пошаговые ловушки при переносе кода — в разделе [Ловушки при переходе с Java](#ловушки-при-переходе-с-java).

> **Сначала:** [типизация](/encyclopedia/1-basics/1-09-dannye-i-informatsiya/4) и [выполнение кода на JVM](/encyclopedia/4-code-dev/4-03-vypolnenie-koda/314). Если Java ещё не знакома — [первая программа на Java](/encyclopedia/5-languages/5-03-java/13).

## Как связаны Java и Groovy

```text
  Исходник .java              Исходник .groovy
         │                            │
         ▼                            ▼
  ┌─────────────┐              ┌─────────────┐
  │  javac      │              │  groovyc    │
  └──────┬──────┘              └──────┬──────┘
         │                            │
         └──────────┬─────────────────┘
                    ▼
            Байт-код JVM (.class)
                    │
                    ▼
         ┌──────────────────────┐
         │  HotSpot / OpenJDK   │  ← JIT, GC, один classpath
         └──────────────────────┘
```

**javac** компилирует `.java`, **groovyc** — `.groovy`; дальше оба файла выглядят для JVM одинаково. Библиотеки из [Maven](/encyclopedia/5-languages/5-03-java/292) или Gradle подключаются к обоим языкам через один classpath.

| Утверждение | Верно? | Пояснение |
|-------------|--------|-----------|
| Groovy заменил Java в корпоративном вебе | Нет | Ядро сервисов обычно на [Java](/encyclopedia/5-languages/5-03-java/271) или [Kotlin](/encyclopedia/5-languages/5-09-kotlin/intro); Groovy чаще в сборке, CI и тестах |
| Любой Java-файл компилируется как Groovy | Почти | Редкие конструкции только в новых версиях Java и граничные случаи могут потребовать правок |
| Java вызывает Groovy-класс напрямую | Да | Если у класса обычные публичные методы с явными типами (см. [Вызов Groovy из Java](#вызов-groovy-из-java)) |
| Groovy всегда медленнее Java | Часто | В динамическом режиме да; с [`@CompileStatic`](./16.md) разрыв заметно сокращается |
| Для QA Automation и DevOps нужны оба | Часто | Java/Kotlin — код приложения; Groovy — [Gradle](./23.md), [Jenkins](./22.md), [Spock](./21.md) |

История появления Groovy и его роль на JVM — [История языка](./1.md).

## Главные различия

| Тема | Java | Groovy |
|------|------|--------|
| **Типизация** | [Статическая](/encyclopedia/1-basics/1-09-dannye-i-informatsiya/4). Тип у `String name` обязателен (кроме `var` с Java 10+) | [Динамическая](./12.md) по умолчанию через `def`; ужесточение — `@TypeChecked`, `@CompileStatic` |
| **Синтаксис** | Явные типы, точка с запятой, `return`, геттеры и сеттеры | [Свойства](./15.md), [замыкания](./11.md), интерполяция строк, меньше шаблонного кода |
| **Диспетчеризация** | Перегрузка метода выбирается при **компиляции** | **Мультиметоды** — финальный метод определяется в **runtime** по реальным типам аргументов |
| **Производительность** | Ориентир для JVM-бэкенда за счёт JIT и статики | В динамике медленнее; для горячих участков — `@CompileStatic` или модуль на Java |
| **Метапрограммирование** | [Рефлексия](/encyclopedia/5-languages/5-03-java/299), аннотации, байткод-агенты | [MetaClass](./11.md), категории, `methodMissing` — поведение класса можно менять во время выполнения |
| **Скрипты** | Класс с `public static void main` | Топ-уровневые выражения в `.groovy`, запуск через `groovy script.groovy` — [первая программа](./2.md) |

**Мультиметод** проще всего понять на примере. В Java компилятор заранее выбирает одну из перегруженных версий `print(int)` или `print(String)`. В Groovy при вызове `print(x)` финальный метод зависит от фактического типа `x` в момент выполнения — результат может отличаться от Java-кода с тем же именем метода.

## Пример на Java и Groovy

Задача — из JSON со списком пользователей вернуть имена только активных записей.

### Java

```java
import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import java.util.ArrayList;
import java.util.List;

public class UserFilter {
    private final ObjectMapper mapper = new ObjectMapper();

    public List<String> activeNames(String json) throws Exception {
        JsonNode root = mapper.readTree(json);
        List<String> result = new ArrayList<>();
        for (JsonNode user : root.get("users")) {
            if (user.get("active").asBoolean()) {
                result.add(user.get("name").asText());
            }
        }
        return result;
    }
}
```

### Groovy

```groovy
import groovy.json.JsonSlurper

class UserFilter {
    List<String> activeNames(String json) {
        def data = new JsonSlurper().parseText(json)
        data.users.findAll { it.active }.collect { it.name }
    }
}
```

Разбор:

- В Java подключают библиотеку [Jackson](https://github.com/FasterXML/jackson), объявляют типы, обходят узлы дерева в цикле `for`.
- В Groovy `JsonSlurper` разбирает JSON в [Map/List](./12.md); `findAll` и `collect` — методы GDK для фильтрации и преобразования коллекции.
- Ключевое слово `def` оставляет тип переменной на усмотрение компилятора Groovy (см. [типы](./12.md)).
- Замыкание `{ it.active }` — функция "оставить элемент, если `active` истинно"; `it` — имя текущего элемента по умолчанию.
- Оба класса компилируются в `.class` и могут лежать в одном Gradle/Maven-модуле.
- В production-сервисе такую логику чаще пишут на Java или с `@CompileStatic`; в тесте или утилите — на Groovy.

Оператор `==` и строки GString — в [таблице ловушек](#ловушки-при-переходе-с-java) и в статье [операторы](./13.md).

## Плюсы и минусы Java

### Плюсы

- **Экосистема**
  - [Maven Central](https://central.sonatype.com/), [Spring Boot](/encyclopedia/5-languages/5-03-java/271), Hibernate
  - [IntelliJ IDEA](/encyclopedia/5-languages/5-03-java/103), профилирование, APM-инструменты
- **Скорость выполнения**
  - JIT в HotSpot, [virtual threads](/encyclopedia/5-languages/5-03-java/308) (Java 21+)
  - Нет накладных расходов динамического runtime Groovy в чистом Java-коде
- **Рефакторинг**
  - Строгие типы и статический анализ
  - Переименование поля или метода подсвечивает все затронутые файлы в IDE
- **Рынок труда**
  - Большинство JVM-вакансий и legacy-кодовых баз на Java

### Минусы

- **Boilerplate**
  - Геттеры, билдеры, длинные цепочки Stream для простых преобразований
- **Быстрый одноразовый скрипт**
  - Нужны класс, `main`, сборка; дольше, чем `groovy script.groovy` — [первая программа Groovy](./2.md)
- **Конфигурация и пайплайны**
  - Выразительный build-скрипт на "чистой" Java получается громоздким; для DSL обычно берут Groovy или Kotlin

## Плюсы и минусы Groovy

### Плюсы

- **Короткий синтаксис**
  - [Свойства](./15.md) вместо пары get/set
  - Интерполяция `"Hello, $name"`
  - Операторы `?.` (безопасный доступ) и `?:` (значение по умолчанию) — [операторы](./13.md)
- **Коллекции и форматы**
  - GDK: `each`, `findAll`, `collect`
  - `JsonSlurper`, `XmlSlurper`
  - Литералы `[1, 2, 3]` и `[key: 'value']`
- **DSL**
  - [Делегирование замыканий](./11.md) лежит в основе синтаксиса `build.gradle`
- **Тесты**
  - [Spock](./21.md) — блоки `given` / `when` / `then`, читаемые спецификации

### Минусы

- **Отладка динамики**
  - `methodMissing`, категории, неявный `def` — стек вызовов менее очевиден, чем у явных Java-типов
- **Производительность**
  - Плотные CPU-циклы в чистом динамическом Groovy уступают Java
  - Для горячего участка — [`@CompileStatic`](./16.md) или вынос в Java-модуль
- **Две модели в одном проекте**
  - Привычки из Java (`==`, деление `5 / 2`, ключи GString в `HashMap`) дают тихие расхождения — см. [ловушки](#ловушки-при-переходе-с-java)

## Где применяют Java и Groovy

| Сфера | Java | Groovy |
|-------|------|--------|
| Микросервисы, банки, ERP | [Spring](/encyclopedia/5-languages/5-03-java/271), долгоживущие сервисы | Редко в ядре; иногда legacy [Grails](./18.md) |
| Android | [Kotlin](/encyclopedia/5-languages/5-09-kotlin/intro) / Java | Не используется |
| `build.gradle`, свои Gradle-задачи | Вызовы из DSL | Язык DSL — [Gradle Groovy](./23.md) |
| Jenkins Pipeline, Job DSL | — | [Jenkins Pipeline](./22.md), [Job DSL](./25.md) |
| Интеграционные тесты к Java-коду | JUnit | [Spock](./21.md) |
| Одноразовые JVM-скрипты | Возможно, но многословно | `groovy script.groovy` — [первая программа](./2.md) |

**Java** — фундамент крупных корпоративных систем, финансовых платформ и высоконагруженных [бэкенд](/encyclopedia/4-code-dev/4-17-veb-razrabotka/intro)-сервисов.

**Groovy** — автоматизация на JVM:

- скрипты сборки;
- пайплайны [CI/CD](/encyclopedia/8-infra-security/8-04-devops-ci-cd/intro);
- тестовые спецификации;
- внутренние DSL команд.

### Критерии выбора

**Java** подходит, если вы пишете:

- долгоживущий backend;
- публичное API библиотеки;
- модуль, чувствительный к производительности;
- мобильное приложение на Android.

**Groovy** стоит подключать, если нужно:

- читать и править `build.gradle`;
- поддерживать `Jenkinsfile`;
- писать [Spock](./21.md)-тесты;
- быстро собрать JVM-скрипт без церемонии с `main`.

В **QA Automation** и **DevOps** на JVM-стеке языки дополняют друг друга. Java (или Kotlin) описывает приложение; Groovy обслуживает сборку, пайплайн и тестовую обвязку. Ядро крупного веб-сервиса обычно остаётся на Java или Kotlin — [Kotlin и Java](/encyclopedia/5-languages/5-09-kotlin/10.md).

| Миф | Как на самом деле |
|-----|-------------------|

| "Groovy умер после Grails" | [Grails](./18.md) сузил долю; Groovy остаётся в Gradle, Jenkins и Spock |

## Совместимость на уровне кода

Groovy компилируется в байт-код JVM и подключает те же классы JDK и Maven-зависимостей, что и Java. В этом блоке — что переносится без правок, где синтаксис расходится и как вызывать Groovy из Java.

## Что обычно работает без изменений

Большая часть **валидного Java 8+** кода компилируется `groovyc` как Groovy:

- объявления классов, интерфейсов, enum (с оговорками по новым фичам Java);
- поля, методы, наследование, generics в исходниках;
- вызовы JDK (`java.util`, `java.time`, NIO, JDBC и т.д.);
- аннотации Java и многие библиотеки Spring, Hibernate, JUnit.

```groovy
// Фрагмент "чистой" Java внутри .groovy-файла

import java.util.stream.Collectors

List<String> names = List.of("a", "b", "c")
List<String> upper = names.stream()
    .map(String::toUpperCase)
    .collect(Collectors.toList())
```

Разбор:
- Фрагмент на `groovy` показывает рабочий пример: начинается с `// Фрагмент "чистой" Java внутри .groovy-файла` и задает контекст выполнения.
- Строки `import` подключают нужные классы и модули, чтобы дальше вызывать API без полного имени пакета.
- Вызовы функций или команд выполняют полезное действие: чтение данных, вычисление результата или запуск задачи сборки.
- Поток выполнения строится на итерации: код последовательно применяет одну и ту же операцию к набору значений.
- Итог фрагмента — воспроизводимый результат — вывод в консоль, изменение данных или артефакт, который можно сразу проверить.


Обратный вызов тоже простой. **Java-класс вызывается из Groovy** напрямую, без обёрток — см. [история и интероп с Java](./1.md).

## Ловушки при переходе с Java

| Тема | Java | Groovy |
|------|------|--------|
| `==` | Сравнение ссылок (для объектов) | Вызов `equals()` |
| Идентичность | `==` для примитивов | `is()` или `===` (версия Groovy) |
| Деление int | `5 / 2` → `2` | `5 / 2` → `2.5` |
| Строки | Только `String` | `String` и **GString** (`"Hi $name"`) |
| Тип переменной | Обязателен (кроме `var` с Java 10+) | `def` — вывод типа |
| Итерация | `for`, Stream | `for (x in list)`, `each`, `collect` |
| Проверка "пусто" | Явные сравнения (`list.isEmpty()`) | Truthiness — `if (list)` считает пустую коллекцию ложной |
| Исключения | Проверяемые `throws` | Не проверяются компилятором Groovy |
| Скрипт | Нужен `class` + `main` | Топ-уровневые выражения в `.groovy` |

---

### GString и оператор равенства

В Java `==` для объектов сравнивает **ссылки** (один и тот же объект в памяти). В Groovy `==` вызывает `equals()` и сравнивает **содержимое**. Для проверки идентичности ссылок в Groovy используют `is()` или `===` (зависит от версии).

```groovy
def plain = 'Hello'
def gstr = "Hello"
assert plain == gstr    // true — equals по содержимому
assert !plain.is(gstr)  // false — разные классы
```

Разбор:
- `plain` — обычный `java.lang.String` из одинарных кавычек.
- `gstr` — объект **GString** из двойных кавычек без подстановки (содержимое то же, класс другой).
- `plain == gstr` в Groovy вызывает `equals()` по содержимому → `true` (в Java `==` сравнил бы ссылки).
- `plain.is(gstr)` — проверка **идентичности** объектов (тот же класс и ссылка) → `false`.
- В `HashMap`/`HashSet` ключи-GString и ключи-String ведут себя по-разному — в API лучше нормализовать к `String`.

В Java `==` для двух `new String("Hello")` дало бы `false` (ссылки).

Сравнение деления — ещё одна ловушка при переносе с Java:

```groovy
println 5 / 2      // 2.5 в Groovy
println (int)(5/2) // 2 — явное приведение, если нужен int
```

Разбор:
- В Groovy оператор `/` для целых даёт `BigDecimal` или `double` (здесь `2.5`). В Java при `int` операндах результат тоже целый (`2`).
- `(int)(5/2)` принудительно отбрасывает дробную часть после деления в Groovy.
- В финансовых расчётах часто используют `5.intdiv(2)` или `BigDecimal` для явной семантики.

### Операторы, которых нет в Java

- `?.` — безопасная навигация по цепочке свойств
- `?:` — Elvis, подстановка значения по умолчанию для "ложного" операнда
- `*.method()` — spread, вызов метода у каждого элемента коллекции
- `in` / `!in` — проверка вхождения в коллекцию или диапазон
- `=~` / `==~` — сопоставление с регулярным выражением
- `..` / `..<` — диапазоны значений

Подробнее — [операторы Groovy](./13.md).

```groovy
def user = [profile: [city: 'Berlin']]
println user?.profile?.city          // Berlin
println user?.profile?.country ?: 'N/A'  // N/A

assert 3 in [1, 2, 3]
assert (1..3) == [1, 2, 3]
assert (1..<3) == [1, 2]             // верхняя граница не включена
```

Разбор:
- `?.` — если слева `null`, цепочка обрывается и выражение даёт `null`, без `NullPointerException`.
- `?:` после `country` подставляет `'N/A'`, потому что `country` отсутствует (доступ к полю даёт `null`).
- `in` проверяет вхождение элемента в коллекцию или диапазон.
- `1..3` — диапазон включительно; `1..<3` — до 3, не включая 3 (аналог `range(1, 3)` в Python).
- В Java для тех же задач писали бы явные `if (x != null)` и циклы.

## Вызов Groovy из Java

**Работает предсказуемо**, если Groovy-класс ведёт себя как обычный JavaBeans-класс:

- явные типы в публичных методах;
- без опоры на `methodMissing` / динамические свойства в API, видимом Java;
- рантайм Groovy (`groovy-*.jar`) в classpath при необходимости.

```java
// Java
Person person = new Person("Alice", 30);
System.out.println(person.getName());
```

Разбор:
- Фрагмент на `java` показывает рабочий пример: начинается с `// Java` и задает контекст выполнения.
- Ключевые операторы и выражения (`def`, литералы, вызовы) формируют данные, с которыми работает остальная часть примера.
- Вызовы функций или команд выполняют полезное действие: чтение данных, вычисление результата или запуск задачи сборки.
- Поток выполнения линейный: шаги идут последовательно, поэтому итог зависит от порядка операций в блоке.
- Итог фрагмента — воспроизводимый результат — вывод в консоль, изменение данных или артефакт, который можно сразу проверить.


```groovy
// Groovy — компилируется в .class с getName()/setName()
class Person {
    String name
    int age
    Person(String name, int age) {
        this.name = name
        this.age = age
    }
}
```

Разбор:
- Фрагмент на `groovy` показывает рабочий пример: начинается с `// Groovy — компилируется в .class с getName()/setName()` и задает контекст выполнения.
- Конструкция `class` описывает структуру объекта: поля хранят состояние, а методы инкапсулируют поведение.
- Вызовы функций или команд выполняют полезное действие: чтение данных, вычисление результата или запуск задачи сборки.
- Поток выполнения линейный: шаги идут последовательно, поэтому итог зависит от порядка операций в блоке.
- Итог фрагмента — воспроизводимый результат — вывод в консоль, изменение данных или артефакт, который можно сразу проверить.


**Из Java сложнее вызвать**

- скрипт без класса (нужен `GroovyShell` / `GroovyClassLoader`);
- DSL с `methodMissing`, категории, глобальный `metaClass`;
- методы только с `def` в сигнатуре на границе API.

Для публичного API библиотек указывают **явные типы** и **`@CompileStatic`** на границе модулей — [рекомендации](./101.md).

## Динамика и статика в одном проекте

| Режим | Когда применяют | Поведение |
|-------|-----------------|-----------|
| По умолчанию | Скрипты, Gradle, Spock | [MetaClass](./11.md), позднее связывание методов |
| `@TypeChecked` | Нужна проверка типов при компиляции | Ошибки типов до запуска; вызовы могут оставаться динамическими |
| `@CompileStatic` | Ядро сервиса, горячий участок кода | Вызовы как в Java, меньше runtime Groovy — [особенности](./16.md) |

Типичное разделение в enterprise-проекте:

- доменная логика — Java или Groovy с `@CompileStatic`;
- сборка, пайплайны и тестовые спецификации — динамический Groovy.

## Неточные формулировки

На собеседованиях и в документации иногда звучат упрощения. Более точные версии:

| Формулировка | Уточнение |
|--------------|-----------|
| "Любой Java-код — валидный Groovy" | Верно для большинства файлов; граничные случаи и новые конструкции только в Java требуют проверки |
| "100% бинарная совместимость" | Classpath и байт-код общие; операторы и динамика Groovy добавляют свои правила |
| "Groovy заменил Java в вебе" | [Grails](./18.md) уступил долю [Spring Boot](/encyclopedia/5-languages/5-03-java/271); Groovy остался в инфраструктуре |

## Стратегия миграции Java-проекта к Groovy

Безопасный маршрут обычно выглядит так:

1. Оставить production-код на Java.
2. Добавить Spock-тесты на Groovy в `src/test/groovy`.
3. Вынести инфраструктурные скрипты в Groovy (Gradle tasks, CI, миграции).
4. Переводить отдельные модули на Groovy с `@CompileStatic` и явными сигнатурами.

Такой порядок снижает риск изменений на критичном пути и дает команде время освоить язык.

## Чек-лист совместимости для API

Перед публикацией Groovy-модуля для Java-потребителей проверьте:

- сигнатуры публичных методов с явными типами;
- отсутствие зависимости публичного API от `methodMissing` и `metaClass`;
- корректный `equals`/`hashCode` у объектов, которые участвуют в коллекциях;
- единые версии `groovy-*` артефактов во всем проекте.

```groovy

import groovy.transform.CompileStatic

@CompileStatic
class UserApi {
    String formatName(String name) {
        name?.trim()?.toUpperCase()
    }
}
```

Разбор:
- Фрагмент на `groovy` показывает рабочий пример: начинается с `import groovy.transform.CompileStatic` и задает контекст выполнения.
- Строки `import` подключают нужные классы и модули, чтобы дальше вызывать API без полного имени пакета.
- Вызовы функций или команд выполняют полезное действие: чтение данных, вычисление результата или запуск задачи сборки.
- Поток выполнения линейный: шаги идут последовательно, поэтому итог зависит от порядка операций в блоке.
- Итог фрагмента — воспроизводимый результат — вывод в консоль, изменение данных или артефакт, который можно сразу проверить.


С таким контрактом Java-клиент работает с классом предсказуемо, как с обычным JVM-классом.
