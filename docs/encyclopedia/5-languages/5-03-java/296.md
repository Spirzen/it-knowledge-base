## Строки в Java

★ **Строка** в Java — объект класса `java.lang.String`. Литерал `"текст"` создаёт объект в пуле строк (string pool) для экономии памяти при повторном использовании одинаковых литералов.

См. также: [типы данных](./15.md), [ввод-вывод и кодировки](./297.md).

---

### Неизменяемость (immutability)

После создания содержимое `String` не меняется. "Изменение" создаёт **новый** объект:

```java
String s = "hello";
s = s + " world";   // новая строка, старая доступна сборщику мусора
```

Разбор:
- фрагмент показывает прикладной сценарий по теме раздела: здесь есть входные данные, операции над ними и проверяемый итог.
- чтение этого блока по шагам дает предсказуемую картину — сначала подготовка данных, затем действие API, затем получение конечного значения.
- после запуска стоит проверить именно эффект этого примера — вывод, значение переменной, статус ответа, состояние БД или результат теста.
- при переносе в production обычно добавляют валидацию входа, явную обработку ошибок и тест на граничные случаи вокруг этого сценария.

Плюсы — потокобезопасность, безопасное хранение в `HashMap` как ключ, предсказуемое поведение при передаче в методы.

Минус: конкатенация в цикле даёт O(n²) по копированию — используйте `StringBuilder`.

### String, StringBuilder, StringBuffer

| Класс | Изменяемый | Потокобезопасный | Когда использовать |
|-------|------------|------------------|-------------------|
| `String` | нет | да (как объект) | Константы, ключи, возврат из API |
| `StringBuilder` | да | нет | Сборка текста в одном потоке |
| `StringBuffer` | да | да (устаревший подход) | Legacy-код; в новом коде — `StringBuilder` |

```java
StringBuilder sb = new StringBuilder();
for (String part : parts) {
    if (!sb.isEmpty()) sb.append(',');
    sb.append(part);
}
String result = sb.toString();
```

- фрагмент показывает прикладной сценарий по теме раздела: здесь есть входные данные, операции над ними и проверяемый итог.

- `StringBuilder` снижает число промежуточных объектов: строка накапливается в изменяемом буфере и превращается в `String` только в конце.
- после запуска стоит проверить именно эффект этого примера — вывод, значение переменной, статус ответа, состояние БД или результат теста.

### String pool и intern

Литералы вроде `"OK"` попадают в общий пул строк, поэтому JVM переиспользует один объект для одинаковых литералов.

```java
String a = "java";
String b = "java";
System.out.println(a == b); // true, один объект из пула

String c = new String("java");
System.out.println(a == c); // false, другой объект
System.out.println(a.equals(c)); // true, содержимое одинаковое
```

Разбор:
- фрагмент показывает прикладной сценарий по теме раздела: здесь есть входные данные, операции над ними и проверяемый итог.
- ключевые вызовы `println`, `String`, `equals` задают основную механику этого примера: обработку, проверку и формирование результата.
- здесь важно различие `==` и `equals` — первый сравнивает ссылки, второй — содержимое, что критично для строк и value-объектов.
- после запуска стоит проверить именно эффект этого примера — вывод, значение переменной, статус ответа, состояние БД или результат теста.
- при переносе в production обычно добавляют валидацию входа, явную обработку ошибок и тест на граничные случаи вокруг этого сценария.

`intern()` возвращает каноническую строку из пула. Используйте его точечно и только после измерений, потому что это trade-off между памятью и стоимостью операций.

### Unicode и символы за пределами BMP

`char` в Java хранит 16-битную единицу UTF-16, а некоторые символы (эмодзи, редкие иероглифы) занимают две единицы.

```java
String s = "A😀B";
System.out.println(s.length()); // 4, а не 3
System.out.println(s.codePointCount(0, s.length())); // 3
```

Если вы обрабатываете пользовательский текст, чаще безопаснее работать с code points, а не с индексами `char`.

### Строки в JSON и SQL

- Для JSON старайтесь использовать сериализаторы (`Jackson`, `Gson`), а не ручную конкатенацию.
- Для SQL всегда применяйте `PreparedStatement`, не склеивайте запросы строками.

```java
String sql = "select * from users where email = ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, email);
}
```

Разбор:
- фрагмент показывает прикладной сценарий по теме раздела: здесь есть входные данные, операции над ними и проверяемый итог.
- ключевые вызовы `prepareStatement`, `setString` задают основную механику этого примера: обработку, проверку и формирование результата.
- параметризация через `PreparedStatement` отделяет SQL-шаблон от пользовательских данных и закрывает типичный риск SQL-инъекции.
- после запуска стоит проверить именно эффект этого примера — вывод, значение переменной, статус ответа, состояние БД или результат теста.
- при переносе в production обычно добавляют валидацию входа, явную обработку ошибок и тест на граничные случаи вокруг этого сценария.

### Производительность

1. Не конкатенируйте `String` в цикле — `StringBuilder` или `String.join`.
2. Не вызывайте `+` в hot path для сборки SQL/JSON — шаблонизаторы или `StringBuilder`.
3. Интернирование (`intern`) — только при доказанной необходимости; в modern JVM пул управляется иначе, чем в старых учебниках.

### Мини-чек-лист

- Сравнение строк идет через `equals`/`Objects.equals`, не через `==`.
- Кодировка явно указана на границе I/O ([ввод-вывод и файлы](./297.md)).
- Длинные текстовые шаблоны вынесены в text blocks.
- Конкатенации в циклах заменены на `StringBuilder` или `join`.
