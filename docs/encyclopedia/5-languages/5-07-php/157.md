## Пространства имён PHP - уникальные имена классов

В крупном проекте десятки библиотек и сотни классов. Без разделения имён неизбежны коллизии: два пакета могут объявить класс `User`, `Logger` или `Exception`. **Пространство имён (namespace)** — это логический префикс, превращающий короткое имя в уникальное: `App\Model\User` и `Vendor\Security\User` — разные типы.

Пространства имён не создают "папки в памяти" и не влияют на производительность напрямую. Это соглашение об именовании, которое связывают с файловой структурой через **PSR-4** и **Composer**. Подробнее об инструменте зависимостей: [Composer](/encyclopedia/5-languages/5-07-php/111).

## Объявление и полное имя

Пространство объявляется в начале файла (до любого исполняемого кода, кроме `declare`):

```php
<?php
declare(strict_types=1);

namespace App\Service;

class Mailer
{
    public function send(string $to, string $body): void
    {
        // ...
    }
}
```

Разбор:
- `declare(strict_types=1);` включает строгую проверку скалярных типов в этом файле, чтобы ошибки типов проявлялись сразу.
- `namespace App\Service;` задает полное имя класса как `App\Service\Mailer` и изолирует его от одноименных классов в других пакетах.
- Сигнатура `send(string $to, string $body): void` фиксирует контракт метода: на вход только строки, на выходе нет возвращаемого значения.
- Внутри класса пока нет реализации отправки (`// ...`), но архитектурно это уже готовая точка расширения для SMTP/API-провайдера.
- Такой формат объявления помогает IDE и статическим анализаторам проверять корректность вызовов еще до запуска кода.

**Полное имя класса (FQCN)** — `App\Service\Mailer`. Внутри того же namespace можно писать коротко: `new Mailer()`.

Вложенность отражает архитектуру, а не обязательную глубину каталогов:

```
App\
  Http\Controller\
  Model\
  Repository\
```

Разбор:
- Блок показывает не код выполнения, а архитектурную схему иерархии пространств имен.
- Корневой префикс `App\` обычно соответствует корню исходников (`src/`) в PSR-4-настройке.
- Вложенные сегменты (`Http\Controller`, `Model`, `Repository`) помогают разделять ответственность по слоям.
- Такая декомпозиция снижает коллизии имен и упрощает навигацию по проекту для команды.

## Оператор use — импорт и алиасы

Чтобы не писать FQCN в каждой строке, подключают имена через `use`:

Разбор:
- `use`-импорты сокращают длинные FQCN и делают сигнатуры конструктора/методов читаемыми.
- Конструктор с `private Mailer $mailer` демонстрирует dependency injection: контроллер получает готовый сервис извне.
- Метод `complete(User $user)` принимает строго типизированную модель пользователя и не работает с "сырыми" массивами.
- `DateTimeImmutable` используется как безопасный тип даты/времени без мутаций состояния объекта.
- Через `$this->mailer->send(...)` контроллер делегирует инфраструктурную задачу отдельному сервису, а не смешивает роли.

**Алиас** — когда короткое имя занято или неудобно:

```php
use App\Legacy\Logger as LegacyLogger;
use Psr\Log\LoggerInterface;

class Worker
{
    public function __construct(
        private LoggerInterface $logger,
        private LegacyLogger $legacy,
    ) {}
}
```

Разбор:
- `as LegacyLogger` создает алиас, чтобы явно различать два логгера с потенциально близкими именами.
- `LoggerInterface` задает контракт по PSR, поэтому класс зависит от абстракции, а не от конкретной реализации.
- Внедрение двух зависимостей через конструктор делает класс тестопригодным: можно подменить реализации моками.
- Такой подход удобен для поэтапной миграции legacy-кода: старый логгер остается, но новый интерфейс уже внедрен.
- Код показывает, как `use` решает конфликт имен без переименования самих классов в исходниках.

Импорт функций и констант (PHP 5.6+):

```php
use function App\Support\config;
use const App\Support\APP_VERSION;

echo config('app.name'), APP_VERSION;
```

Разбор:
- `use function` импортирует функцию по имени, позволяя вызывать ее без полного namespace.
- `use const` аналогично импортирует константу, делая конфигурационный код короче и чище.
- В `echo` сначала вызывается `config(...)`, затем выводится `APP_VERSION`; оператор запятой у `echo` печатает оба значения последовательно.
- Такой стиль снижает шум от длинных префиксов и сохраняет читабельность в точках частого использования.
- Особенно полезно в bootstrap-коде, где конфиг и константы используются в каждой второй строке.

Групповой импорт (PHP 7.0+):

```php
use App\Model\{User, Post, Comment};
```

Разбор:
- Это групповой импорт: общий префикс `App\Model\` указывается один раз.
- Внутри фигурных скобок перечисляются сущности, которые реально используются в файле.
- Запись уменьшает дублирование и риск опечаток в повторяющихся namespace-сегментах.
- При рефакторинге групповой импорт проще поддерживать: меняется один префикс вместо нескольких строк.

## Глобальное пространство и встроенные классы

Классы без `namespace` живут в **глобальном** пространстве. Встроенные типы (`Exception`, `DateTime`, `PDO`) тоже глобальные. Внутри `namespace App\...` обращение к ним требует префикса `\`:

```php
namespace App\Util;

// Ошибка: ищется App\Util\Exception
// throw new Exception('fail');

throw new \Exception('fail');           // верно
$now = new \DateTimeImmutable();        // верно
```

Разбор:
- Внутри `namespace App\Util` неполное имя `Exception` искалось бы как `App\Util\Exception`, что и приводит к ошибке.
- Префикс `\` указывает на глобальное пространство имен и явно выбирает встроенные классы PHP.
- Этот прием обязателен для классов ядра (`\Exception`, `\DateTimeImmutable`, `\PDO`) в namespaced-коде.
- Явная квалификация делает код предсказуемым и защищает от случайного затенения пользовательскими классами.

## Связь с файлами — PSR-4

Стандарт **PSR-4** задаёт правило: префикс namespace → корневая папка, остаток пути = остаток namespace + имя класса.

| FQCN | Путь к файлу (при префиксе `App\` → `src/`) |
|------|---------------------------------------------|
| `App\Model\User` | `src/Model/User.php` |
| `App\Http\Controller\HomeController` | `src/Http/Controller/HomeController.php` |

Имя файла совпадает с именем класса, расширение `.php`. Один класс (или enum, trait, interface) — один файл.

В `composer.json` проекта:

```json
{
  "autoload": {
    "psr-4": {
      "App\\": "src/"
    }
  }
}
```

Разбор:
- Раздел `autoload.psr-4` связывает namespace-префикс `App\\` с директорией `src/`.
- Двойной обратный слеш нужен, потому что это JSON-строка с экранированием.
- После изменения конфигурации требуется пересобрать автозагрузчик (`composer dump-autoload`), иначе карта классов не обновится.
- Этот блок формирует фундамент, на котором работает `new App\...` без ручных `require`.

После `composer dump-autoload` подключают единую точку входа:

```php
<?php
require __DIR__ . '/vendor/autoload.php';

use App\Model\User;

$user = new User();
```

Разбор:
- `require __DIR__ . '/vendor/autoload.php';` подключает единый автозагрузчик Composer.
- `use App\Model\User;` импортирует класс, чтобы ниже использовать короткое имя `User`.
- `new User()` запускает цепочку автозагрузки: Composer по PSR-4 ищет и подключает нужный файл автоматически.
- Такой bootstrap убирает ручное подключение файлов и снижает риск порядка загрузки.
- В production это стандартная точка входа для CLI-скриптов и web-entrypoint.

Интерпретатор при первом обращении к `User` вызывает автозагрузчик Composer, который по карте PSR-4 подключает файл.

## Ручная автозагрузка (без Composer)

Для учебных скриптов достаточно `spl_autoload_register`:



<ExternalCodeEmbed example="php/php-507-157-002" title="Ручная автозагрузка (без Composer)" minHeight={354} />



Разбор:
- `spl_autoload_register(...)` регистрирует callback, который PHP вызывает при первом обращении к неизвестному классу.
- Проверка `str_starts_with($class, $prefix)` ограничивает обработку только собственным namespace-пулом (`App\\`).
- `substr(...)` и `str_replace('\\', '/', ...)` переводят FQCN в относительный путь файла по правилам PSR-4.
- `is_file($file)` служит защитой от `require` несуществующего пути и лишних warning-сообщений.
- Это учебная минимальная автозагрузка; в реальном проекте лучше Composer, потому что он покрывает и зависимости из `vendor`.

В продакшене почти всегда используют Composer: он объединяет автозагрузку проекта и всех зависимостей из `vendor/`.

## Типичные ошибки

| Ситуация | Что происходит |
|----------|----------------|
| Файл не в том каталоге относительно PSR-4 | `Class "App\Model\User" not found` |
| Опечатка в `namespace` и в `use` | Класс не находится или подключается "чужой" |
| `require` старого файла с тем же классом | Fatal error: Cannot declare class ... |
| Циклические зависимости классов | Ошибка при загрузке; рефакторинг через интерфейсы |

**Нельзя** объявлять два класса с одним FQCN. **Нельзя** смешивать в одном файле несколько именованных классов в строгих проектах (PSR-1 рекомендует один класс на файл).

## Практика в веб-приложении

Типичная структура без фреймворка:

```
project/
  public/
    index.php      ← единственная точка входа для HTTP
  src/
    Http/
    Model/
    Service/
  vendor/
    autoload.php
  composer.json
```

`public/index.php` только подключает autoload и делегирует маршрутизацию. Вся логика — в классах с namespace `App\...`. Это совпадает с подходом Laravel и Symfony, где корень приложения отделён от публичной директории.

## Пошаговый план миграции legacy-проекта на PSR-4

Если проект начинался с `require` и глобальных функций, переход делайте поэтапно:

1. Добавьте `composer.json` и `autoload.psr-4` для префикса `App\\`.
2. Перенесите сначала новые классы в `src/` без трогания старых файлов.
3. Введите `public/index.php` как единую точку входа и подключайте `vendor/autoload.php`.
4. Постепенно переносите legacy-код в классы и заменяйте ручные `require`.
5. После каждой итерации выполняйте `composer dump-autoload` и smoke-тесты.

Такой подход снижает риск "большого взрыва" и позволяет мигрировать систему без остановки разработки.

## Мини-чеклист качества по namespaces

- В каждом файле совпадают путь, `namespace` и имя класса.
- Для внешних зависимостей используются `use` и алиасы.
- Встроенные глобальные классы (`\DateTimeImmutable`, `\PDO`, `\Exception`) явно префиксованы там, где нужно.
- В проекте нет дублирующихся FQCN.
